# Security hardening checklist

**Consolidated mitigations from the "Mitigating security threats" chapter — host validation, TLS, brute force, token leakage, redirect URIs, FAPI/OAuth 2.1, and session limits — for hardening an RHBK realm/deployment.**

## Checklist
- **Validate the hostname.** RHBK derives the public hostname from request headers and
  does not validate it; it is used in token `issuer` fields and password-reset URLs.
  Behind no proxy/LB, configure acceptable hostnames via the hostname SPI / fixed
  frontend URL to prevent host-header injection.
- **Require SSL/HTTPS.** Set the realm SSL mode to `All requests` in production (see
  [[realm-administration]]). HTTPS prevents man-in-the-middle access-token theft; SSL is
  **not** enabled by default. On clients, keep the SSL trust manager enabled with a
  truststore to block DNS MITM.
- **Enable brute force detection** plus a strong password policy and OTP — see
  [[brute-force-detection]], [[password-policies]], [[otp-policies]].
- **Restrict redirect URIs.** Avoid unspecific/open redirect URIs; use the
  `auth-flow-enforce` executor / client policies where needed.
- **Adopt FAPI / OAuth 2.1 compliance** via client policies — this enforces SSL,
  secure redirect URIs, and other best practices automatically.
- **Limit token exposure.** Shorten access-token lifespans (Timeouts page), keep refresh
  tokens private to the client, and optionally issue holder-of-key (mTLS-bound) tokens.
  Keep the authorization-code lifespan under ~10 s. See [[tokens-and-sessions]].
- **Limit scope & audience.** Use per-client Scope mappings / client scopes to trim the
  roles in a token, and limit token audiences in low-trust environments.
- **Have a key-compromise plan.** Rotate and remove compromised signing keys, then push
  a **not-before** revocation policy so clients fetch new public keys and reject tokens
  signed with the old key — see [[realm-keys-and-rotation]].
- **Protect the Admin Console / REST API.** Bearer-token auth makes CSRF infeasible; you
  can additionally validate CORS origins on the admin REST API.
- **Read-only / validated user attributes.** Mark sensitive attributes read-only and
  validate user-supplied attribute values (user profile).
- **Limit authentication sessions** when using the Data Grid provider — each
  `RootAuthenticationSessionEntity` can hold many sub-sessions, so cap them to bound the
  authentication-session cache memory. See [[distributed-caches]].

## Contradictions / caveats
- Bodies sourced are RHBK **26.0**; the chapter (Mitigating security threats) is present
  in 26.2/26.4 primary results. OAuth 2.1 / FAPI client-policy specifics evolve across
  26.0/26.2/26.4/26.6 — verify against your version.
- Passwords are stored hashed (Argon2 default, or PBKDF2-HMAC-SHA512 under FIPS), never
  in cleartext — see [[password-policies]].
