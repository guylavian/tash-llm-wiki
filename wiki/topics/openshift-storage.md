# OpenShift Storage

**Storage in Kubernetes/OpenShift is split into a producer abstraction (the PersistentVolume) and a consumer request ([[persistent-volume-claim]]), bridged either by pre-provisioned volumes or, far more commonly, by a [[storage-class]] driving on-demand provisioning through a [[csi-driver]].**

## The PV/PVC model
- A **PersistentVolume (PV)** describes an actual piece of storage: backend type, capacity, access modes, reclaim policy, volume mode.
- A **[[persistent-volume-claim]] (PVC)** is a namespaced *request* for storage matching some size/access-mode/volume-mode — the abstraction application manifests actually reference, hiding backend detail.
- **Access modes**: ReadWriteOnce (RWO), ReadOnlyMany (ROX), ReadWriteMany (RWX), ReadWriteOncePod (RWOP — restricts to one specific pod cluster-wide, stricter than RWO's "one node"). Choosing RWO for a multi-replica workload that needs concurrent writers from several pods is the textbook **Multi-Attach error**.
- **Volume mode**: `Filesystem` (default, mounted as a directory) or `Block` (raw block device handed to the pod).

## Binding vs dynamic provisioning
- If a pre-created PV already matches a PVC's request, a control loop binds them directly — no provisioning needed.
- Otherwise, if the PVC names (or defaults to) a **[[storage-class]]**, that class's `provisioner` — a [[csi-driver]] for modern backends — **dynamically provisions** a brand-new volume sized and typed to the request, creates the PV object, and binds it to the PVC. This is what makes "just create a PVC" work without an admin pre-staging volumes.
- **A PVC that names no StorageClass, when no default StorageClass exists, has nothing to bind to and stays `Pending` forever** — the single most common storage failure mode, and the first thing to check (inferred synthesis of the binding/provisioning chain above) before suspecting the backend itself.

## Reclaim policy
When a bound PVC is deleted, the underlying PV's `reclaimPolicy` decides its fate:
- **`Retain`** — the PV survives with its data; an admin must manually delete the PV and, separately, the backing storage asset if it should truly go away. Reusing it later requires clearing its `claimRef`.
- **`Delete`** (the dynamic-provisioning default) — the PV and its backing storage asset are removed automatically. Retain is the safer default for data that must never be silently destroyed by a PVC deletion.

## StorageClass tuning that changes behavior under the hood
- **`volumeBindingMode: WaitForFirstConsumer`** delays provisioning until a pod actually consumes the PVC, so the volume lands in the right topology for that pod's scheduling constraints — `Immediate` (the default) can otherwise bind/provision a volume the scheduler then can't reach, producing an unschedulable pod on topology-constrained backends.
- **`allowVolumeExpansion: true`** is required before a bound PVC can request more space later.

## Kubernetes-upstream vs OpenShift-specific
- The PV/PVC/StorageClass/CSI model itself is pure upstream Kubernetes — OpenShift adds no new API surface here. What's OpenShift-specific is *operational*: OCP ships CSI drivers for its supported cloud/on-prem platforms out of the box and documents day-2 tasks like changing the cluster default StorageClass and expanding persistent volumes as first-class admin procedures.
