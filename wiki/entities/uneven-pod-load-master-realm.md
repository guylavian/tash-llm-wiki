# Uneven pod load / LOGIN_ERROR flood behind Kong/NGINX ingress

**Symptom → cause → fix for one pod hot, all pods flooding LOGIN_ERROR/user_not_found, near-zero throughput.**

## Body
**Symptom.** One pod shows much higher CPU than the others; all pods flood with
`LOGIN_ERROR` / `user_not_found` warnings; ~100% error rate and near-zero useful
throughput.

**Cause.** Auth is being sent to
`POST /realms/master/.../token` with `client_id=admin-cli`. The reserved
**master** realm has no application users, so every failed login still runs the
full DB lookup + Infinispan check + thread-pool slot — burning capacity without
authenticating anyone. (Often a load test hammering the wrong endpoint.)

**Fix.** Point auth at the **application** realm:
```
POST /realms/<application-realm>/protocol/openid-connect/token
```
with the app's registered client ID and a valid user. Make each client/thread do
its own independent login (JMeter: add an HTTP Cookie Manager that clears cookies
each iteration). Clear any brute-force lockout on the admin account.

Applies to RHBK 26.x clustered behind Kong / NGINX Ingress.

## Contradictions / caveats
This is a request-routing/test-design issue, not a load-balancer stickiness bug.
For genuine session-affinity questions on OpenShift see the gated pointers in
[[troubleshooting-index]] (kb:7075697, kb:7076310).
