# OTP policies (TOTP / HOTP)

**Realm-level policy (Authentication → Policy → OTP Policy) that configures the one-time-password generator (FreeOTP / Google Authenticator) used as a second factor, choosing between time-based (TOTP) and counter-based (HOTP) algorithms.**

RHBK renders a QR code on the OTP setup page from these settings.

## TOTP vs HOTP
- **TOTP** (time-based): hashes the current time + shared secret; valid only within a
  short window. More secure (short matchable window); no DB write per login, so better
  under load, but a TOTP can be reused within its valid interval unless disabled.
- **HOTP** (counter-based): hashes a shared counter incremented on each successful
  login. More user-friendly (no time limit to type), but requires a **DB update on every
  increment** — a performance drain under heavy load.

## Configuration options
TOTP and HOTP share:
- **OTP hash algorithm** — default `SHA1`; `SHA256`/`SHA512` are more secure.
- **Number of digits** — OTP length (shorter = friendlier, longer = more secure).
- **Look around window** — number of intervals the server tries when generator/server
  clocks drift. Default `1`; for a 30 s interval that accepts a 90 s window (±30 s).

TOTP-only:
- **OTP token period** — interval in seconds for regenerating the TOTP.
- **Reusable code** — whether an OTP may be reused; **off by default** (admin must
  explicitly allow reuse).

HOTP-only:
- **Initial counter** — starting counter value.

OTP is wired into login via the Conditional OTP sub-flow in [[authentication-flows]];
it only prompts when the user has an OTP credential configured.

## Contradictions / caveats
- Bodies sourced are RHBK **26.0**; OTP policy options are consistent in 26.2/26.4
  primary results.
- The default hash algorithm `SHA1` is for compatibility; prefer `SHA256`/`SHA512`
  for new realms (see [[security-hardening-checklist]]).
