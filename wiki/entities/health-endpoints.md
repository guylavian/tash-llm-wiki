# Health endpoints and Kubernetes probes

**RHBK exposes four REST health endpoints on the management port `9000`, returning `200 OK`/`503` plus a JSON `status`, for wiring Kubernetes startup/liveness/readiness probes.**

## The four endpoints

- `/health/started` — **startup** probe for initial boot, before liveness takes over.
- `/health/live` — **liveness**: if it fails, terminate and restart the instance.
- `/health/ready` — **readiness**: only route traffic once it succeeds; a failure means temporarily unavailable, divert traffic elsewhere.
- `/health` — accumulates all health-check procedures.

Each returns HTTP `200 OK` on success or `503 Service Unavailable` on failure, with a JSON body `{"status":"UP","checks":[...]}`. Per-check entries can include `Keycloak Initialized`, `Graceful Shutdown`, `Keycloak cluster health check`, and `Keycloak database connections async health check`.

## Enabling and placement

Enable with the **build-time** option:

```
bin/kc.[sh|bat] build --health-enabled=true
```

Enabling health also turns on **async server bootstrap** by default (HTTP ports open while bootstrapping). Endpoints sit on the management port (`9000`) by default — see [[management-port]]. If `http-management-health-enabled=false`, the health endpoints stay on the **main** HTTP(S) ports instead; in that case block external traffic to `/health` at your proxy.

## Probing

- **curl**: `curl --head -fsS http://localhost:9000/health/ready` — exit status 0 means live/ready.
- **Kubernetes**: define an HTTP probe (not a liveness *command*). With mTLS `https-client-auth=required` the management interface inherits it; set `https-management-client-auth` to `request` or `none` so probes don't need a client cert.
- **HEALTHCHECK in Containerfile**: the image strips `curl`, so use BASH `/dev/tcp`:
  `{ printf 'HEAD /health/ready HTTP/1.0\r\n\r\n' >&0; grep 'HTTP/1.0 200'; } 0<>/dev/tcp/localhost/9000`

In multi-site HA, `health/ready` is checked periodically to mark a Pod ready, and a separate `lb-check` endpoint on the load balancer confirms the cluster is up. See [[ha-cross-site]].

## Contradictions / caveats

- The in-container `curl` removal is a deliberate security measure across 26.x — run probes from outside the container or use the `/dev/tcp` trick.
- `health-enabled` is **build-time**: changing it requires a re-build (or re-augmentation), not just a restart flag.
