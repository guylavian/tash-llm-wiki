# Brute force detection

**Realm feature (Realm settings → Security defenses → Brute Force Detection) that temporarily or permanently locks an account after repeated login failures; disabled by default.**

## Lockout modes
- **Temporary lockout** — disables the account for a growing period as the attack
  continues and failures hit multiples of *Max Login Failures*.
- **Permanent lockout** — disables the account until an administrator re-enables it.

When locked, RHBK returns the generic `Invalid username or password` message so an
attacker cannot tell the account is disabled.

## Key parameters (defaults)
| Parameter | Meaning | Default |
|---|---|---|
| Max Login Failures | Threshold of failures | 30 |
| Quick Login Check Milliseconds | Minimum time between attempts | 1000 ms |
| Minimum Quick Login Wait | Lock time when attempts are faster than the quick-login check | 1 min |
| Wait Increment | Time added per temporary lockout | 1 min |
| Max Wait | Maximum temporary lockout | 15 min |
| Failure Reset Time | Window after which the failure count resets | — |

**Wait-time strategies:** *By multiples* (default) increments wait when the failure
count is a multiple of Max Login Failures — `Wait Increment * (count / Max Login
Failures)` (integer division). *Linear* increments once count ≥ Max Login Failures —
`Wait Increment * (1 + count - Max Login Failures)`.

## Trade-off
Brute-force lockout makes the server vulnerable to **denial-of-service**: an attacker who
knows account names can deliberately trigger lockouts. Combine with a strong
[[password-policies]] and OTP rather than relying on lockout alone. Authentication
sessions can also be capped (see [[security-hardening-checklist]]).

## Contradictions / caveats
- Bodies sourced are RHBK **26.0**; defaults and the two wait strategies are consistent
  in 26.2/26.4 primary results.
- The DoS exposure is inherent to lockout; consider permanent lockout only with an
  admin re-enable process in place.
