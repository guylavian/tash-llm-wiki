# RHBK database schema auto-migration

**RHBK migrates the relational database schema automatically the first time it
connects to the database; a manual mode lets you export the SQL and apply it
yourself.**

## Body
This same mechanism handles both RH-SSO 7.6 → RHBK migration (RHBK can reuse the
existing RH-SSO database instance) and RHBK version-to-version upgrades.

### Automatic (default)
Start the server connected to the target database. If the schema changed for the
new version, it is migrated in place. With the Operator the schema is migrated
automatically the first time RHBK connects.

### Manual
Set the JPA migration strategy to `manual`:

```
kc.sh start --spi-connections-jpa-quarkus-migration-strategy=manual
```

The server checks whether migration is needed, writes the required DDL to
`bin/keycloak-database-update.sql`, and then **exits**. Review/apply the SQL
yourself, then start normally. Change the output path with:

```
kc.sh start --spi-connections-jpa-quarkus-migration-export=<path>/<file.sql>
```

## Contradictions / caveats
- **Single-version-at-a-time rule:** never let two different server versions
  access the same database concurrently. Shut down RH-SSO 7.6 (or the old RHBK
  pods) before the migrating instance starts. The Operator enforces this with its
  default `recreate` upgrade strategy — see [[operator-cr-migration]].
- Migrating the **embedded database** managed by the RH-SSO 7.6 Operator is **not
  supported**; convert it to an external user-provisioned database first.
- Always back up the database before migrating; auto-migration is one-way (inferred —
  the migration checklist lists "Database backup was created" as a precondition, but
  the cited notes don't state the one-way/no-rollback characterization explicitly).
