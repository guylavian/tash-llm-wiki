# Step-up authentication (ACR / LoA)

**A flow pattern that grants access to clients or resources based on the user's achieved authentication assurance level, prompting an additional factor only when a higher level is required.**

## How it works
- The realm maps **ACR** (Authentication Context Class Reference) string values to
  numeric **LoA** (Level of Authentication) values in Realm settings (and optionally per
  client, though realm-level mapping is the best practice) — see [[realm-administration]].
- A custom browser flow places authenticators in **Conditional** sub-flows keyed on LoA
  conditions. The first sub-flow satisfies level 1 (e.g. password); a higher sub-flow
  adds a 2nd factor for level 2.
- A client requests a level by sending `acr_values` or the `claims` parameter in the
  OIDC request; the resulting `acr` claim appears in the access and ID tokens. The flow's
  conditions compare the requested LoA against what the user has already satisfied and
  prompt the extra factor only if needed.

This is built with the requirement types and Conditional sub-flows described in
[[authentication-flows]] and typically uses [[otp-policies]] or WebAuthn as the
higher-level factor.

## Contradictions / caveats
- Bodies sourced are RHBK **26.0**; ACR→LoA mapping and the step-up flow are present in
  26.2/26.4 primary results. Refer to the official OIDC spec and the version-specific
  step-up documentation for `acr_values` semantics.
