# Session Persistence — Database-backed vs Volatile Caches

**By default RHBK persists user sessions in the database and caches them in
Infinispan; the cache can instead be made the source of truth to cut DB load, at
the cost of losing all sessions if every node restarts.**

## The two modes
- **Database-backed (default).** Sessions, clients, realms and other entities are
  stored in the database and **cached** in Infinispan. In the multi-cluster model
  the DB is **synchronously replicated** across both sites, and a cache write
  emits an invalidation via the `work` cache. This is why "no data loss" holds
  across site failures — the durable copy is in the replicated DB.
- **Volatile (cache as source of truth).** You can stop persisting sessions to the
  DB to reduce database load and IOPS. See [[distributed-caches]] for the required
  cache settings (≥2 owners, unlimited entries). Trade-off: **all sessions are
  lost if every pod restarts**, since nothing durable backs them.

## Sizing impact (why the default exists)
- DB-backed sessions cost roughly **1400 write IOPS and 0.35–0.7 vCPU per 100
  login/logout/refresh requests/s** on Aurora multi-AZ — significant, hence the
  volatile option for high-throughput, lower-durability needs.
- A pod's base footprint (~1250 MB RAM) already assumes ~10,000 cached sessions;
  caches refill from the DB after a restart, so do not size resources only for the
  warm steady state.
- For >2500 concurrent clients, default 10,000-entry caches overflow and the DB
  becomes a bottleneck; the guide suggests enlarging the `users` cache by 2× and
  `realms` cache by 4× the concurrent client count.

## Relation to load shedding (not the same thing)
`http-max-queued-requests` caps the in-flight request **queue** (HTTP 503 past the
limit) — a throughput-protection knob, independent of where sessions are stored.

## Contradictions / caveats
- Volatile sessions break the multi-cluster durability guarantees — only use where
  losing all sessions on a full restart is acceptable.
- Token/session **lifespans and semantics** (offline sessions, refresh tokens) are
  covered in [[tokens-and-sessions]]; this page is about *where* session state
  lives, not how long it is valid.
- Sizing numbers are guide starting points (RHBK 26.x); always run your own load
  tests.
