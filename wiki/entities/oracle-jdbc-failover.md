# Oracle JDBC failover broken over TCPS at RHBK startup

**Symptom → cause → fix for RHBK failing to fail over between Oracle SCAN/`ADDRESS` hosts over TLS at startup.**

## Body
**Symptom.** RHBK startup fails connecting to Oracle with
`ORA-17002: I/O error: sleep interrupted, Authentication lapse 0 ms` and
`Got Refused, SessionTraceId=...`. With a `FAILOVER=ON` / `LOAD_BALANCE=OFF`
`ADDRESS_LIST`, the driver retries only the first SCAN host and never reaches the
second `ADDRESS`. Placing the working host *second* succeeds; placing it *first*
fails consistently — proof the driver cannot fail over.

**Cause.** Defect in the **Oracle JDBC thin driver 23.2.0.0.0** (the version
bundled in affected setups). After a Refuse packet, the TLS handshake in
`NSProtocolNIO.establishConnectionAfterRefusePacket` is interrupted
(`InterruptedIOException: sleep interrupted`) instead of moving on to the next
address. The `Authentication lapse 0 ms` confirms failure at the TLS layer
before DB authentication.

**Fix.** Replace the Oracle JDBC driver JAR with a version per the RHBK
*Supported Configurations* article. Confirm `DriverVersion=23.2.0.0.0` in the
startup logs (that is the affected version), drop in the corrected JAR in the
providers directory, and restart.

Air-gap: stage the corrected driver JAR in your internal mirror before deploying.

Applies to RHBK 26.0.x / 26.2.x / 26.4.x with Oracle (JDBC thin, TCPS/TLS).

## Contradictions / caveats
This is a driver-version fix, not a connection-string fix — the `FAILOVER=ON`
syntax is correct. For JDBC *URL format* errors (a different failure mode) see
the gated [[troubleshooting-index]] DB section (kb:7059141).
