# Authorization resources and scopes

**A resource is the object being protected (a page, REST endpoint, file, EJB, or a group/type of them); a scope is a bounded action or attribute on that resource (view, edit, delete, cost…). Together they are the targets that [[authorization-permissions|permissions]] protect.**

## Resource
A resource has a unique id and can represent one concrete asset (e.g. "Alice's Banking Account") or a whole class ("Banking Account"). Fields when created (Console or [[protection-api]]):
- **Name** — human-readable, unique.
- **Type** — a string grouping resource *instances*, used by **typed permissions** to apply common policy to all resources of that type. Default resource type is `urn:resource-server-name:resources:default`.
- **URIS** — locations/addresses; for HTTP resources these are the relative paths served (the default resource uses `/*`).
- **Scopes** — zero or more scopes associated with the resource.
- **Attributes** — key/value pairs (value may be one or many comma-separated strings) surfaced to policies during evaluation (enables ABAC).
- **Owner** — defaults to the resource server, but can be set to a user id (then you can write owner-based policies; central to the UMA "Alice's account" sharing model).

## Scope
A scope is "one of the potentially many verbs that can logically apply to a resource" — typically an action (view/edit/delete) but it can also name a slice of data (e.g. a `cost` scope on a `project` resource for cost-specific policies). Scopes are managed under the **Authorization Scopes** tab.

## Resource- vs scope-based protection
- A [[authorization-permissions|resource-based permission]] protects the resource as a whole (optionally **Apply to Resource Type** for all resources of a type).
- A **scope-based permission** protects specific scopes, optionally narrowed to one resource — finer granularity over the actions allowed.

## Remote management
With Remote Resource Management enabled, resource servers register/update/delete/query resources remotely through the [[protection-api]] (Resource Registration Endpoint), and may set a user id so a resource belongs to that user.

## Contradictions / caveats
- Bodies are consistent across RHBK **26.0–26.6**. The guide notes a forward-looking aspiration ("In the future… allow users to control their own resources") — owner self-service today is bounded to the UMA Account Console "My Resources" flow, not full self-management.
