# Security Context Constraints (SCC)

**An SCC is cluster-level policy that decides what security-sensitive things a pod may request** — which UID it runs as, whether it can use host networking/PID, the Linux capabilities it keeps, and the volume types it may mount. It is the OpenShift admission gate that has no vanilla-Kubernetes equivalent (the nearest upstream analogue is Pod Security Admission).

## The default — `restricted-v2`
- Runs containers with a **random, high, non-root UID** from the namespace's allocated range, drops most Linux capabilities, and forbids privilege escalation, host networking, and host-path volumes.
- This is *stricter than upstream Kubernetes by default*. An image that hardcodes `USER 0` / writes to a fixed UID-owned path / binds a privileged port (<1024) is admitted on plain Kubernetes but **fails on OpenShift** — the canonical "works on my kind cluster, CrashLoopBackOff on OCP" surprise (inferred: this is the highest-frequency porting failure).

## How a pod gets an SCC
- SCCs are granted to the pod's **ServiceAccount** (via RBAC). At admission, OpenShift picks the SCC the pod's identity is allowed to use and that admits the pod's requested securityContext; if none admits it, the pod is **rejected** (or mutated to fit).
- The fix for a root-assuming image is to make it UID-agnostic (group `root`/GID 0 with group-writable dirs), **not** to grant `anyuid` broadly — widening the SCC is the anti-pattern.
