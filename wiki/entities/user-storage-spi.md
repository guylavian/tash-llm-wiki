# User Storage SPI

**The SPI for bridging an external proprietary user/credential store into RHBK's user metamodel — the same SPI the built-in LDAP and Active Directory federation is implemented on top of.**

## When user lookup hits the SPI

On a user lookup (e.g. login) RHBK checks, in order: the user cache, then its local database, then it loops through each enabled User Storage provider until one returns the user. The provider queries the external store and maps the result to RHBK's `UserModel`. Providers are enabled and configured **per realm** under the **User Federation** tab (they are not enabled by default). This is the engine under [[ldap-user-federation]].

## Provider & factory

- Provider class implements `org.keycloak.storage.UserStorageProvider` (a sparse base interface with `preRemove(...)` callbacks for realm/group/role removal). Instances are created **per transaction** and `close()`d when the transaction completes.
- Factory implements `org.keycloak.storage.UserStorageProviderFactory<T>` and **must** name the concrete provider class as the type parameter — the runtime introspects it to discover which capability interfaces the provider supports. `create(KeycloakSession, ComponentModel)` allocates the provider; `ComponentModel` carries the per-realm instance id and configuration.

## Capability interfaces (mix-ins)

You implement only the capabilities your external store supports:

| Interface | Purpose |
|---|---|
| `UserLookupProvider` | log in with users from the store (almost always implemented) |
| `UserQueryMethodsProvider` | complex queries to view/manage users in the admin console |
| `UserCountMethodsProvider` | count queries |
| `UserQueryProvider` | combined query + count capability |
| `UserRegistrationProvider` | add/remove users |
| `UserBulkUpdateProvider` | bulk updates across many users |
| `CredentialInputValidator` | validate credential types (e.g. passwords) |
| `CredentialInputUpdater` | update credential types |

## Model & storage ids

Returned users implement `org.keycloak.models.UserModel`. The critical method is `getId()`, whose format **must** be:

```
"f:" + component id + ":" + external id      e.g.  f:332a234e31234:wburke
```

The component id (from `ComponentModel.getId()`) lets the runtime route a lookup straight to the originating provider without polling every provider; the external id (username/uid) lets that provider find the user in the external store.

Caveat: WebAuthn limits the user-handle to 64 bytes. To stay within that, assign a short component id in `validateConfiguration(...)` using `KeycloakModelUtils.generateShortId()` (22 chars, leaving 40 for the external id).

Security: any attribute used to link/establish identity (e.g. the built-in LDAP provider's `LDAP_ID`) must be made read-only so users cannot edit it.

## Packaging & deployment

Add `META-INF/services/org.keycloak.storage.UserStorageProviderFactory` listing the factory FQCNs, build the JAR, copy it to `providers/`, then run `kc.sh build`. Connecting to an external relational store uses RHBK's additional-datasource config; obtain its entity manager via `session.getProvider(JpaConnectionProvider.class, "user-store").getEntityManager()`. Quickstarts exist for a JPA-backed and a properties-file-backed provider. See [[spi-provider-model]] for the general packaging rules.

## Contradictions / caveats

- The capability-interface model is consistent across RHBK 26.0–26.6. The named additional-datasource pattern (`user-store`) is the RHBK/Quarkus way; RH-SSO 7.x used `getDefaultProvider`-style datasource wiring.
- This SPI customizes user *federation*. For protocol-level claim shaping use protocol mappers; for login-flow steps use authenticators — see [[spi-provider-model]].
