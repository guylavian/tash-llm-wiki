# Distributed tracing (OTLP exporter and sampling)

**RHBK records OpenTelemetry spans for the request lifecycle via a supported Quarkus OTel extension, exporting in batches over gRPC OTLP to `http://localhost:4317` by default, with configurable sampling to control volume.**

## Enabling

In **RHBK 26.4/26.6** (`opentelemetry` feature on by default):

```
bin/kc.[sh|bat] start --tracing-enabled=true
```

In **26.0** the feature must be named explicitly:

```
bin/kc.[sh|bat] start --tracing-enabled=true --features=opentelemetry
```

Defaults: batch export, `grpc` protocol, endpoint `http://localhost:4317`, service name `keycloak` (`tracing-service-name`, takes precedence over `service.name` in `tracing-resource-attributes`). The `tracing-*` options can override the global [[opentelemetry-centralization]] settings to ship traces to a different collector.

For development, `jaegertracing/all-in-one` bundles an OTel collector + UI (ports `16686` UI, `4317` gRPC, `4318` HTTP).

## What is in a trace

Spans are created for: incoming HTTP requests; outgoing DB calls (incl. acquiring a connection); outgoing LDAP requests (incl. connecting); outgoing HTTP incl. IdP brokerage. Tags are prefixed `kc.` — e.g. `kc.clientId`, `kc.realmName`, `kc.sessionId`, `kc.token.id`, `kc.token.issuer`, `kc.token.sid`, `kc.authenticationSessionId`, `kc.authenticationTabId`. A sampled trace also carries the user events of that request (LOGIN/LOGOUT/REFRESH_TOKEN) and LDAP communication errors as log entries.

## Trace IDs in logs

When tracing is on, log lines include `traceId`, `parentId`, `spanId`, and a `sampled` flag, so logs correlate to a request. Hide them per handler with `log-<handler>-include-trace`, e.g. `--log-console-include-trace=false`. Explicitly overriding a handler's log format disables trace inclusion for it.

## Sampling

`tracing-sampler-type` selects the sampler: `always_on`, `always_off`, `traceidratio` (default), `parentbased_always_on`, `parentbased_always_off`, `parentbased_traceidratio`.

- Default `traceidratio` uses `tracing-sampler-ratio`, default `1.0` (all traces). Range `[0,1]` in 26.4+ (`0.0` disables sampling at runtime); `(0,1]` in 26.0.
- **Production**: lower the ratio (e.g. `0.1` = 10%) to cap trace-store cost and overhead.
- `parentbased_traceidratio` keeps parent/child spans consistent (no incomplete traces) but is open to DoS via manipulated `tracestate` headers — filter trace headers and assess caller trust per W3C Trace Context.

## Kubernetes / Operator

Tracing propagates deployment info to containers. Filter in your backend by `service.name` (deployment), `k8s.namespace.name`, `host.name` (pod). The Operator auto-sets `KC_TRACING_SERVICE_NAME` and `KC_TRACING_RESOURCE_ATTRIBUTES` (the latter always includes `k8s.namespace.name` unless overridden). See [[rhbk-operator]].

## Contradictions / caveats

- **Maturity**: tracing is labelled **preview** in 26.0 (Server Configuration Guide ch.21). By 26.4/26.6 the Observability Guide treats it as the standard root-cause path and `opentelemetry` is on by default.
- **CR support**: 26.4+ allow tracing config via the Keycloak CR / advanced configuration; 26.0 had "no support for tracing configuration in the CR yet" — use `additionalOptions`.
- Ratio range and the `0.0`-disables behavior differ between 26.0 (`(0,1]`) and 26.4+ (`[0,1]`).
