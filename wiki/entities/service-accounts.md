# ServiceAccounts

**A ServiceAccount is an in-API-server identity for Pods and other automated clients, authorized like any other identity via [[kubernetes-rbac]] bindings.**

## Identity shape
- Username: `system:serviceaccount:<project>:<name>`.
- Every ServiceAccount is a member of two groups: `system:serviceaccounts` (all accounts) and `system:serviceaccounts:<project>` (accounts in that project).
- Every namespace gets a `default` ServiceAccount automatically; a Pod that doesn't name one gets `default` assigned to it.

## Tokens
- **Bound/projected tokens (recommended, upstream default since Kubernetes 1.22+)** — short-lived, audience-scoped JWTs issued via the `TokenRequest` API and mounted as a projected volume; they auto-rotate and are tied to the lifetime of the referencing object (Pod/Secret), so deleting the Pod invalidates the token immediately under a `TokenReview` check.
- **Legacy long-lived Secret tokens (deprecated)** — a static, non-expiring, non-rotating token Secret. Kubernetes ≥1.24 stopped auto-generating these by default; **OpenShift stopped auto-generating a long-lived API token Secret per ServiceAccount starting in 4.16** — existing ones keep working post-upgrade but new ServiceAccounts don't get one (OpenShift-specific timeline layered on the upstream deprecation).
- Verification: the recommended `TokenReview` API invalidates a bound token the instant its backing object (Pod/Secret/ServiceAccount) is deleted; OIDC-style validation instead trusts the token until its stated expiry, so it lags a deletion.

## OpenShift-specific: automatic image pull secrets
OpenShift auto-generates an image pull secret per ServiceAccount to wire up the internal image registry with user auth — but only when the `ImageRegistry` cluster capability/integrated registry is enabled; disabling it later deletes the previously generated pull secrets automatically. This has no upstream Kubernetes equivalent (there's no cluster-internal registry concept upstream).

## Granting permissions
Bind a Role/ClusterRole to the ServiceAccount exactly as for a user or group — RBAC treats it identically ([[kubernetes-rbac]]). This is also the SCC-admission path: an SCC is granted to a ServiceAccount, not directly to a Pod (see [[security-context-constraints]]).
