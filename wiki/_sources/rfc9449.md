# RFC 9449 — OAuth 2.0 Demonstrating Proof of Possession (DPoP)

Sender-constrains access (and optionally refresh) tokens by binding them to a per-client public key. The client proves possession of the matching private key on each request via a signed DPoP proof JWT, so a stolen token alone is useless.

## dpop-sender-constraining

### DPoP proof JWT structure (§4.2)
- RULE: JOSE header `typ` MUST be `dpop+jwt`; `alg` MUST be a registered **asymmetric** signature alg (never `none`, never symmetric); `jwk` carries the public key and MUST NOT contain the private key (§4.2).
  - ANTI-PATTERN: emitting `typ:JWT`, accepting `alg:none`/HS256, or leaking the private key in `jwk`.
  - SYMPTOM: RS rejects with `invalid_dpop_proof`; proofs are forgeable / key-confused; security review flags symmetric DPoP.
- RULE: Required claims — `jti` (unique, unguessable), `htm` (request method), `htu` (target URI sans query/fragment), `iat` (creation time) (§4.2).
  - ANTI-PATTERN: reusing/sequential `jti`; omitting `htm`/`htu`; binding `htu` with the query string attached.
  - SYMPTOM: replay not detectable; valid proofs rejected because `htu` never matches; `invalid_dpop_proof`.
- RULE: When calling a protected resource the proof MUST include `ath` = base64url(SHA-256(ASCII access-token value)); include `nonce` when a server supplied one (§4.2, §7).
  - ANTI-PATTERN: dropping `ath` on resource calls; hashing the wrong token; ignoring the issued nonce.
  - SYMPTOM: RS returns `invalid_dpop_proof`; one proof reusable across different tokens.

### AS binds token to the proof key (§5, §6.1)
- RULE: On the token endpoint the AS MUST associate the issued token with the DPoP proof's public key and return `token_type: DPoP` (§5). JWT access tokens carry the binding as `cnf.jkt` = base64url JWK SHA-256 Thumbprint (§6.1).
  - ANTI-PATTERN: issuing a `Bearer` token; omitting `cnf/jkt`; binding to the wrong/AS key instead of the client proof key.
  - SYMPTOM: RS cannot confirm binding → treats token as bearer or rejects; sender-constraining silently absent.

### RS validates proof + confirms binding (§4.3, §7.1)
- RULE: RS MUST verify (§4.3): exactly one `DPoP` header; single well-formed JWT; all required claims present; `typ=dpop+jwt`; `alg` asymmetric and not `none`; signature verifies against embedded `jwk`; `jwk` has no private key; `htm`/`htu` match the actual request; `nonce` matches if one was issued; `iat` within an acceptable window; and `ath` equals the presented token's hash **and** the token's bound key (`jkt`) equals the proof's `jwk` thumbprint (§4.3 item 12).
  - ANTI-PATTERN: validating the proof signature but never confirming `jkt` == thumbprint(`jwk`); skipping `htm`/`htu`/`ath`.
  - SYMPTOM: a proof from key A accepted with a token bound to key B → sender-constraining bypassed; pen-test finding.
- RULE: For a DPoP-bound token the RS MUST require a `DPoP` header and MUST NOT grant access unless every check passes (§7.1).
  - ANTI-PATTERN: accepting the token without an accompanying proof.
  - SYMPTOM: stolen token usable as a bearer token; binding defeated.

### Reject bearer-scheme downgrade (§7.2)
- RULE: A DPoP-bound access token presented via the `Bearer` scheme (RFC 6750) MUST be rejected (§7.2).
  - ANTI-PATTERN: RS that falls back to bearer validation for a DPoP token.
  - SYMPTOM: attacker strips DPoP and replays as `Authorization: Bearer …`; should fail but doesn't.

### DPoP-Nonce mechanism (§8, §9)
- RULE: AS MAY require a server nonce; if missing it returns HTTP 400 with error `use_dpop_nonce` and a fresh `DPoP-Nonce` header; RS signals the same via HTTP 401 + `WWW-Authenticate: DPoP` + `DPoP-Nonce`. Nonce values MUST be unpredictable; AS MUST reject a proof whose `nonce` doesn't match a recently supplied value (§8, §9).
  - ANTI-PATTERN: predictable/static nonces; client not retrying with the returned nonce; server not echoing a new nonce.
  - SYMPTOM: infinite 400/401 loop ("use_dpop_nonce") in client logs; tickets about DPoP requests failing until retried.

### Replay protection (§11.1, §11.3)
- RULE: Servers MUST accept proofs only within a short time window after `iat` (seconds/minutes), SHOULD enforce one-time use via `jti` tracking (store jti or its hash), and SHOULD use server nonces to further cut replay (§11.1).
  - ANTI-PATTERN: unbounded/large `iat` skew; no `jti` cache; relying on `ath` alone.
  - SYMPTOM: captured proof replayable within a long window; duplicate-request abuse.
- RULE: Once a nonce has been provided to a client, the server MUST NOT accept proofs lacking the `nonce` claim (no downgrade) (§11.3).
  - ANTI-PATTERN: accepting nonce-less proofs after issuing a nonce.
  - SYMPTOM: nonce protection silently bypassable.

### Algorithm restrictions (§4.2, §4.3, §11.6)
- RULE: Implementations MUST allow only secure asymmetric signature algorithms for DPoP proofs; `none` MUST NOT be allowed (§11.6).
  - ANTI-PATTERN: an `alg` allowlist that includes `none` or HMAC families.
  - SYMPTOM: forged proofs accepted; audit/CVE-class finding.

### ath token-substitution binding (§7)
- RULE: RS MUST recompute SHA-256 of the presented token and verify it equals `ath`; this stops one proof being reused with different tokens, but does not by itself stop replay — the `iat`/nonce window still matters (§7).
  - ANTI-PATTERN: trusting `ath` without recomputation; treating `ath` as full replay defense.
  - SYMPTOM: proof/token mix-and-match accepted; replay within window unaddressed.

### Error codes & challenge (§7.1)
- RULE: RS challenges with `WWW-Authenticate: DPoP`; `error=invalid_dpop_proof` (proof fails §4.3), `error=use_dpop_nonce` (nonce required next), `error=invalid_token` (token/binding invalid); SHOULD advertise acceptable proof algs via the `algs` parameter (§7.1).
  - ANTI-PATTERN: returning generic 401/`invalid_token` for proof problems; omitting `algs`.
  - SYMPTOM: clients can't tell why they failed or which alg to use; harder interop/debugging.

### Long-lived-token / pre-generation caveat (§11.2)
- RULE: Without the nonce mechanism, proofs can be pre-generated (attacker picks `iat`), so deployments not using nonces SHOULD NOT issue long-lived DPoP-constrained access tokens (§11.2).
  - ANTI-PATTERN: long token lifetimes + no server nonce.
  - SYMPTOM: exfiltrated pre-built proofs prove only possession of a proof, not the key; window of misuse widens.

### Scope notes (§11.4, §11.7)
- DPoP fails if an adversary runs code in the client's context (can mint proofs while online); non-exportable keys limit but don't eliminate this (§11.4).
- DPoP signs only HTTP method + URI, not body/other headers — request-payload integrity relies on TLS (§11.7).
