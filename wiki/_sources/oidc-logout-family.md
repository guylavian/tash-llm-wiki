# OIDC Logout family (RP-Initiated / Front-Channel / Back-Channel / Session Management) — raw staging note

Distilled load-bearing requirements, grouped by the wiki concept they feed. Each bullet: RULE (+ spec/section) / ANTI-PATTERN / SYMPTOM. Paraphrased tightly. Four OIDF specs cover this family: RP-Initiated Logout (RPIL), Front-Channel Logout (FCL), Back-Channel Logout (BCL), Session Management (SM).

## rp-initiated-logout
- RULE (RPIL §2.1): OP MUST publish `end_session_endpoint` in discovery metadata; it is the HTTPS URL the RP redirects the user agent to in order to request logout. ANTI-PATTERN: RP hardcodes a guessed logout path / OP omits the metadata. SYMPTOM: logout button 404s or hits wrong path; "end session endpoint not found".
- RULE (RPIL §2, §6): `id_token_hint` is RECOMMENDED on the logout request. If it is ABSENT (or the supplied ID Token doesn't belong to the current OP session), the OP MUST ask the End-User to confirm logout before acting. ANTI-PATTERN: silent logout on any unauthenticated GET. SYMPTOM: DoS / forced-logout — attacker links log the victim out without consent.
- RULE (RPIL §2): when `client_id` is sent together with `id_token_hint`, the OP MUST verify the client_id matches the `aud` of that ID Token. ANTI-PATTERN: trusting client_id without cross-checking the token. SYMPTOM: mismatched-client logout request accepted; wrong RP context.
- RULE (RPIL §2, §3): `post_logout_redirect_uri` MUST have been previously registered, and the OP MUST NOT redirect unless the supplied value EXACTLY matches one registered value. ANTI-PATTERN: substring/prefix/wildcard match, or redirecting to any caller-supplied URL. SYMPTOM: open-redirect after logout / "invalid post_logout_redirect_uri" ticket; phishing landing page.
- RULE (RPIL §3, §4): OP MUST NOT perform post-logout redirection if it cannot confirm the target's legitimacy, and any failed validation MUST abort the operation (no redirect on error). ANTI-PATTERN: redirecting on a partially-validated request. SYMPTOM: user bounced to attacker site even though logout "failed".
- RULE (RPIL §2): OP MUST support BOTH HTTP GET and POST at the end-session endpoint (GET = query string, POST = form-encoded). ANTI-PATTERN: GET-only logout. SYMPTOM: POST logout returns 405; SPA/back-end logout integration breaks.
- RULE (RPIL §2): if the RP sends `state`, the OP MUST echo it back on the post-logout redirect; `ui_locales` is a hint and unsupported locales SHOULD NOT cause an error. ANTI-PATTERN: dropping state / erroring on unknown locale. SYMPTOM: RP can't correlate the logout callback (CSRF/return-path confusion); locale request rejected.
- RULE (RPIL §4): it is NOT an error for the RP to request logout when the OP doesn't consider the user logged in (logout is idempotent). ANTI-PATTERN: returning an error on already-logged-out. SYMPTOM: spurious error on double-click / repeated logout.

## back-channel-logout
- RULE (BCL §2.4): the Logout Token is a signed JWT whose REQUIRED claims are `iss`, `aud`, `iat`, `exp`, `jti`, and an `events` claim containing the member `http://schemas.openid.net/event/backchannel-logout`; it MUST contain `sub` and/or `sid`. ANTI-PATTERN: reusing a plain ID Token / omitting `events` or both subject claims. SYMPTOM: RP rejects token; "logout_token missing events/sub/sid"; logout silently no-ops.
- RULE (BCL §2.4, §4.1): a `nonce` claim MUST NOT be present in a Logout Token (prevents misuse as an ID Token); explicit typing `typ: logout+jwt` is RECOMMENDED to prevent cross-JWT confusion. ANTI-PATTERN: minting the logout token through the ID-Token path (carries nonce / wrong typ). SYMPTOM: token confusion / RP treats it as an auth token, or RP rejects for nonce-present.
- RULE (BCL §2.6): RP MUST validate the Logout Token like an ID Token — verify signature (`alg: none` MUST NOT be used), `iss`/`aud`/`iat`/`exp`, presence of `sub`/`sid`, presence of the `events` member, and ABSENCE of `nonce`. ANTI-PATTERN: accepting unsigned or unvalidated logout tokens. SYMPTOM: forged logout token logs users out (DoS), or replay across sessions.
- RULE (BCL §2.2): RP advertises `backchannel_logout_uri`; `backchannel_logout_session_required` indicates whether the RP requires a `sid` in the token. ANTI-PATTERN: registering a back-channel URI but not honoring sid requirement / OP not sending sid. SYMPTOM: logout can't target the right session; "sid required" rejection.
- RULE (BCL §2.5): OP sends an HTTP POST (`application/x-www-form-urlencoded`) with a `logout_token` form parameter to the RP's back-channel URI. ANTI-PATTERN: GET, JSON body, or token-in-query. SYMPTOM: RP can't parse request; 400; logout not delivered.
- RULE (BCL §2.7): on a valid token the RP locates the session(s) by `iss`+`sub` and/or `sid` and clears that state; refresh tokens (without offline_access) for that session SHOULD be revoked. ANTI-PATTERN: relying on the token to be an ID Token / not clearing the session / leaving refresh tokens live. SYMPTOM: "logged out" user still has a live session via cached cookie or refresh token.
- RULE (BCL §2.8): RP MUST return HTTP 200 (or 204) on success and HTTP 400 on a bad/invalid Logout Token; response SHOULD set `Cache-Control: no-store`. ANTI-PATTERN: returning 200 on failure, or caching the logout response. SYMPTOM: OP can't tell logout failed (no retry/alert); cached logout endpoint.
- RULE (BCL §4): the signed Logout Token is the DoS defense; OPs SHOULD use short `exp` (preferably ≤ ~2 minutes). ANTI-PATTERN: long-lived logout tokens. SYMPTOM: captured logout token replayable for a long window.

## (supporting — front-channel & session management, context for the two concepts above)
- RULE (FCL §2): RP registers `frontchannel_logout_uri` whose scheme/host/port MUST match a registered redirect URI; OP renders it in an `<iframe>` and the RP MUST clear cookies/local-storage on receipt; response SHOULD set `Cache-Control: no-store`. ANTI-PATTERN: front-channel URI on an unrelated origin / not clearing state. SYMPTOM: iframe logout doesn't fire, session lingers. (context for [[rp-initiated-logout]])
- RULE (FCL §2): if the OP adds `iss`/`sid` query params, it MUST include BOTH; the RP MAY validate them against the ID Token's claims. ANTI-PATTERN: sending only one, or ignoring mismatch. SYMPTOM: RP can't bind the logout to the right session.
- RULE (FCL §4.1, SM §5.1): front-channel/iframe logout is unreliable when browsers block third-party content/cookies — back-channel logout is the resilient alternative; deployments SHOULD add defensive detection. ANTI-PATTERN: relying solely on front-channel for critical logout. SYMPTOM: intermittent "still logged in elsewhere" reports in modern browsers. (reinforces [[back-channel-logout]] as the durable mechanism)
- RULE (SM §2, §3.2): `session_state` (opaque salted hash of client_id + origin + OP user-agent state) is returned to enable RP session monitoring; OP SHOULD include `sid` in ID Tokens when session params are used — `sid` is the join key for both front- and back-channel logout. ANTI-PATTERN: no `sid` issued, so logout can't target a specific session. SYMPTOM: logout affects all-or-nothing sessions instead of the right one.
- RULE (SM §3.1, §3.2, §6): both OP and RP iframes MUST enforce postMessage origin checking and reject messages from any other origin (XSS/cross-origin defense); RP re-authenticates with `prompt=none` on a "changed" message but MUST NOT on "error". ANTI-PATTERN: accepting postMessage from any origin / re-auth loop on error. SYMPTOM: cross-origin session-state spoofing, or infinite re-auth "changed" loop.
