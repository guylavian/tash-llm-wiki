# RFC 8705 — OAuth 2.0 Mutual-TLS Client Authentication and Certificate-Bound Access Tokens

Two independent mechanisms: (1) authenticate OAuth clients at the token endpoint with an X.509 client cert over mutual TLS (`tls_client_auth` PKI mode, or `self_signed_tls_client_auth`); (2) sender-constrain access/refresh tokens by binding them to the client's TLS cert (`cnf.x5t#S256` thumbprint), so a stolen token is useless without the matching cert + private key.

## mtls-bound-tokens

### Two mTLS client-auth methods (§2.1, §2.2)
- RULE: `tls_client_auth` (PKI) — AS validates the cert chain to a trusted CA, then matches exactly ONE registered subject value: `tls_client_auth_subject_dn` or one SAN (`_san_dns`/`_san_uri`/`_san_ip`/`_san_email`). Only one such metadata field per client (§2.1, §2.1.2).
  - ANTI-PATTERN: registering multiple subject matchers; matching on a partial/normalized DN; trusting any CA in the truststore rather than the agreed anchor.
  - SYMPTOM: client authenticates with the wrong cert; or auth fails with `invalid_client`; DN-normalization mismatches across vendors.
- RULE: `self_signed_tls_client_auth` — AS does NOT validate the chain; it matches the presented cert against the client's registered certs in `jwks`/`jwks_uri` (via JWK `x5c`) and confirms private-key possession via the TLS handshake (§2.2, §2.2.2).
  - ANTI-PATTERN: chain-validating a self-signed cert; registering the cert by thumbprint only and failing to update `jwks` on rotation.
  - SYMPTOM: handshake/cert-chain errors for self-signed certs; auth breaks silently after cert rotation until `jwks` is updated.
- RULE: Every mTLS-authenticated request MUST include the `client_id` parameter; failed cert auth returns `invalid_client` (§2, §2.3).
  - ANTI-PATTERN: relying on the cert alone to identify the client; omitting `client_id`.
  - SYMPTOM: AS can't resolve which client/match to apply → `invalid_client`.

### Certificate binding mechanism (§3)
- RULE: When mTLS is used at the token endpoint the AS MAY bind the issued access token to the client cert; binding is INDEPENDENT of the auth method (a public client can get a cert-bound token without OAuth-layer mTLS auth) (§3, §1).
  - ANTI-PATTERN: assuming cert binding requires `tls_client_auth`/confidential client; binding to the AS cert instead of the client cert.
  - SYMPTOM: public/native clients can't sender-constrain; tokens not actually bound.
- RULE: AS MUST only issue a cert-bound token for a cert whose private-key possession the client proved in the TLS handshake (§6.1).
  - ANTI-PATTERN: binding to a cert presented but not proven (no client_auth in handshake).
  - SYMPTOM: binding forgeable; pen-test finding.
- RULE: A client requesting a cert-bound token over a NON-mutual-TLS connection may receive an UNBOUND token; mTLS-intending clients MUST use the `mtls_endpoint_aliases` URL when the AS publishes one (§3.4, §5).
  - ANTI-PATTERN: hitting the conventional token endpoint when an mTLS alias exists; expecting binding without presenting a cert.
  - SYMPTOM: token silently unbound (no `cnf`); intermittent "token not bound" depending on which host/endpoint was used.
- RULE: Binding covers token-endpoint flows (authorization_code, refresh_token); the implicit grant is explicitly OUT OF SCOPE (§6.4).
  - ANTI-PATTERN: trying to cert-bind implicit-flow tokens.
  - SYMPTOM: no binding path for browser implicit clients.

### `cnf` / `x5t#S256` confirmation claim (§3.1, §3.2)
- RULE: The binding is carried in the `cnf` claim as member `x5t#S256` = base64url(SHA-256(DER-encoded client cert)), with trailing `=` padding omitted (RFC 4648 §5). In JWT access tokens it's the `cnf` payload claim; for introspection it's a top-level `cnf` in the response JSON (§3.1, §3.2, §9.1).
  - ANTI-PATTERN: hashing the PEM/base64 text instead of the raw DER; hashing the public key/SPKI instead of the whole cert; leaving `=` padding; using SHA-1 `x5t`.
  - SYMPTOM: thumbprints never match → RS returns `invalid_token`; interop failures with conformant ASes.

### RS validation of a cert-bound token (§3.2, §3.4, §6.2)
- RULE: The RS MUST obtain the client cert from the (mutually authenticated) TLS layer, compute SHA-256 of its DER encoding, and require an EXACT match against the token's `cnf.x5t#S256`; on mismatch reject with HTTP 401 + `invalid_token` (§3.4, §3.2).
  - ANTI-PATTERN: treating the bound token as a bearer token; skipping the thumbprint compare; partial/prefix match.
  - SYMPTOM: stolen cert-bound token replayed without the cert is accepted → sender-constraining bypassed; or every request 401s because the cert isn't reaching the RS.
- RULE: The RS MUST NOT validate the cert's trust chain — mTLS here is purely a proof-of-possession channel, so any cert (incl. self-signed/expired) is acceptable as long as its thumbprint matches `x5t#S256` (§6.2).
  - ANTI-PATTERN: RS rejecting an expired/self-signed client cert during the PoP check; running full PKIX validation at the RS.
  - SYMPTOM: valid cert-bound requests rejected after the cert expires even though the thumbprint still matches.

### Metadata & registration (§3.3, §3.4, §5, §9)
- RULE: AS metadata `tls_client_certificate_bound_access_tokens` (boolean, default false) advertises the capability; client registration metadata of the same name (default false) signals client intent; `token_endpoint_auth_method` carries `tls_client_auth` / `self_signed_tls_client_auth` (§3.3, §3.4, §9.3).
  - ANTI-PATTERN: assuming binding when neither side advertised it; mismatched AS/client flags.
  - SYMPTOM: client expects a `cnf` that never appears.
- RULE: `mtls_endpoint_aliases` is an AS-metadata JSON object of alternative endpoint URLs (token, introspection, revocation, etc.) used to isolate mTLS so conventional clients aren't prompted for certs; mTLS clients MUST prefer the alias when present (§5).
  - ANTI-PATTERN: ignoring the alias; conventional clients hitting an mTLS host and getting cert prompts.
  - SYMPTOM: browser cert-selection prompts for non-mTLS clients; mTLS client requests go unbound because they used the plain endpoint.

### Security considerations (§6.3, §6.5, §7.1, §7.2, §7.4, §8)
- RULE: Binding rests on SHA-256 second-preimage resistance; if it weakens, register a new confirmation method for a stronger hash (§7.2).
  - ANTI-PATTERN: defining a custom hash; reusing SHA-1.
  - SYMPTOM: spec/interop drift; weak-hash audit finding.
- RULE (cert rotation): a cert-bound token becomes invalid when the client rotates its cert — treat like expiry: get a fresh token (via refresh) and retry (§6.3).
  - ANTI-PATTERN: long-lived bound tokens that outlive the cert; no refresh-on-rotation path.
  - SYMPTOM: `invalid_token` storm right after a cert renewal/rotation.
- RULE (refresh tokens): refresh tokens to CONFIDENTIAL `tls_client_auth`/`self_signed` clients are indirectly bound via the auth requirement; for PUBLIC clients the AS SHOULD bind the refresh token to the cert and re-validate on each refresh (§7.1, §4).
  - ANTI-PATTERN: handing a public client an unbound refresh token.
  - SYMPTOM: stolen public-client refresh token usable from anywhere.
- RULE (PKI spoofing): in `tls_client_auth`, a cert with the same subject (DN/SAN) from a DIFFERENT trusted CA can impersonate; the AS SHOULD restrict trust anchors to CAs meeting policy, agreed out-of-band (§7.4).
  - ANTI-PATTERN: trusting the OS/default CA bundle for client-cert auth.
  - SYMPTOM: impersonation via a same-subject cert from another CA; security review flags broad truststore.
- RULE (TLS termination): TLS MAY terminate at a reverse proxy / load balancer, but securely conveying the client cert (or its thumbprint) from the proxy to the app server is OUT OF SCOPE — get it right or the binding is unverifiable (§6.5).
  - ANTI-PATTERN: trusting an unauthenticated client-cert header (e.g. spoofable `X-SSL-Client-Cert`) injected past the proxy.
  - SYMPTOM: header-spoofing bypass of the PoP check; RS validates a cert the client never presented.
- RULE (TLS version / X.509 validation / privacy): applies to any TLS version supporting client-cert auth (TLS 1.2/1.3), per BCP 195; implementors SHOULD reuse a vetted X.509 library (basic constraints, key usage, validity, critical extensions, NUL-byte/wildcard handling, revocation) rather than hand-rolling; prefer TLS 1.3 since pre-1.3 sends the client cert in cleartext, enabling third-party correlation (privacy) (§7.3, §7.5, §8).
  - ANTI-PATTERN: custom X.509 parsing/validation; defaulting to TLS 1.2 for single-user/native clients.
  - SYMPTOM: CVE-class cert-parsing bugs; client cert observable on the wire on pre-1.3 connections.
