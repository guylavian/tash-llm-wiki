# RFC 9068 — JWT Profile for OAuth 2.0 Access Tokens

Defines a standard, validatable JWT layout for OAuth2 access tokens (header `typ`, required claims, RS validation steps). Resource-server (RS) validation is normative in Section 4; data layout in Section 2; security considerations in Section 5.

## access-token-validation-resource-server

- **RULE** (§2.1) — JWT access tokens MUST be signed; `alg` MUST NOT be `none`; AS MUST support RS256 among its signing algs. RS MUST validate the signature per RFC 7515 using the `alg` header.
  - **ANTI-PATTERN** — Accepting `"alg":"none"`, or decoding the JWT payload without verifying the signature at all.
  - **SYMPTOM** — Forged/unsigned tokens accepted; an attacker-crafted token passes; later: `invalid_token` only after a fix, or silent privilege grants in logs.

- **RULE** (§2.1) — JWT access token MUST carry header `typ` = `at+jwt` (or media type `application/at+jwt`) to explicitly declare it is a profile access token, distinguishing it from an OIDC ID Token.
  - **ANTI-PATTERN** — Issuing/accepting access tokens with `typ: JWT` or no `typ`; not pinning the expected type on the RS.
  - **SYMPTOM** — ID Tokens or other JWTs accepted as access tokens; interop tools warn "unexpected typ"; cross-token confusion.

- **RULE** (§4) — RS MUST reject any token whose `typ` is not `at+jwt`/`application/at+jwt`.
  - **ANTI-PATTERN** — Skipping the `typ` check because "it's still a valid JWT signed by our AS."
  - **SYMPTOM** — ID Token replayed at an API endpoint and honored; audit shows wrong token class used.

- **RULE** (§4) — RS MUST verify `iss` exactly matches the AS issuer identifier it trusts; current time MUST be before `exp` (small clock-skew leeway only, a few minutes max). If encrypted, decrypt with the keys/algs registered.
  - **ANTI-PATTERN** — Trusting any issuer, prefix/substring matching `iss`, or large/unbounded `exp` leeway.
  - **SYMPTOM** — Token from a different realm/AS accepted; expired tokens still work; "token from foreign issuer" incidents.

- **RULE** (§2.2) — Required claims in every profile access token: `iss`, `exp`, `aud`, `sub`, `client_id`, `iat`, `jti`. For grants with no resource owner (e.g. client credentials), `sub` SHOULD identify the client application.
  - **ANTI-PATTERN** — RS assuming `sub` is always an end user; missing-claim tolerance.
  - **SYMPTOM** — NPE / "missing sub|aud|exp" errors; client-credentials tokens mis-attributed to a human user.

- **RULE** (§4 / RFC 6750 §3.1) — On ANY validation failure, the RS response MUST use error code `invalid_token` (per RFC 6750 Bearer error handling).
  - **ANTI-PATTERN** — Returning generic 500 / `invalid_request`, or a 200 with empty data, on a bad token.
  - **SYMPTOM** — Clients can't distinguish "refresh the token" from a server bug; opaque 500s in tickets instead of `WWW-Authenticate: Bearer error="invalid_token"`.

## audience-and-scope-checks

- **RULE** (§4) — RS MUST validate that `aud` contains a resource indicator identifying THIS resource server; MUST reject the token if `aud` does not list this RS as a valid audience.
  - **ANTI-PATTERN** — Not checking `aud` at all, or accepting any token signed by the trusted AS regardless of intended audience.
  - **SYMPTOM** — A token minted for API-A is replayed against API-B and accepted (token substitution); "wrong audience" only caught downstream.

- **RULE** (§2.2.3) — When the request has a `scope`, the access token SHOULD carry a `scope` claim (RFC 8693 §4.2); every scope string MUST be meaningful for the resources named in `aud`.
  - **ANTI-PATTERN** — Treating scope as global/independent of audience; granting access on scope presence while ignoring `aud`.
  - **SYMPTOM** — Over-broad access; a scope valid for one API silently authorizes another.

- **RULE** (§3) — AS sets `aud` from the `resource` parameter (RFC 8707) when present (SHOULD match it), else a default resource indicator (MAY be inferred from `scope`). AS MUST NOT issue a token whose granted authorization would be ambiguous (e.g. multiple resources where a scope can't be unambiguously tied to one `aud` entry).
  - **ANTI-PATTERN** — Issuing a single token with many audiences and a flat scope set, leaving the RS to guess which scope applies to which resource.
  - **SYMPTOM** — RS over-authorizes because it can't disambiguate scope-to-resource; confused-deputy behavior.

- **RULE** (§4) — If the token carries authorization claims (scope/roles/groups/entitlements), the RS SHOULD use them together with its own contextual info to allow or reject the call.
  - **ANTI-PATTERN** — Authorizing on authentication alone (valid signature ⇒ full access), ignoring scope/roles.
  - **SYMPTOM** — Any valid token can hit any endpoint; missing fine-grained authz in pen-test findings.

- **RULE** (§2.2.3.1) — For non-delegation authorization attributes the AS SHOULD use the SCIM `roles`, `groups`, `entitlements` claim names (RFC 7643 §4.1.2).
  - **ANTI-PATTERN** — Inventing ad-hoc claim names per service; RS hardcoded to vendor-specific claims.
  - **SYMPTOM** — Brittle cross-service authz; claim-name drift between AS and RS.

## jwt-validation-pitfalls

- **RULE** (§5, with §2.1) — Explicit typing (`at+jwt`) per RFC 8725 prevents cross-JWT confusion between profile access tokens and OIDC ID Tokens.
  - **ANTI-PATTERN** — Relying only on claim shape (both look alike) instead of `typ`; RS that accepts ID Tokens as access tokens.
  - **SYMPTOM** — ID Token used as a bearer token and accepted; token-type confusion CVEs/findings.

- **RULE** (§5, ref RFC 8725 §2.8) — To prevent cross-JWT confusion, the AS MUST use a distinct `aud` identifier per resource so tokens for different resources from the same issuer can't be interchanged.
  - **ANTI-PATTERN** — Reusing one generic audience for all APIs; wildcard/shared audiences.
  - **SYMPTOM** — Token for resource X accepted at resource Y; lateral movement across APIs.

- **RULE** (§5) — Do NOT rely on different signing keys for ID Tokens vs access tokens as a security boundary: the RS must accept any key published in AS/OIDC discovery metadata, so compromising any one published key lets an attacker forge accepted JWTs.
  - **ANTI-PATTERN** — Assuming "ID Tokens are signed with a different key, so an ID Token can't be used as an access token"; treating key separation as isolation.
  - **SYMPTOM** — Single leaked/rotated key forges valid access tokens; algorithm/key-confusion exploitation.

- **RULE** (§5, with §2.2) — AS must prevent clients from influencing `sub` in confusing ways (e.g. registering an arbitrary `client_id` that becomes `sub` under client_credentials).
  - **ANTI-PATTERN** — Allowing client-chosen `client_id`/identifiers that collide with user identifiers in `sub`.
  - **SYMPTOM** — Client impersonates a user/another client via crafted `sub`; identity collision in authz decisions.

- **RULE** (§4) — Allow only minimal clock-skew leeway (a few minutes) on `exp`; reject thereafter.
  - **ANTI-PATTERN** — Wide/disabled expiry tolerance to "avoid clock complaints."
  - **SYMPTOM** — Long-expired tokens still accepted; replay window widened.
