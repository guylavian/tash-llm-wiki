# RFC 8414 — OAuth 2.0 Authorization Server Metadata

Load-bearing normative requirements distilled for the wiki. Tight paraphrase only — see the RFC for verbatim text.

## authorization-server-metadata-discovery

### Well-known URI construction (§3)
- **RULE:** Build the metadata URL by INSERTING `/.well-known/oauth-authorization-server` between the host and the path of the issuer identifier, over HTTPS. No path → `https://host/.well-known/oauth-authorization-server`. With path `…/issuer1` → `https://host/.well-known/oauth-authorization-server/issuer1`.
- **ANTI-PATTERN:** APPENDING the suffix to the end (OIDC Discovery style, `…/issuer1/.well-known/…`) instead of inserting it; or assuming the OIDC `/.well-known/openid-configuration` path is the same thing.
- **SYMPTOM:** 404 on the metadata document; client falls back to hardcoded endpoints; "discovery failed / metadata not found".

### Issuer identity validation (§3.3, §6.2)
- **RULE:** The `issuer` value in the returned document MUST be byte-identical to the issuer URL used to build the request. If they differ, the response MUST NOT be used.
- **ANTI-PATTERN:** Trusting the document without comparing its `issuer` to the requested issuer (trailing-slash drift, scheme/host mismatch silently accepted).
- **SYMPTOM:** Impersonation — attacker serves metadata carrying the legitimate `issuer` but their own endpoints/keys; clients then send credentials/codes to the attacker. Manifests as tokens accepted by the wrong AS, or auth flows redirecting to an unexpected host.

### Issuer used for AS mix-up defense (§2)
- **RULE:** The issuer identifier ties the metadata to a specific AS and is the anchor used to prevent authorization-server mix-up attacks when more than one AS is in play.
- **ANTI-PATTERN:** Treating endpoints as interchangeable across multiple ASes without binding each response/token back to its issuer.
- **SYMPTOM:** Mix-up attack — client redeems a code at the wrong AS / accepts a token minted by a different issuer; confused-deputy behavior.

### Required vs optional fields (§2)
- **RULE:** REQUIRED: `issuer` (HTTPS, no query/fragment), `response_types_supported`; `authorization_endpoint` (required unless no grant types use it), `token_endpoint` (required unless only implicit is supported). RECOMMENDED: `scopes_supported`. OPTIONAL: `jwks_uri` (HTTPS), `registration_endpoint`, `grant_types_supported` (defaults to `["authorization_code","implicit"]`), `token_endpoint_auth_methods_supported` (default `client_secret_basic`), `response_modes_supported` (default `["query","fragment"]`), `code_challenge_methods_supported` (PKCE).
- **ANTI-PATTERN:** Omitting `issuer` / `response_types_supported`; emitting zero-length arrays instead of omitting the member; relying on a field the AS never advertised.
- **SYMPTOM:** Client cannot construct authorization or token requests; "missing required metadata field"; PKCE silently skipped because `code_challenge_methods_supported` was absent.

### HTTP method & response format (§3.1, §3.2)
- **RULE:** Metadata is retrieved with HTTP GET; success is `200 OK` with `Content-Type: application/json`. Unknown/extra members are allowed; empty arrays MUST be omitted. Errors use an appropriate non-200 status.
- **ANTI-PATTERN:** Serving the doc as `text/html` or wrong content type; returning 200 with an error body; requiring POST.
- **SYMPTOM:** JSON parse failures; client rejects/ignores the document; intermittent discovery timeouts.

### TLS requirements (§6.1)
- **RULE:** The metadata endpoint and the `issuer` MUST use HTTPS. Clients MUST validate the server cert per RFC 6125; MUST support TLS 1.2+ with a confidentiality- and integrity-providing ciphersuite.
- **ANTI-PATTERN:** Plain HTTP metadata; disabling cert verification ("insecure"/`--insecure`); accepting self-signed or hostname-mismatched certs.
- **SYMPTOM:** MITM / DNS spoofing substitutes attacker endpoints and keys; "PKIX path building failed" / cert-validation errors when verification is correctly on.

### Signed metadata (§2.1)
- **RULE:** Metadata MAY be supplied as a `signed_metadata` member: a JWS-signed JWT containing an `iss` claim for the attesting party. When supported, its values OVERRIDE the corresponding plain-JSON members. Consumers MAY ignore it if unsupported. The `signed_metadata` member MUST NOT itself appear as a claim inside the JWT.
- **ANTI-PATTERN:** Reading plain JSON values while a `signed_metadata` JWT is present (and the client claims to support it); failing to check the signature/`iss`.
- **SYMPTOM:** Attacker-tampered unsigned values are used instead of the signed ones; signature-verification failures on the metadata JWT.

### Scope / out-of-band caveat (§6.3, §6.4)
- **RULE:** A standard metadata format aids attackers as much as legitimate clients — the same protections apply regardless of how metadata is published. Securely binding a protected resource to its AS is OUT OF SCOPE here.
- **ANTI-PATTERN:** Assuming publishing standardized metadata is itself a security boundary; pairing a resource with an AS without an independent trust check.
- **SYMPTOM:** Client uses the wrong resource/AS pairing; tokens replayed to an unintended resource without detection.
