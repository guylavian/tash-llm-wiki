# RHBK/Keycloak Requests Are Not Being Shared Evenly Between Pods Behind Kong / NGINX Ingress

RHBK/Keycloak Requests Are Not Being Shared Evenly Between Pods Behind Kong / NGINX Ingress
Environment
- Red Hat Build of Keycloak (RHBK)
- 26.x
Issue
- One pod shows significantly higher CPU utilisation than other pods in the cluster
- Inconsistent Load Distribution Across Keycloak Cluster Pods Behind Ingress
- RHBK pod logs are flooded with LOGIN_ERROR / user_not_found warnings at high frequency across all pods.
Resolution
- To fix the authentication issue during load testing, update the configuration with the correct realm-specific settings.
Token URL: `/realms/<application-realm>/protocol/openid-connect/token`
Client ID: Use the application's registered client ID
Username: Use a valid user account from the application realm
Grant Type: `password` (if supported by the application)
-
Clear any brute-force lockout on the admin account
-
Configure your load test tool so that each virtual user thread performs its own independent login rather than sharing a pre-authenticated session or reusing cookies across threads. In JMeter, set the HTTP Cookie Manager to clear cookies each iteration and ensure each thread group user executes the full authentication flow independently.
Root Cause
-
The root cause is a misconfigured load test plan sending authentication requests to the wrong Keycloak realm and client.
Keycloak's master realm and admin-cli client are reserved exclusively for internal administration purposes. They are not intended to serve application authentication traffic. When a load test tool targets POST /realms/master/protocol/openid-connect/token with client_id=admin-cli, every request fails with user_not_found because application users do not exist in the master realm.
Critically, failed authentication requests are not with low efforts. Each failed login still performs the full processing pipeline:- A database user lookup against the realm's user store
- An Infinispan distributed cache check
- A thread pool slot held for the full duration of the request lifecycle
At high concurrency, this means hundreds or thousands of expensive no-op requests per second saturate the executor thread pools across all pods simultaneously, producing the same CPU and latency symptoms that would be expected from a genuine application load but with a 100% error rate and zero useful throughput.
- A secondary risk arises from Keycloak's built-in brute-force protection. Repeated failed login attempts against a specific username on any realm including master will trigger account lockout if brute-force protection is enabled. Sustained load test runs with incorrect credentials can result in the Keycloak admin account being locked, disrupting legitimate administrative access to the cluster.
Diagnostic Steps
Step 1:— Examine pod logs for LOGIN_ERROR patterns
During or immediately after a load test run, check the logs of all RHBK pods for the presence of LOGIN_ERROR events:
kubectl logs <keycloak-pod-0> -n <namespace> | grep "LOGIN_ERROR"
kubectl logs <keycloak-pod-1> -n <namespace> | grep "LOGIN_ERROR"
kubectl logs <keycloak-pod-2> -n <namespace> | grep "LOGIN_ERROR"
If the output is dominated by entries similar to the following, the load test is targeting the wrong realm:
WARN [org.keycloak.events] type="LOGIN_ERROR", error="user_not_found",
realmName="master", clientId="admin-cli", username="<testuser>",
ipAddress="<load-test-source-ip>"
Pay attention to the realmName and clientId fields. If these show master and admin-cli respectively while your application realm is different, the load test configuration is the cause.
Step 2: Identify the source IP and correlate with the load test tool
The ipAddress field in the LOGIN_ERROR log entries will show the originating IP. Confirm this matches the host running your load test tool. If the IP belongs to your JMeter or load test machine, this confirms the requests are coming from the test plan and not from a misconfigured application service.
Step 3: Confirm the correct application realm and endpoint
Identify the realm your application actually uses by checking your application service logs or configuration. The correct token endpoint should be:
POST /realms/<your-application-realm>/protocol/openid-connect/token
Cross-reference this against what the load test plan is calling. Any deviation in the realm path is the configuration error to fix.
Step 4: Confirm test users exist in the correct realm
Before re-running the test, verify that the users referenced in the load test plan exist in the target application realm:
kubectl exec -n <namespace> <keycloak-pod-0> -- /opt/keycloak/bin/kcadm.sh get users -r <application-realm> --server http://localhost:8080 --realm master --user <admin-user> --password <admin-password>
If the command returns an empty list or does not include the test user accounts, create the necessary users before re-running the test.
Step 5: Check for brute-force lockout on the admin account
If the load test has been running with failed attempts against the master realm for a sustained period, check whether the admin account has been flagged or locked:
kubectl exec -n <namespace> <keycloak-pod-0> -- /opt/keycloak/bin/kcadm.sh get attack-detection/brute-force/users/<admin-user-id> -r master --server http://localhost:8080 --realm master --user <admin-user> --password <admin-password>
If the response shows numFailures above zero or disabled: true, the account has been affected by brute-force tracking.
