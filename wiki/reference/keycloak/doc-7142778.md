# Failover not working correctly when configuring Red Hat build of Keycloak with an Oracle Database

Failover not working correctly when configuring Red Hat build of Keycloak with an Oracle Database
Environment
- Red Hat build of Keycloak
- 26.0.X
- 26.2.X
- 26.4.X
Issue
When using the following connection string:
jdbc:oracle:thin:@(DESCRIPTION=...(ADDRESS_LIST=(FAILOVER=ON)(LOAD_BALANCE=OFF)(ADDRESS=(PROTOCOL=TCP)(HOST=<HOST 1>))(ADDRESS=(PROTOCOL=TCP)(HOST=<HOST 2>)))...
As far as we know from default JDBC
behavior, it should connect to the first connection <HOST 1>
, but the application keep connecting to the next host which is <HOST 2>
.
- Authentication lapse 0 ms is reported in the ORA-17002 message, confirming failure at the TLS layer before any DB authentication was attempted, with LOAD_BALANCE=OFF, placing the working host second in the ADDRESS_LIST succeeds, while placing it first fails consistent with failover to the second address being the only working path.
Error messages seen in Keycloak logs:
Got Refused, SessionTraceId = XXXXXXXX
ORA-17002: I/O error: sleep interrupted, Authentication lapse 0 ms
Datasource '<default>': ORA-17002: I/O error: sleep interrupted
ERROR: Failed to start server in (production) mode
ERROR: Failed to obtain JDBC connection
ERROR: Acquisition timeout while waiting for new connection
Stack trace pattern confirming the defect:
Caused by: java.io.InterruptedIOException: sleep interrupted
at oracle.net.nt.ConnStrategy.execute(ConnStrategy.java:718)
at oracle.net.resolver.AddrResolution.resolveAndExecute(AddrResolution.java:688)
at oracle.net.ns.NSProtocolNIO.establishConnectionAfterRefusePacket(NSProtocolNIO.java:567)
at oracle.net.ns.NSProtocolNIO.handleConnectPacketResponse(NSProtocolNIO.java:449)
Resolution
This issue has been reported to happen when using an outdated version from the Oracle JDBC
driver.
Ensure to update it according to the Red Hat build of Keycloak Supported Configurations Article.
Root Cause
-
The root cause is a known defect in Oracle JDBC thin driver version 23.2.0.0.0 affecting TCPS (TLS) connections when connect-time
failover is configured with multiple SCAN listener addresses.However, under TCPS, after receiving the Refuse packet, the driver attempts to re-establish the connection at the TLS layer via
NSProtocolNIO.establishConnectionAfterRefusePacket. In affected driver versions, this step is interrupted during the TLS handshake,
generating InterruptedIOException: sleep interrupted instead of gracefully failing over to the next address.The result is that the driver never reaches the second address in the connection string, repeats all configured retries (RETRY_COUNT)
against the same failing host, and ultimately throws ORA-17002, causing Keycloak to fail to obtain a JDBC connection at startup.The key indicator that identifies this as a driver-layer failure rather than a configuration or DB issue is Authentication lapse 0 ms
in the ORA-17002 message meaning zero time was spent in authentication, confirming the failure occurred at the network/TLS layer
before the database was ever reached.
Diagnostic Steps
Step 1: Check the Oracle JDBC driver version in use. It appears in the log output on startup:
For example:
DriverVersion=23.2.0.0.0
Alternatively, check the JAR deployed under the Keycloak providers directory.
Step 2: Confirm the Failure Pattern in Logs, with trace logging enabled, look for the following pattern on
startup:
1. Got Refused repeating against the same SCAN host across all retries
2. Same SessionTraceId value on every retry confirming the second address is never attempted
3. The socket options line confirming TCPS is in use: socketOptions={..., 38=TLS, ...}
4. The stack trace containing *NSProtocolNIO.establishConnectionAfterRefusePacket* followed by
InterruptedIOException: sleep interrupted Authentication lapse 0 ms in the ORA-17002 message
Example log sequence confirming the defect:
nt: host=<scan-hostname>, port=1234, socketOptions={..., 38=TLS, ...}
Got Refused, SessionTraceId = XXXXXXXX
...
Got Refused, SessionTraceId = XXXXXXXX -> same ID, same host, retry 2
...
ORA-17002: I/O error: sleep interrupted, Authentication lapse 0 ms
