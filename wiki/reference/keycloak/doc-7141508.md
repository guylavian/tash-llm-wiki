# Integrating Active Directory Kerberos SSO with Keycloak on Red Hat IdM Clients

Integrating Active Directory Kerberos SSO with Keycloak on Red Hat IdM Clients
Environment
- Red Hat Build of Keycloak (RHBK)
- 26.x
Issue
- Configuring Kerberos/SPNEGO SSO for Red Hat build of Keycloak with Active Directory on an IdM-enrolled RHEL System
- Bypassing Host IdM Configuration for Keycloak AD Kerberos Authentication
- Configuring an Isolated krb5.conf for Keycloak AD SSO on RHEL
Resolution
To resolve the dual-domain conflict and enable silent browser SSO, isolate Keycloak's Kerberos configuration from the host OS's IdM configuration.
Phase 1: Prepare Active Directory
Create a Service Account: In AD, create a standard user account for Keycloak (e.g., keycloak-svc). Enable AES-256 encryption in the account properties.
Generate the Keytab: Open a Command Prompt as a Domain Admin on the AD Domain Controller and map the Service Principal Name (SPN) to the account:
ktpass -out keycloak-ad.keytab -princ HTTP/sso.example.com@AD.EXAMPLE.COM -mapuser keycloak-svc@AD.EXAMPLE.COM -pass * -crypto AES256-SHA1 -ptype KRB5_NT_PRINCIPAL
(Note: The SPN HTTP/sso.example.com must exactly match the public URL users type into their browsers).
Move the resulting keycloak-ad.keytab to the RHEL VM (e.g., to /opt/keycloak/conf/).
Phase 2: Create an Isolated Kerberos Configuration
Do not modify the default /etc/krb5.conf managed by IdM. Instead, create a dedicated file for Keycloak/RHBK.
Create /opt/keycloak/conf/krb5-ad.conf:
[libdefaults]
default_realm = AD.EXAMPLE.COM
dns_lookup_realm = true
dns_lookup_kdc = true
[realms]
AD.EXAMPLE.COM = {
kdc = dc01.ad.example.com
admin_server = dc01.ad.example.com
default_domain = ad.example.com
}
[domain_realm]
.ad.example.com = AD.EXAMPLE.COM
ad.example.com = AD.EXAMPLE.COM
Ensure the Keycloak system user owns the keytab and the config file.
chown keycloak:keycloak /opt/keycloak/conf/keycloak-ad.keytab
chmod 600 /opt/keycloak/conf/keycloak-ad.keytab
Phase 3: Inject Configuration into the Keycloak JVM
Instruct the Keycloak Java process to bypass the OS Kerberos file and use your isolated AD configuration.
Modify Keycloak environment file (e.g., /etc/sysconfig/keycloak for systemd setups) and append the property to JAVA_OPTS_APPEND
:
JAVA_OPTS_APPEND="-Djava.security.krb5.conf=/opt/keycloak/conf/krb5-ad.conf"
Restart the Keycloak service.
Phase 4: Configure the Keycloak Admin Console
- Log in to the Keycloak Admin Console.
- Go to Authentication -> Flows -> Browser. Change the Kerberos execution requirement from DISABLED to
ALTERNATIVE (this ensures a fallback to a password form if SSO fails).
- Go to User Federation and select your existing Active Directory LDAP provider.
- Enable Allow Kerberos authentication and configure:
- Kerberos Realm: AD.EXAMPLE.COM
- Server Principal: HTTP/sso.example.com@AD.EXAMPLE.COM
- KeyTab: /opt/keycloak/conf/keycloak-ad.keytab
Phase 5: Client Browser Configuration
For the SPNEGO flow to succeed, the client's web browser must be configured to trust the Keycloak URL.
Google Chrome/Microsoft Edge (Windows):
Add the Keycloak URL (e.g., https://sso.example.com) to the Local Intranet Zone via Windows Internet Options (or GPO).
Mozilla Firefox:
Navigate to about:config and add the Keycloak domain (e.g., sso.example.com) to the network.negotiate-auth.trusted-uris preference.
Root Cause
- In enterprise environments, a RHEL virtual machine hosting Red Hat build of Keycloak (RHBK) is often enrolled in a Red Hat IdM (FreeIPA) domain for system-level management, while the end-users authenticate via a separate Microsoft Active Directory (AD) domain.
When attempting to configure Kerberos/SPNEGO browser authentication for Keycloak, administrators encounter failures because the underlying Java Virtual Machine (JVM) defaults to using the host operating system's /etc/krb5.conf file. Since the RHEL host is joined to IdM, this configuration file points to the IdM realm, causing Keycloak to fail to authenticate the AD-issued Kerberos tickets.
Furthermore, even if the keytab is generated, administrators frequently encounter GSSException decryption errors due to strict RHEL file permission restrictions preventing the Keycloak system user from reading the keytab.
Note: This configuration does not require a cross-realm forest trust between Red Hat IdM and Microsoft Active Directory. Keycloak/RHBK operates independently by holding its own AD service keytab and communicating directly with the AD Key Distribution Center (KDC).
Diagnostic Steps
- Run the kinit command on the RHEL server to verify the keytab maps correctly to the AD realm.
kinit -k -t /opt/keycloak/conf/keycloak-ad.keytab HTTP/sso.example.com@AD.EXAMPLE.COM -V
Error: kinit: Preauthentication failed while getting initial credentials
Diagnosis: There is a mismatch between the Service Principal Name (SPN), the AD realm, or a problem with the cryptographic salt. Ensure the domain name of the SSO service exactly matches the mapping created in AD.
- If kinit succeeds but Keycloak still rejects browser logins, enable Kerberos debugging in the Keycloak JVM by appending the following to JAVA_OPTS_APPEND:
-Dsun.security.krb5.debug=true -Dsun.security.spnego.debug=true
- With debugging enabled, watch the Keycloak standard output/server logs for the following exceptions:
Error: GSSException: Failure unspecified at GSS-API level (Mechanism level: Invalid argument (400) - Cannot find key of appropriate type to decrypt AP-REQ - AES256 CTS mode with HMAC SHA1-96)
Diagnosis: The Keycloak JVM cannot read the keytab file to decrypt the ticket. This is almost always caused by incorrect file ownership or restrictive SELinux contexts.
Error: Received kerberos token, but there is no user storage provider that handles kerberos credentials.
Diagnosis: This is a cascading failure. Because the keytab was unreadable (causing the GSSException above), the Kerberos integration module failed to initialize, causing Keycloak to falsely report that no provider exists.
