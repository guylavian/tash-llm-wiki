# Unable to access Keycloak Admin WebUI after enabling Client Authentication on security-admin-console 

Unable to access Keycloak Admin WebUI after enabling Client Authentication on security-admin-console
Environment
- Red Hat Build Of Keycloak (RHBK)
- 26.x
Issue
- Resolving "invalid_client_credentials" Error on security-admin-console
- Recovering Admin Access After Accidentally Enabling Client Authentication on security-admin-console
- Resolving RHBK Admin Lockout When 2FA/OTP Blocks CLI Recovery (invalid_grant) ?
- Emergency Database Recovery, Restoring Keycloak Admin Access When CLI and WebUI are Blocked ?
Resolution
- CLI access was blocked by OTP requirements, the configuration must be reverted manually via the backend
database (PostgreSQL in this scenario), followed by a service restart to flush Keycloak's in-memory cache.
Step 1: Connect to the PostgreSQL Database, Access your Keycloak PostgreSQL database using psql or your preferred database
client.
Step 2: Find the internal Client ID, retrieve the internal UUID of the security-admin-console client for the master realm:
SELECT c.id
FROM client c
JOIN realm r ON c.realm_id = r.id
WHERE c.client_id = 'security-admin-console' AND r.name = 'master';
(Copy the UUID returned by this query. It will be used as <CLIENT_ID> in the following steps).
Step 3: Revert the client to Public , update the client record to disable client authentication:
UPDATE client
SET public_client = true
WHERE id = '<CLIENT_ID>';
Step 4: Remove the PKCE constraint, delete the attribute that enforces the PKCE method for this client:
DELETE FROM client_attributes
WHERE client_id = '<CLIENT_ID>' AND name = 'pkce.code.challenge.method';
Step 5: The database changes will not take effect until the cache is cleared. Restart the RHBK service.
Note: Direct Database Update/changes are NOT Recommended, test in lower environment before applying in production.
Optional: In case of 2FA (OTP) not enabled follow RHBK the admin CLI commands. It is highly recommended trying the CLI method first, as it is safer and does not require a server restart.
Even though the security-admin-console is broken, the Admin CLI uses a completely different client (admin-cli) to authenticate. As long as haven't modified the admin-cli client, you can use the command line to fix the UI.
Run these commands from the bin directory of your Red Hat build of Keycloak installation:
- Authenticate with the server
./kcadm.sh config credentials --server <YOUR_KEYCLOAK_URL> --realm master --user <ADMIN_USERNAME>
You will be prompted to enter your admin password.
- Find the internal ID of the locked client
./kcadm.sh get clients -r master -q clientId=security-admin-console --fields id
Copy the id value output by this command it will look like a long string of letters and numbers, not the word security-admin-console.
- Revert the changes, replace
with the copied ID from the previous step:
./kcadm.sh update clients/<ID_FROM_STEP_2> -r master -s publicClient=true -s 'attributes."pkce.code.challenge.method"=""'
Once this is done, clear your browser cache or open an Incognito window, and you should be able to log in to the WebUI immediately.
Additional Notes:
- The kcadm.sh CLI uses a "Direct Access Grant" (Resource Owner Password Credentials) to authenticate. This is a direct API
call that expects just a username and password; it doesn't know how to handle interactive OTP prompts, so it defaults to
throwing an invalid_grant error.Since main admin account is locked behind OTP and cannot easily bypass it via the CLI in such cases
use direct database modification.
Root Cause
-
The security-admin-console client is the application backing the Admin UI itself. It is designed to be a public client. By
enabling Client authentication turned it into a confidential client, which means Keycloak now expects a client secret
during the code-to-token exchange. Since the browser-based Admin UI doesn't have this secret, it fails with the
invalid_client_credentials error.The security-admin-console client acts as the frontend application backing the Keycloak Admin WebUI itself. It is designed by
default to be a public client. -
By manually enabling "Client authentication" and setting the PKCE Method in the Admin WebUI, the client was converted into
a confidential client. This forced Keycloak to expect a client secret during the OIDC code-to-token exchange. Because the
browser-based Admin UI does not possess or transmit this secret, the exchange fails with invalid_client_credentials, locking
all users out of the console.
Diagnostic Steps
-
Administrators are unable to log into the Red Hat build of Keycloak (RHBK) Admin WebUI.
-
The RHBK server logs display the following warning during login attempts:
WARN [org.keycloak.events] (executor-thread-1) type="CODE_TO_TOKEN_ERROR", realmId="<realm-id>", realmName="master", clientId="security-admin-console", userId="null", ipAddress="<ip>", error="invalid_client_credentials", grant_type="authorization_code"
- Standard recovery involves using the kcadm.sh CLI tool. However, if the admin account has Two-Factor Authentication (OTP)
enabled, the CLI command (kcadm.sh config credentials --server--realm master --user ) will fail with: Invalid user
this happens because the CLI uses a Direct Access Grant that cannot process interactive OTP prompts.
