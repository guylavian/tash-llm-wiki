# Intermittent Loss of Active Directory Identity Provider Link in RHBK

Intermittent Loss of Active Directory Identity Provider Link in RHBK
Environment
- Red Hat Build Of Keycloak (RHBK)
- 26.x
Issue
- Users occasionally lose their Identity Provider (IdP) link to Active Directory and are prompted to "merge accounts" upon login in
Red Hat build of Keycloak (RHBK) . - Users Sporadically Disconnected from Active Directory IdP in RHBK
Resolution
- The solution is to reconfigure the Identity Provider mapper to use an attribute from Active Directory that is guaranteed to be
immutable for the entirely for the user account. In Active Directory, the standard for this is the objectGUID.
Note: This change will resolve the issue for the future. However, it will cause a one-time disruption for all existing users. On their next
login, Keycloak will be looking for a link based on the objectGUID and will not find one (as the old links were based on sAMAccountName).
Workaround: Re-assigning the link will fixes the immediate problem for a single user. It means the user was
presented with the "merge account" screen and they clicked the "Link" button, or an administrator manually
linked their account. This action re-creates the link based on the current, problematic configuration.
Root Cause
-
The Identity Provider link relies on a stable, unique identifier provided by the external IdP (Active Directory) during
every login. When a user logs in,Keycloak uses this identifier to look up the corresponding local user account via the
stored federated link. -
The root cause of the link loss is the use of a mutable (changeable) attribute from Active Directory as this
unique identifier.- Attributes like sAMAccountName (username) and userPrincipalName (email-style login) can be changed by AD
administrators. - When such an attribute is changed in Active Directory, Keycloak receives a new identifier for that user upon their
next login attempt. - Since new identifier does not match the one stored in the existing federated link, Keycloak cannot find the link.
It then sees a pre-existing local account with a matching email or username and prompts the user to "merge" the
accounts to re-establish the link with the new identifier.

Diagnostic Steps
Perform the following steps when user reports this issue:
-
Verify the User's State:
- In the RHBK Admin Console, navigate to Users and find the affected user.
- Click on the Identity Provider Links tab. Confirm that the link to your Active Directory provider is
missing.
-
Inspect the Identity Provider Mapper:
- Navigate to Identity Providers and select your configured Active Directory provider.
- Click on the Mappers tab.
- Locate the mapper of type Username Template Importer. This mapper defines which AD attribute is used to uniquely identify users for the federated link.
Click Edit and examine the Template field.
-
Identify the Problematic Configuration:
- The issue is confirmed if the Template field is configured to use a mutable attribute. Common examples include:
${ATTRIBUTE.sAMAccountName}
${ATTRIBUTE.userPrincipalName}
${ATTRIBUTE.cn}
- Correlate with Active Directory:
- Contact your Active Directory administrator and ask them to check the user's account history.
- Confirm if the attribute used in the mapper (e.g., sAMAccountName) was recently changed for that user (e.g., due to a name change, domain change, or typo correction).
This provides definitive evidence linking the AD change to the Keycloak behavior.
