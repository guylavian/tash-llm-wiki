# RFC 9207 — OAuth 2.0 Authorization Server Issuer Identification

Load-bearing normative requirements distilled for the wiki. Tight paraphrase only — see the RFC for verbatim text.

## issuer-identification-mixup

### AS MUST return `iss` in the authorization response (§2, §2.2)
- **RULE:** An AS supporting this spec MUST add the `iss` parameter to the authorization response — in BOTH success and error responses — carrying its issuer identifier so the client can tell which AS answered.
- **ANTI-PATTERN:** Omitting `iss` entirely, or adding it only to successful responses while error responses go out unmarked.
- **SYMPTOM:** Client cannot bind the response to a specific AS; mix-up defense silent-fails; spec-compliant clients reject the unmarked response.

### `iss` value format — https URL, no query/fragment (§2)
- **RULE:** The `iss` value is the AS issuer identifier: an `https` URL with no query or fragment components, sent `application/x-www-form-urlencoded` in the query (code/`none`) or fragment (implicit/`id_token`) per the response mode.
- **ANTI-PATTERN:** Emitting an `http` URL, or appending a query string / `#fragment` to the issuer; building the value so it drifts from the metadata `issuer`.
- **SYMPTOM:** Client's exact-match comparison rejects a legitimate response over a format mismatch; "issuer mismatch" despite the right server.

### Client MUST validate `iss` against the intended AS (§2.4)
- **RULE:** On EVERY authorization response (success and error), the client MUST extract `iss`, URL-decode it, and compare it — by simple string comparison (RFC 3986 §6.2.1) — to the issuer of the AS the request was actually SENT to. Mismatch → MUST reject and MUST NOT continue the grant (no code exchange).
- **ANTI-PATTERN:** Normalizing/canonicalizing the URL (lowercasing, trailing-slash stripping); matching against a SET of configured ASes instead of the one intended for this request; logging a warning but proceeding anyway.
- **SYMPTOM:** Mix-up succeeds — code/token meant for the honest AS is redeemed at the attacker's AS; credential leakage; "confused deputy" routing of the grant to the wrong server.

### Treat error responses with the same suspicion (§2.4)
- **RULE:** For error responses too, the client MUST NOT assume the error came from the intended AS — validate `iss` before acting on the error.
- **ANTI-PATTERN:** Trusting an unauthenticated error blindly and retrying / redirecting the user based on attacker-supplied error content.
- **SYMPTOM:** Attacker injects a fake error to steer the flow or mislead the client about the failure cause.

### Reject missing `iss` from a supporting AS; discard `iss` from a non-supporting AS (§2.3, §2.4)
- **RULE:** If the client's config says the AS supports `iss` (e.g. metadata `authorization_response_iss_parameter_supported: true`), a response WITHOUT `iss` MUST be rejected. Conversely, an `iss` arriving from an AS not known to support it SHOULD be discarded.
- **ANTI-PATTERN:** Accepting a response whose `iss` was stripped by an attacker; or trusting an `iss` from a server that never advertised support.
- **SYMPTOM:** Stripping bypass — attacker removes `iss` and the client proceeds; or false rejects/false accepts of legacy servers.

### Metadata consistency and support flag (§2.3)
- **RULE:** The AS metadata `issuer` MUST be identical to the `iss` it sends, and the AS MUST advertise `authorization_response_iss_parameter_supported: true` to signal support.
- **ANTI-PATTERN:** Publishing one `issuer` in metadata but emitting a different `iss`; sending `iss` while the support flag is absent/`false`.
- **SYMPTOM:** Client rejects all responses (metadata vs `iss` disagree); or compliant client treats the AS as non-supporting and discards the `iss`.

### Issuer identifiers MUST be unique per AS (§4)
- **RULE:** Clients MUST NOT let two different ASes share the same issuer identifier; with manually-configured ASes the client MUST enforce uniqueness of accepted `iss` values.
- **ANTI-PATTERN:** Configuring two ASes with the same `issuer` (copy-paste/template typo), defeating disambiguation.
- **SYMPTOM:** Client cannot tell the two ASes apart; routes the grant to the wrong one — mix-up reopens.

### `iss` parameter is NOT cryptographically protected (§4)
- **RULE:** The `iss` parameter has no signature/HMAC — it is sufficient against mix-up because the relevant attack uses a response from the HONEST AS that the client must merely route correctly; tampering buys the attacker nothing here.
- **ANTI-PATTERN:** Treating the bare `iss` parameter as an integrity guarantee against a response-injecting/tampering attacker.
- **SYMPTOM:** Over-trust of an unsigned value in threat models beyond mix-up (where a signed mechanism is needed).

### Equivalent signed countermeasures and multi-issuer matching (§4)
- **RULE:** A signed `iss` claim in an ID Token (`code id_token`) or a JARM JWT response is an acceptable alternative defense. When a response carries MORE THAN ONE issuer identifier (e.g. `iss` parameter AND ID Token `iss`), they MUST be identical or the client MUST reject.
- **ANTI-PATTERN:** `iss` parameter says `honest.as.example` while the ID Token `iss` claim says a different AS; or accepting one and ignoring the other.
- **SYMPTOM:** Inconsistent validation — response/token issuer disagree; an attacker-spliced token slips through if the client checks only one.

### Single-AS clients: not vulnerable today, but future-proof (§4)
- **RULE:** Clients that talk to only one AS are not currently exposed to mix-up, but adding a second AS introduces the risk — implement `iss` validation proactively.
- **ANTI-PATTERN:** Skipping `iss` handling because "we only have one AS," then onboarding a second IdP without revisiting it.
- **SYMPTOM:** Latent mix-up exposure surfaces the moment a second AS/IdP is brokered in.
