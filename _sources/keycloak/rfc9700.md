# RFC 9700 — OAuth 2.0 Security BCP (raw staging note)

Distilled load-bearing requirements, grouped by the wiki concept they feed. Each bullet: RULE (+ section) / ANTI-PATTERN / SYMPTOM. Paraphrased tightly.

## pkce
- RULE (§2.1.1): public clients MUST use PKCE; ASes MUST support PKCE; confidential clients RECOMMENDED. ANTI-PATTERN: plain code flow with no `code_challenge`. SYMPTOM: stolen/leaked auth code redeemed by attacker; "code injection" account takeover.
- RULE (§2.1.1): clients SHOULD use a challenge method that doesn't expose the verifier — `S256` is the only such method (avoid `plain`). ANTI-PATTERN: `code_challenge_method=plain`. SYMPTOM: verifier visible in request logs/referrer, PKCE protection nullified.
- RULE (§2.1.1): if a valid `code_challenge` was sent, AS MUST enforce `code_verifier` at the token endpoint. ANTI-PATTERN: AS ignores verifier mismatch. SYMPTOM: token issued without verifier check; injection succeeds.
- RULE (§2.1.1 PKCE-downgrade): AS MUST accept a token request with `code_verifier` only if a `code_challenge` was present in the authz request. ANTI-PATTERN: accepting verifier when challenge was absent. SYMPTOM: attacker strips challenge to downgrade, then injects.
- RULE (§2.1.1): AS MUST advertise PKCE support; RECOMMENDED to publish `code_challenge_methods_supported`. ANTI-PATTERN: no discovery metadata; client guesses. SYMPTOM: client can't confirm PKCE support, falls back to weaker CSRF defense.
- RULE (§4.5.3.1): PKCE blocks authorization-code injection — verifier check fails for injected codes. SYMPTOM (correct impl): `invalid_grant` / PKCE verification failed on injected code.

## redirect-uri-validation
- RULE (§2.1, §4.1.3): AS MUST compare redirect URIs to pre-registered ones with EXACT string matching (RFC 3986 simple string comparison). ANTI-PATTERN: prefix/substring/wildcard/regex matching. SYMPTOM: code/token redirected to attacker domain; `redirect_uri_mismatch` when later tightened.
- RULE (§4.1.3): only exception — native apps with `localhost`/loopback URIs MUST allow variable port numbers. ANTI-PATTERN: pinning a fixed loopback port. SYMPTOM: native app login fails when OS assigns a different ephemeral port.
- RULE (§2.1): clients and ASes MUST NOT expose open redirectors (forwarding browser to arbitrary URI from a query param). ANTI-PATTERN: generic `?redirect=`/`?next=` follower endpoints. SYMPTOM: token/code exfiltration chained through the open redirect.

## state-and-nonce
- RULE (§2.1, §4.7.1): clients MUST prevent CSRF. If AS supports PKCE, client MAY rely on PKCE's CSRF protection; otherwise one-time `state` CSRF tokens bound to the user agent MUST be used. ANTI-PATTERN: no state and no confirmed PKCE. SYMPTOM: login CSRF / session fixation — victim signed into attacker's session.
- RULE (§4.7.1): client MUST confirm AS supports PKCE before relying on PKCE for CSRF; if not supported, `state` or `nonce` MUST be used. ANTI-PATTERN: assuming PKCE-as-CSRF against a non-PKCE AS. SYMPTOM: silent CSRF gap, no error.
- RULE (§2.1): in OIDC flows the `nonce` parameter provides CSRF protection. ANTI-PATTERN: dropping/not validating `nonce`. SYMPTOM: ID-token replay / cross-session injection.
- RULE (§4.7.1): if `state` carries app state whose integrity matters, clients MUST protect `state` against tampering and swapping. ANTI-PATTERN: trusting un-signed state contents. SYMPTOM: state-swap → wrong-account/return-path manipulation.

## refresh-token-rotation
- RULE (§2.2.2, §4.14): refresh tokens for PUBLIC clients MUST be sender-constrained OR use refresh-token rotation. ANTI-PATTERN: long-lived static refresh token in an SPA/native app. SYMPTOM: stolen refresh token reused indefinitely; no breach detection.
- RULE (§2.2.2, from RFC 6749): refresh tokens for CONFIDENTIAL clients MUST only be usable by the client they were issued to (bound via client auth). ANTI-PATTERN: accepting a refresh token without client authentication. SYMPTOM: cross-client refresh-token replay.
- RULE (§4.14 rotation semantics): on rotation, reuse of an already-redeemed refresh token signals theft → revoke the chain. SYMPTOM (correct impl): `invalid_grant` on replayed old refresh token; whole grant family revoked.

## audience-and-scope-checks
- RULE (§2.3): access-token privileges SHOULD be the minimum required (least privilege). ANTI-PATTERN: one broad token for all resource servers. SYMPTOM: token leak from one RS grants access everywhere.
- RULE (§2.3): access tokens SHOULD be audience-restricted to one RS (or a small set); `aud` per RFC 9068 MAY carry it; `resource` (RFC 8707) / `scope` MAY select the RS. ANTI-PATTERN: no `aud`, token accepted by any RS. SYMPTOM: token replay across services; RS confused-deputy.
- RULE (§4.10.2): the RS MUST verify the intended audience and refuse the request if audience validation fails. ANTI-PATTERN: RS skips `aud` check. SYMPTOM: cross-audience token accepted; 200 where 401 expected (audit finding).
- RULE (§2.3): access tokens SHOULD be restricted to specific resources/actions; `scope` and `authorization_details` (RFC 9396) MAY scope them. ANTI-PATTERN: wildcard scopes. SYMPTOM: over-privileged token, scope-creep audit ticket.

## dpop-sender-constraining
- RULE (§2.2.1, §4.10.1): AS and RS SHOULD sender-constrain access tokens via mTLS (RFC 8705) or DPoP (RFC 9449). ANTI-PATTERN: plain bearer tokens with no proof-of-possession. SYMPTOM: stolen token replayed from any host.
- RULE (§4.10.1): DPoP works with public clients and can combine with any confidential-client auth method. ANTI-PATTERN: assuming PoP needs mTLS/confidential client only. SYMPTOM: SPAs/native apps left on plain bearer.
- RULE (§4.10.1 limitation): sender-constraining fails if attacker captures BOTH token AND key material. ANTI-PATTERN: storing the DPoP/mTLS private key alongside the token. SYMPTOM: PoP defeated; replay still possible.

## issuer-identification-mixup
- RULE (§2.1): when a client talks to more than one AS, a mix-up defense is REQUIRED. ANTI-PATTERN: multi-IdP client with no issuer check. SYMPTOM: code sent to honest AS but redeemed at attacker AS (mix-up); account compromise.
- RULE (§2.1, §4.4.2.1): clients SHOULD use the `iss` parameter per RFC 9207 (or an equivalent `iss` value); on receiving the response the client MUST compare received issuer to the stored/expected issuer and MUST abort on mismatch. ANTI-PATTERN: ignoring/not validating `iss`. SYMPTOM: silent acceptance of response from wrong AS.
- RULE (§4.4.2.2 alternative): if not using RFC 9207, clients MUST use a distinct redirect URI per issuer; this SHOULD be used only when other options are unavailable. ANTI-PATTERN: shared redirect URI across multiple issuers without `iss`. SYMPTOM: cannot disambiguate responding AS → mix-up.

## bearer-token-usage
- RULE (§4.3.2): clients MUST NOT pass access tokens in a URI query parameter (RFC 6750 §2.3 style). ANTI-PATTERN: `?access_token=...` in URLs. SYMPTOM: token leaks via logs, browser history, Referer header.
- RULE (§2.6): authorization responses MUST NOT travel over unencrypted connections; AS MUST NOT allow `http`-scheme redirect URIs except native loopback clients. ANTI-PATTERN: `http://` redirect URI in registration. SYMPTOM: code/token interception on the wire; registration rejected when enforced.
- RULE (§2.6): end-to-end TLS (BCP 195) between client and RS is RECOMMENDED. ANTI-PATTERN: TLS terminated early / cleartext internal hop. SYMPTOM: bearer token sniffed inside the perimeter.
- RULE (§4.2.4): suppress the Referer header (Referrer-Policy) so codes/tokens in URLs don't leak. ANTI-PATTERN: default referrer leaking the authz response URL. SYMPTOM: code/state leaked to third-party resources.

## service-to-service-client-credentials
- RULE (§2.5): ASes SHOULD enforce client authentication where issuing/protecting client credentials is feasible. ANTI-PATTERN: unauthenticated "confidential" clients. SYMPTOM: client impersonation; token issued to anyone with the client_id.
- RULE (§2.5): RECOMMENDED to use asymmetric client auth — mTLS (RFC 8705) or signed-JWT "private_key_jwt" (RFC 7521/7523) — over shared secrets. ANTI-PATTERN: static `client_secret` in many services/CI. SYMPTOM: leaked shared secret → fleet-wide compromise; secret-rotation churn.
- NOTE: RFC 9700 does not give a dedicated client_credentials (machine-to-machine) grant section; its guidance here is the client-authentication hardening above. Treat the grant-specific detail as out of scope for this source (defer to RFC 6749 §4.4 and RFC 9068 for AT format).

## jwt-validation-pitfalls
- RULE (§4.6.1, OIDC): a forged/leaked ID Token can't be substituted because it's signed (or encrypted) and the `nonce` claim binds it to the session — implies signature AND nonce MUST be validated. ANTI-PATTERN: trusting ID Token without signature/nonce check. SYMPTOM: ID-token injection / replay; wrong-subject login.
- RULE (audience, via §2.3/§4.10.2 + RFC 9068): JWT access tokens MUST be validated for intended audience (`aud`). ANTI-PATTERN: decode-without-verify; ignoring `aud`. SYMPTOM: cross-service token accepted.
- NOTE / GAP: RFC 9700 does NOT deeply cover classic JWT pitfalls (alg-confusion RS256→HS256, `alg:none`, `kid` injection, missing signature verification). Those are out of scope here — defer to JWT BCP RFC 8725 and RFC 7518/9068 for the canonical rules. Captured as a wanted upstream source.

## grant-type recommendations (cross-cutting)
- RULE (§2.1.1): authorization code grant is the recommended interactive flow (with PKCE). 
- RULE (§2.1.2): clients SHOULD NOT use the implicit grant (`response_type=token`) or any response type issuing access tokens in the authz response, unless injection/leakage are fully mitigated; SHOULD use `response_type=code` instead. ANTI-PATTERN: implicit flow SPA. SYMPTOM: access-token leakage/replay via URL fragment, browser history.
- RULE (§2.4): Resource Owner Password Credentials (ROPC) grant MUST NOT be used — exposes user credentials to the client, blocks MFA/modern credential binding, enlarges attack surface. ANTI-PATTERN: app collects username/password and posts to token endpoint. SYMPTOM: credential exposure; no MFA; security-review block.
