# OpenShift Networking

**Every workload's path to the network runs through the same four layers: a [[kubernetes-service]] gives it a stable identity, a [[kubernetes-ingress]] or [[openshift-route]] exposes that Service externally, [[ovn-kubernetes]] is the plumbing that actually moves the packets, and [[cluster-dns]] plus [[network-policy]] control who can resolve and reach it.**

## Layer 1 — Service: hiding pod churn
Pods are ephemeral and their IPs change on every reschedule. A [[kubernetes-service]] gives callers a stable ClusterIP + DNS name and load-balances only to pods currently passing readiness. This is the substrate everything above sits on — a Route or Ingress always points **at a Service**, never directly at pods.

## Layer 2 — external exposure: Route vs Ingress
- **[[openshift-route]]** is OpenShift's native, older object for exposing a Service over HTTP(S), served by the built-in HAProxy Ingress router, with three TLS modes — see [[route-tls-termination]] (edge / passthrough / re-encrypt).
- **[[kubernetes-ingress]]** is the upstream Kubernetes equivalent. On OCP, creating an Ingress auto-generates a managed Route, so the two coexist rather than compete (inferred).
- Upstream Kubernetes itself now recommends the newer Gateway API over Ingress (the Ingress API is frozen) — an upstream-only trend the OCP Route model isn't affected by, since Route predates and sits alongside Ingress rather than depending on it (inferred).

## Layer 3 — OVN-Kubernetes: the plumbing
**[[ovn-kubernetes]]** is the default OCP CNI/network plugin: an OVN-over-OVS overlay network programmed via OpenFlow, using Geneve encapsulation between nodes. It is what actually implements Service virtual IPs, pod-to-pod routing, egress IPs, and — critically — [[network-policy]] enforcement and logging. Replaced the older OpenShift SDN plugin as OCP's default.

## Layer 4a — cluster DNS
**[[cluster-dns]]**, via CoreDNS deployed by the OpenShift DNS Operator, resolves `*.cluster.local` Service/Pod names for every pod. A pod's injected `resolv.conf` search-domain list and `ndots:5` default determine when a bare name is tried against internal search domains first before an absolute lookup — the mechanism behind a lot of "works with FQDN, fails with short name" reports.

## Layer 4b — NetworkPolicy: the allow-list firewall
**[[network-policy]]** is opt-in, application-centric micro-segmentation: by default all pods in a project are reachable from any other pod; a NetworkPolicy only restricts traffic for the pods it selects, additively across multiple policies. As of OCP 4.22, OpenShift itself ships default NetworkPolicy objects in some control-plane namespaces — do not modify OpenShift's own policies.

## Kubernetes-upstream vs OpenShift-specific
| Concept | Upstream Kubernetes | OpenShift-specific |
|---|---|---|
| External HTTP(S) exposure | Ingress (frozen API; requires 3rd-party/cloud controller) | Route (native, HAProxy router, TLS termination modes) |
| CNI/overlay | Any CNI plugin (pluggable) | OVN-Kubernetes is the shipped default |
| DNS | CoreDNS (generic Service/Pod DNS spec) | DNS Operator manages CoreDNS as a cluster-scoped CR |
| NetworkPolicy | Requires a supporting plugin, no defaults | OCP ships default policies protecting some control-plane namespaces (4.22+) |

## Contradictions / caveats
- Upstream Kubernetes docs describe Ingress as still generally available but frozen with no further development, while OpenShift's own Route object continues to receive new capabilities (e.g. externally managed certificates, HSTS) — so on OCP, Route is the actively evolving mechanism even though Ingress objects are also fully supported and auto-translated.
