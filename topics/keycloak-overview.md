# Keycloak / RHBK overview

**Keycloak — productized by Red Hat as Red Hat build of Keycloak (RHBK) — is a
single sign-on solution for web apps and RESTful web services: a separate server
that applications point to, which authenticates users over OpenID Connect or
SAML 2.0 and hands applications signed tokens instead of credentials.**

## What it is

The product's stated goal is to make security simple: security features developers
normally write themselves come out of the box, tailorable per organization, with
customizable UIs for login, registration, administration, and account management.
It also serves as an integration platform for existing LDAP/Active Directory
servers and can delegate authentication to third-party IdPs like Facebook and
Google.

Headline features: SSO/single sign-out, OpenID Connect + OAuth 2.0 + SAML support,
identity brokering, social login, LDAP/AD user federation, a Kerberos bridge, the
Admin and Account consoles, themes, two-factor auth (TOTP/HOTP), configurable login
flows, session management, token mappers, and per-realm/app/user not-before
revocation policies.

## How it operates

Browser applications redirect the user's browser to the Keycloak server to enter
credentials — users are completely isolated from applications, and applications
never see credentials. Applications instead receive a cryptographically signed
identity token or assertion carrying profile data and permission data, usable to
call REST services securely.

## Core concepts

- A **realm** manages a set of users, credentials, roles, and groups; a user
  belongs to and logs into a realm, and realms are isolated from one another —
  see [[realm-administration]].
- A **client** is an entity that can request Keycloak to authenticate a user —
  typically an application or service being secured — see
  [[securing-apps-oidc-saml]]. Each client has a built-in **service account**.
- **Users, roles, groups**: roles categorize users, composite roles nest roles,
  groups bundle attributes and role mappings — see [[roles-and-groups]] and
  [[managing-users-credentials]].
- Logins create **sessions**, and clients receive **tokens** shaped by protocol
  mappers — see [[tokens-and-sessions]].
