# OpenShift — Builds and Images

**Builds, Source-to-Image, and ImageStreams are OpenShift platform additions — none of them exist in vanilla Kubernetes, which expects you to build images outside the cluster and reference a fixed registry path.** OCP instead runs the build in-cluster and gives you a stable local reference (an ImageStreamTag) to point Deployments/DeploymentConfigs at.

## The chain: BuildConfig → ImageStream → rollout
1. A [[buildconfig-s2i|BuildConfig]] describes a build: a **strategy** (how to produce the image) and one or more **sources** (Git repo, inline Dockerfile, or a binary payload).
2. The build's `output` pushes the resulting image to an **ImageStreamTag** in an [[image-streams|ImageStream]] — not to a raw registry path.
3. A `DeploymentConfig` (or a build) with an **ImageChange trigger** watching that same ImageStreamTag reacts automatically: a new image in the stream starts a new rollout, without anyone re-editing a manifest to bump a tag. This is the OpenShift-native version of a CI/CD "build then deploy" pipeline, done with cluster-native objects instead of external tooling.

If the consuming object's ImageStreamTag reference isn't updated, the rollout keeps using the last known-good image even after the underlying registry image changes — the decoupling is deliberate, not a bug.

## Build strategies
A `BuildConfig`'s `strategy` section picks one of three:
- **Source (S2I)** — the default and OpenShift's own approach: injects application source directly into a builder image via the image's `assemble`/`run` scripts, with no Dockerfile required from the developer. See [[buildconfig-s2i]] for the mechanics and how to customize a builder image's scripts.
- **Docker** — builds straight from a Dockerfile (executed via Buildah on OCP 4).
- **Custom** — the builder image itself owns the whole build process; runs with elevated privilege and is restricted to trusted cluster admins by default, not exposed to regular developers.

## Triggers
A `BuildConfig` can define **triggers** — `GitHub`/generic webhook, or `ImageChange` — so a source-code push or an upstream image update starts a new build automatically; without any trigger, a build only starts on a `BuildConfig` change or a manual `oc start-build`.

## Where images live
Source images for a build, and the images an ImageStream tracks, can come from OpenShift's own **internal (integrated) registry**, an external registry (`registry.redhat.io`, `quay.io`), or another ImageStream in the same cluster — the ImageStream is a virtual view over these, holding no image bytes itself; only its metadata (tag history, SHA pointers) lives in etcd.

## Contradictions / caveats
- OpenShift's `latest` ImageStreamTag is a **tracking tag** that follows a specific release line, not "the newest pushed image" the way Docker's `latest` tag conventionally means — don't carry the Docker assumption over.
