# LDAP / Active Directory User Federation

**Connecting RHBK to an external LDAP or Active Directory directory so its users
become RHBK users, via the User Storage SPI's built-in LDAP provider.**

## Body
RHBK ships a built-in LDAP federation provider (configured under **User
Federation → Add LDAP providers** in the admin console). It supports both plain
LDAP and Active Directory vendor presets. Two orthogonal axes govern behavior:

- **Storage / import mode** — whether LDAP users are copied into RHBK's database
  or read on demand. See [[ldap-storage-mode]].
- **Edit mode** — `READ_ONLY`, `WRITABLE`, or `UNSYNCED`, controlling whether
  profile changes flow back to LDAP. See [[ldap-storage-mode]].

Kerberos can ride on top: with the `LDAPFederationProvider` + Kerberos support,
RHBK provisions user data from LDAP; with a standalone `KerberosFederationProvider`
the user can self-update the profile. For LDAPS, the provider needs the directory's
CA in a truststore — in operator/OpenShift deployments this is the system
truststore, configured separately from the provider page.

Group/role mapping and attribute mapping are handled by **LDAP mappers** attached
to the provider (each is a candidate [[ldap-mappers]] entity page).

## Contradictions / caveats
- The **Import Users** toggle and storage-mode wording is stable across RHBK
  26.0 → 26.6, but always confirm the version against `reference/keycloak/` (the
  notes carry `version:`; QUERY op in [`CLAUDE.md`](../CLAUDE.md)).
- Truststore wiring differs between bare-metal (`kc.sh`) and the
  [[rhbk-operator]] — don't assume the console-page CA upload applies on OpenShift.
- Performance: importing+syncing large directories has real cost; read-only
  no-import avoids the local copy but loses some query/listing capability
  (inferred — operational trade-off synthesized across the storage-mode options).
