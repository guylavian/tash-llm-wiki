# DNS for AD DS

**AD DS uses DNS as its locator service: clients find domain controllers, and DCs
find each other, by resolving SRV records under the `_msdcs` zone — so broken DNS
looks exactly like broken AD.**

## Body

AD DS depends on **DNS name resolution** to make domain controllers locatable. The
**DC Locator** turns a client's site membership into a specific DC by querying SRV
records (e.g. under `_msdcs.<forest-root>`); this is the mechanism that ties DNS
health to [[ad-replication]] and to logon working at all.

**AD-integrated DNS zones** are the recommended deployment: the zone data is stored
in the directory and replicated **with** AD replication, which eliminates the
need for secondary zones and zone transfers, gives multi-master DNS updates, and lets
you secure dynamic updates. This is why a healthy AD usually means DNS rides along on
the same DCs.

Key planning pieces:
- **Domain Controller Location** — the SRV-record lookup flow the DC Locator follows;
  clients prefer in-site DCs and fall back to the next-closest site.
- **Active Directory-Integrated DNS Zones** — directory-stored, AD-replicated zones.
- **Computer Naming** and **Disjoint Namespace** — naming constraints; a *disjoint
  namespace* (the AD domain name differs from the machines' primary DNS suffix)
  works but makes AD↔DNS integration noticeably more complex and is a frequent
  source of subtle locator failures (inferred — flagged as the complexity caveat in
  the source).

## Contradictions / caveats

- **Event ID 2088** ("DNS lookup failure ... replication succeeded") signals DNS is
  misconfigured even though replication found a fallback path — treat it as a warning
  to fix DNS before it becomes a hard outage.
- Time, DNS, and FSMO are the three recurring AD root-cause dependencies
  (see [[active-directory-implementation-review]]); DNS is the one that most often
  presents as "AD is down" when the directory itself is fine (inferred).
