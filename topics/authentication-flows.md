# Authentication flows, MFA, and step-up

**An authentication flow is an ordered container of executions and sub-flows (screens, authenticators, actions) that runs during login, registration, reset-credentials and brokering; requirement types on each element decide whether and how it runs.**

## Built-in flows and requirement types
RHBK ships built-in flows (e.g. **Browser**, **Reset Credentials**, **Registration**,
**First Broker Login**) that you cannot modify directly but whose **requirements** you
can change, or which you can **Duplicate** and edit. Each execution/sub-flow has one of
four requirement types:
- **Required** — must succeed; flow terminates on failure. All Required elements run
  sequentially.
- **Alternative** — only one Alternative element needs to succeed; ignored if a sibling
  Required element exists.
- **Disabled** — does not count toward success.
- **Conditional** (sub-flows only) — acts as Required if all its condition executions
  evaluate true, else Disabled. A sub-flow with executions but *not* set Conditional is
  treated as functionally Disabled.

The default **Browser** flow: `Cookie` (Alternative) → `Kerberos` (disabled by default)
→ `Identity Provider Redirector` (Alternative, handles `kc_idp_hint`) → `Forms`
sub-flow (Username Password Form Required, then `Browser - Conditional OTP` sub-flow
gated by `Condition - User Configured`). See [[identity-brokering]] for the redirector.

## Building flows
Create a **top-level** flow (type `basic` for everything except client authentication,
which uses `client`), then add **steps** (executions) and **sub-flows** (type `basic`
or `form`). Executions are **automatic** (like Cookie) or **interactive** (halt for
input). A flow completes when at least one execution returns `success`. Order matters —
drag to reorder. Bind a finished flow to a binding (Browser, Reset credentials, etc.)
via **Action → Bind flow**.

> **Security gotcha:** if a 2nd-factor authenticator (OTP Form, WebAuthn) is set
> **Required** and the user lacks that credential, they are allowed to *set it up
> during* authentication — meaning they never actually authenticated with it. Always
> put a real 1st-factor (Password or WebAuthn Passwordless) before it.

Executions can carry an **authenticator reference value** consumed by the AMR protocol
mapper to populate the `amr` claim (RFC-8176) in OIDC tokens.

## MFA / passwordless
- **OTP** — TOTP or HOTP, configured by [[otp-policies]]. The Conditional OTP sub-flow
  only triggers when the user has an OTP credential.
- **WebAuthn / Passkeys** — a password-less browser flow combines `WebAuthn Passwordless
  Authenticator` (Alternative) with a `Password with OTP` sub-flow (Password Form
  Required + OTP Form Required) as alternatives, letting a user pick passkey *or*
  password+OTP. WebAuthn registration is driven by the `Webauthn Register Passwordless`
  required action, not auto-prompted when the authenticator is Alternative.

## Step-up authentication
[[step-up-authentication]] uses Conditional sub-flows keyed on **Level of Authentication
(LoA)** values (mapped from ACR in [[realm-administration]]) so a client/resource can
demand a higher assurance level, prompting an extra factor only when needed.

## Contradictions / caveats
- Bodies sourced are RHBK **26.0**; the Configuring authentication chapter is present in
  26.2/26.4 primary results with consistent flow semantics.
- The `client` top-level flow type is only for authenticating clients (applications),
  not users.
