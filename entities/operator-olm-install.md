# Installing the RHBK Operator via OLM

**Installing the `rhbk-operator` through OpenShift's Operator Lifecycle Manager —
from OperatorHub or a `Subscription`, with manual upgrade approval and air-gapped
catalog mirroring for disconnected clusters.**

## Install

- In the OpenShift web console: Home → Operators → OperatorHub, search "Keycloak",
  pick the Operator (named **`rhbk-operator`** in the default catalog), follow the
  on-screen steps. Choose the **channel that matches your target RHBK version**.

## Manual approval (recommended, documented from 26.6)

By default OLM **automatically** upgrades the Operator, which can cause:
unintended RHBK upgrades (the default image tracks the Operator version),
CR-compatibility breaks, behavioral changes, and **no downgrade path** once DB
migration has run. Red Hat strongly recommends `Manual` approval so you can review
release notes, schedule maintenance, test in non-prod, and back up the DB first.

CLI form — set `installPlanApproval: Manual` on the `Subscription`:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: rhbk-operator
  namespace: <target-namespace>
spec:
  channel: <desired-channel>
  name: rhbk-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Manual
```

Every subsequent upgrade then requires explicit approval via OLM UI/CLI.

## Multiple Operators / namespaces

Watching multiple/all namespaces is **not fully supported** — install one Operator
per namespace. CRDs are cluster-wide and **shared**: the last-installed Operator's
CRDs win and override existing ones. Newer CRDs are generally backward compatible,
but older Operators fail on CRs using newer fields (deserialization error). Keep
Operator versions aligned across namespaces.

## Disconnected / air-gapped

For disconnected clusters, mirror the operator catalog and images into a local
registry and wire them via `ImageContentSourcePolicy` / catalog mirroring, then
install from the mirrored `redhat-operators` source as above (see
`ref:rhbk-operator.md`). Pair with a **pre-optimized custom image**
([[custom-keycloak-image]]) so the server does not re-augment at start.

## Contradictions / caveats

- The explicit manual-approval procedure (`installPlanApproval: Manual`) is from
  the **26.6** Operator Guide; earlier streams document only the OperatorHub flow
  and default to automatic OLM upgrades.
- `Explicit` rolling-update strategy interacts badly with automatic OLM upgrades —
  another reason to prefer Manual approval (see [[operator-rolling-updates]]).
