# CSI Driver (CSIDriver)

**The Container Storage Interface (CSI) is the standard plugin model storage vendors implement so Kubernetes/OpenShift can attach, mount, and provision their volumes without in-tree code; the `CSIDriver` object tells the cluster how a given driver behaves.** It is the modern replacement for the deprecated in-tree ("`kubernetes.io/...`") volume plugins that older [[storage-class]] provisioners used.

## Key CSIDriver fields
- **`attachRequired`** — whether the driver implements `ControllerPublishVolume`; if `true`, the attach/detach controller waits for a VolumeAttachment before mounting. If `false`, the attach step is skipped entirely. Immutable once set.
- **`podInfoOnMount`** — if `true`, kubelet passes pod name/namespace/UID (and an `ephemeral` flag) to the driver's `NodePublishVolume` call as VolumeContext; drivers that don't need this leave it `false` (the default).
- **`fsGroupPolicy`** — controls whether the driver lets Kubernetes change volume ownership/permissions before mount; default `ReadWriteOnceWithFSType` only applies fsGroup when an fstype is set and the access mode is RWO.
- **`storageCapacity`** — if `true`, the driver publishes `CSIStorageCapacity` objects and volume binding with `WaitForFirstConsumer` (see [[storage-class]]) will pause until capacity is published for the target topology.

## Dynamic provisioning role
A StorageClass's `provisioner` field names a CSI driver (or an in-tree/external one); when a [[persistent-volume-claim]] requests that class and no matching PV exists, the CSI driver is what the cluster calls to actually create the backing volume and the PV object representing it — eliminating the need for an admin to manually pre-provision storage with the backend (inferred synthesis linking the CSIDriver object to the dynamic-provisioning workflow).
