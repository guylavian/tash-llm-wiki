# Policy enforcer (PEP)

**A policy enforcer is the Policy Enforcement Point at the resource server: it talks to RHBK Authorization Services, obtains authorization data, and gates access to protected resources based on the [[requesting-party-token|RPT]] decisions. RHBK ships Java and JavaScript enforcers.**

## Built-in enforcers
- **Java Policy enforcer** — for Java client applications.
- **JavaScript Policy enforcer** — for apps secured by the RHBK JavaScript adapter.

PEP is a design pattern; you can implement your own in any language against the RESTful API and the [[requesting-party-token|UMA-ticket grant]].

## JavaScript integration (`keycloak-js/authz`)
Install `keycloak-js` (NPM), then build a `KeycloakAuthorization` over a `Keycloak` instance:

```js
import Keycloak from "keycloak-js";
import KeycloakAuthorization from "keycloak-js/authz";
const keycloak = new Keycloak({ url, realm, clientId });
const authorization = new KeycloakAuthorization(keycloak);
await keycloak.init();
```

Two ways to get an RPT, each async with `onGrant`/`onDeny`/`onError` callbacks:
- **`authorize(authorizationRequest)`** — UMA flow. On a `401` + `WWW-Authenticate` from a UMA-protected resource server, extract the [[permission-ticket|ticket]] and pass `{ ticket }`; on `onGrant` retry the original request with the RPT as bearer.
- **`entitlement(resourceServerClientId[, request])`** — obtain an RPT for all resources/scopes the user can access, or for specific `permissions: [{ id, scopes }]`.

The authorization request supports `permissions`, and `metadata` with `response_include_resource_name`, `response_permissions_limit`, and `submit_request` — mirroring the [[requesting-party-token|token-endpoint parameters]]. The current token is available as `authorization.rpt`.

## Where it fits
The enforcer is the PEP in the PAP/PDP/PEP/PIP model of [[fine-grained-authorization]]: RHBK is the centralized PDP; the enforcer asks it for decisions and enforces them locally (inferred — a cross-page synthesis placing the enforcer in that model, not a single-source statement). The resource server's [[policy-enforcement-mode]] still governs what happens when no policy is associated.

## Contradictions / caveats
- Stable across RHBK **26.0–26.6**.
- The guide documents only the **Java** and **JavaScript** enforcers here; other platforms require a custom PEP against the REST API.
- Legacy **RH-SSO 7.x** used different (WildFly-era) adapters; migrating PEPs is part of [[rhsso-to-rhbk-migration]] (inferred — not covered by this chapter's cited sources).
