# MachineConfig & the Machine Config Operator (MCO)

**The MCO is OpenShift's day-2 node-management layer (no upstream Kubernetes equivalent): `MachineConfig` objects declare the desired OS-level state for a `MachineConfigPool` (e.g. `worker`, `master`), and the on-node Machine Config Daemon (MCD) applies and continuously verifies it.**

## Objects
- **MachineConfig** — Ignition-style declaration of files, systemd units, kernel args, etc. for a pool. Multiple MachineConfigs targeting the same pool are merged into one `rendered-<pool>-<hash>` config.
- **MachineConfigPool (MCP)** — groups nodes (by default `master`/`worker`; custom pools are supported) and tracks their rollout status: `Machine Count`, `Updated Machine Count`, `Ready Machine Count`, `Degraded Machine Count`.
- **Machine Config Daemon (MCD)** — the per-node agent that applies the rendered config and drains/reboots the node as needed.

## Configuration drift detection
The MCD checks for **configuration drift** — the on-disk state diverging from the rendered MachineConfig (e.g. an admin hand-edits a file the MachineConfig also manages) — at node boot, whenever a managed file/unit changes outside the MachineConfig, and before applying a new one. On detection it sets both the **node** (`machineconfiguration.openshift.io/state: Degraded`, with a `machineconfiguration.openshift.io/reason` annotation) and the owning **MCP** (`NodeDegraded` condition) to Degraded and reports the mismatched file/reason. A degraded node stays online and serves workloads but **cannot be updated** further until remediated.

Remediation: either make the on-disk file/permissions match the MachineConfig again, or force a re-apply (drop a force file so the MCD bypasses drift detection and reapplies the current rendered config) — never hand-edit around the mismatch permanently, since the next node reboot/MachineConfig change will re-detect the same drift.

## Where it fits in an update (day-2 vs upgrade)
MCO manifests are applied by the [[cluster-operators|CVO]] near the **end** of the release runlevels — the control plane finishes updating first, and only then does the MCO begin draining/updating/rebooting nodes to the new OS/config. A cluster can legitimately report "updated" (control plane done) while node-level MCO rollout is still in progress — see [[cluster-operators]].
