# Admin console lockout after enabling Client Authentication on security-admin-console

**Symptom → cause → fix for being locked out of the Admin UI after flipping `security-admin-console` to confidential.**

## Body
**Symptom.** Admin Web UI login fails. Server log shows
`type="CODE_TO_TOKEN_ERROR" ... clientId="security-admin-console" ... error="invalid_client_credentials"`.

**Cause.** Enabling **Client authentication** on the master realm's built-in
`security-admin-console` client converted it from public to confidential. The
browser UI has no client secret, so the code-to-token exchange fails.

**Fix.** Preferred — no restart, via admin-cli:
```bash
./kcadm.sh update clients/<ID> -r master \
  -s publicClient=true \
  -s 'attributes."pkce.code.challenge.method"=""'
```
If the admin account has OTP (so the CLI password grant fails with
`invalid_grant`), revert directly in PostgreSQL:
```sql
UPDATE client SET public_client = true WHERE id='<CLIENT_ID>';
DELETE FROM client_attributes WHERE client_id='<CLIENT_ID>' AND name='pkce.code.challenge.method';
```
then restart RHBK to flush the in-memory cache. Test in a lower environment
first; an air-gapped restart flushes the cache. (inferred — the source says to
test in a lower environment before applying in production; the air-gapped
framing is added context, not stated in kb:7138771.)

Applies to RHBK 26.x, master realm `security-admin-console` client.

## Contradictions / caveats
The DB-edit path is a recovery measure only — prefer the kcadm path when the CLI
can still authenticate. Compare to lost-admin recovery via
[[kc-bootstrap-admin]].
