# ClusterOperators & the Cluster Version Operator (CVO)

**A `ClusterOperator` resource is the standard status report for one OpenShift platform component (kube-apiserver, network, ingress, etc.); the Cluster Version Operator (CVO) is the controller that applies release manifests and watches every ClusterOperator's conditions to drive install/upgrade forward one runlevel at a time.**

## Conditions (OpenShift-specific)
Every ClusterOperator reports (at minimum):
- `Available` — the component is functioning.
- `Progressing` — the component is actively rolling out a change (e.g. `kube-apiserver-operator` finishing post-upgrade work).
- `Degraded` — the component has a problem serious enough to flag, though it may still be partially available.
- `status.versions` — the version(s) the component has actually reconciled to.

## How the CVO uses them
The CVO organizes manifests into ordered **Runlevels**. Before advancing to the next runlevel it waits until every ClusterOperator in the current one reports **`Available=True`**, **`Degraded=False`**, **and** the desired version in `status.versions`. A single stuck operator (e.g. `kube-apiserver-operator` still `Progressing=True` after its manifest applied) blocks the whole upgrade at that runlevel until it resolves — this is why "the upgrade is stuck" triage starts with `oc get co` / `oc describe co <name>`, not with individual pod logs (inferred: standard field triage order, not stated verbatim as a single sentence in the source).

The [[machine-config|Machine Config Operator (MCO)]] manifests apply near the *end* of the runlevel sequence — nodes only start draining/rebooting for a new OS/config after the control plane itself has finished updating, so a cluster can report "control plane updated" well before every node finishes (see [[machine-config]]).

## Relationship to OLM (the boundary to keep straight)
Default platform ClusterOperators are managed by the **CVO** and have **no** `Subscription` object. Application Operators installed via OperatorHub are managed by **OLM** and do have one. `oc get co` (CVO/ClusterOperator) and `oc get subs` (OLM/Subscription) are triaging two different control loops — see [[operator-lifecycle-manager]].
