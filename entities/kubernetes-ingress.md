# Kubernetes Ingress

**An Ingress exposes HTTP/HTTPS routes from outside the cluster to a [[kubernetes-service]], with routing rules (host/path) defined on the Ingress resource itself.** The Ingress API is frozen upstream (no further changes) though still generally available; upstream Kubernetes now recommends the newer Gateway API instead (upstream).

## How it's fulfilled
- Creating an Ingress object alone has **no effect** — it requires an **Ingress controller** to satisfy it, usually by programming a load balancer or edge router. Kubernetes upstream ships no controller by default; cloud providers ship AWS/GCE controllers, and third parties (e.g. ingress-nginx) fill the gap elsewhere.
- An Ingress does not expose arbitrary ports/protocols — only HTTP/HTTPS. Non-HTTP exposure uses `Service.Type=NodePort` or `LoadBalancer` instead (see [[kubernetes-service]]).
- Various Ingress controller implementations differ in the fine details even though they target the same reference spec (inferred: this is why cross-controller portability of advanced Ingress annotations is limited).

## OpenShift specifics
- OpenShift ships its own, older, native exposure object: [[openshift-route]], served by the built-in HAProxy-based Ingress Operator/router. On OCP, creating a Kubernetes Ingress object causes the **Ingress Operator to auto-generate a managed Route** under the hood, so the two objects coexist rather than compete (inferred, cross-referenced from [[openshift-route]]).
