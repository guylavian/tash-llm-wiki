# Requesting Party Token (RPT) and obtaining permissions

**An RPT is an access token issued by the token endpoint that carries the permissions RHBK granted after evaluating all policies for the requested resources/scopes. Clients request it with the UMA-ticket grant and present it as a bearer token to the resource server.**

## The grant
Send an authorization request to the standard token endpoint with
`grant_type=urn:ietf:params:oauth:grant-type:uma-ticket`. Key parameters:
- **audience** — client id of the target resource server (mandatory when `permission` is used).
- **permission** — `RESOURCE_ID#SCOPE_ID` (repeatable; `Resource A#Scope A, Scope B`, or `#Scope A`). Extension that lets clients request without a ticket. `permission_resource_format` (`id`|`uri`) and `permission_resource_matching_uri` control URI matching.
- **ticket** — a [[permission-ticket]] received during the UMA flow.
- **rpt** — a previously issued RPT to extend (incremental authorization). `response_permissions_limit` keeps only the last N.
- **claim_token** + **claim_token_format** — push extra claims to policies (BASE64 JSON, values as string arrays); format is `urn:ietf:params:oauth:token-type:jwt` (access token) or the OIDC ID Token type.
- **submit_request=true** — with a ticket, persist async permission requests for owners to approve (the "Request Access" pattern).
- **response_mode** — `decision` (`{ "result": true }`) or `permissions` (`[{"rsid":...,"scopes":[...]}]`); both return **403** when nothing maps. `response_include_resource_name` toggles resource names in the RPT.

Success returns `200` with the RPT in `access_token`; denial returns `403` with `{"error":"access_denied","error_description":"request_denied"}`.

## Client authentication to the token endpoint
- **Bearer token** — send an existing access token in the `Authorization: Bearer` header; permissions are evaluated in that token's user/client context.
- **Client credentials** — any supported method (`client_id`/`client_secret`, JWT, …).

## Requesting "any" access
Calling with only `audience` (no `permission`) evaluates permissions for resources owned by the resource server, owned by the requesting user, and explicitly granted to that user — *not* literally all resources.

## Pushing claims
Without a ticket (UMA-less flow) you can pass `claim_token`/`claim_token_format` so policies (e.g. ABAC [[authorization-policy-types|JavaScript policies]]) see those claims during evaluation.

## Contradictions / caveats
- Stable across RHBK **26.0–26.6**.
- An RPT is still an OAuth2 access token — its lifespan/validation follow [[tokens-and-sessions]] and [[oidc-token-validation]]. Use token introspection to read the permissions it carries.
- The JS adapter wraps this grant via `authorize()`/`entitlement()` — see [[policy-enforcer]] (inferred cross-reference, drawn from the enforcer chapter, not this one).
