# Remote Desktop Services (RDS)

**Remote Desktop Services hosts session-based desktops/apps (and VDI) for users
connecting through Remote Desktop clients or a web client, composed from five
role types.**

## Body

- **RD Session Host** — holds the actual session-based apps/desktops. Grouped
  into **collections**; larger deployments build a base VM image and provision
  RDSH VMs from it rather than installing apps directly on each host. Multiple
  users typically share one RD Session Host (non-admin accounts); a **personal
  session desktop** collection gives a user full admin access to their own
  instance.
- **RD Connection Broker** — routes and load-balances incoming connections across
  an RD Session Host farm, and reconnects a disconnected user to their existing
  session on the correct host. DNS round-robin load balancing to session hosts is
  **not supported** when Connection Broker is enabled. A Connection Broker
  **cluster** (for HA/scale) requires an Azure SQL Database or a SQL Server
  AlwaysOn Availability Group.
- **RD Gateway** — lets public-network users reach RDS resources over HTTPS
  (TCP 443) and UDP 3391, using SSL to encrypt the channel; the certificate name
  must match the gateway's externally resolvable FQDN.
- **RD Web Access** — a web portal (needs IIS) that publishes desktops/apps and
  launches them via the native Remote Desktop client; also needs a matching,
  CA-issued (for production) certificate.
- **RD Licensing** — activates and issues RDS Subscriber Access Licenses (SALs);
  hosting providers typically deploy two license servers in the same availability
  set for HA.

For cost-conscious/small deployments, roles are commonly combined: RD Web Access +
RD Gateway on one VM, or RD Connection Broker on the same VM as AD DS.

## Contradictions / caveats

**RD Session Host is not included in the [[server-core]] installation option** —
Server Core's role-service table lists "Remote Desktop Connection Broker,"
"Remote Desktop Licensing," and "Remote Desktop Virtualization Host" as available,
but **not** the Session Host role service. A session-based (RDSH) deployment
therefore needs Server with Desktop Experience (or a client-OS-based host for VDI);
Server Core only covers the broker/licensing/virtualization-host side of RDS.
