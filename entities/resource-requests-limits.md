# Resource Requests and Limits

**A container's `request` tells the scheduler how much of a resource to reserve for it; its `limit` tells the kubelet/kernel the ceiling it may not exceed — and the two resource types (CPU, memory) enforce their limit differently.**

## Requests — the scheduling input
The `kube-scheduler` uses each container's resource **request** to decide which node can host the Pod. If a Pod's total requests don't fit on any node (or the request is unset and the cluster is full), the Pod is stuck **Pending** with a `FailedScheduling: Insufficient cpu/memory` event — the request, not the limit, drives placement.

If a node has spare capacity, a container **can** use more than its request; a request is a floor the kubelet reserves for that container, not a hard ceiling.

## Limits — enforcement differs by resource
- **CPU limit** — enforced by throttling. The kernel restricts CPU access once the container approaches its limit; a CPU limit is a hard cap the container simply cannot exceed, but it never gets killed for hitting it.
- **Memory limit** — enforced by the kernel via out-of-memory (OOM) kills. A container that exceeds its memory limit isn't stopped immediately — the kernel kills it reactively, under memory pressure — producing an **OOMKilled** container status. Because the kubelet then restarts it under the owning controller's restart policy, an under-sized memory limit shows up operationally as a **CrashLoopBackOff**.
- If only a limit is set (no request), Kubernetes copies the limit value as the request.

## Built-in resource types
`cpu` (cores), `memory` (bytes), `ephemeral-storage` (bytes), and `hugepages-<size>` (Linux only) are the built-in types; clusters can also expose custom **extended resources** via device plugins.
