# OpenShift internal OAuth server

**OpenShift's control plane runs a built-in OAuth server (OpenShift-specific — no upstream Kubernetes equivalent) that turns a validated identity-provider login into a Kubernetes API bearer token.**

## Flow
1. A token request hits `/oauth/authorize` with a configured identity provider (htpasswd, LDAP, GitHub, GitLab, Google, Keystone, request-header, OIDC, basic-auth — see [[openshift-auth-and-rbac]]).
2. The identity provider determines the requesting person's identity.
3. The server maps that identity to (or creates) an OpenShift `User`, mints an access token, and returns it.

Supports standard OAuth2 **authorization code grant** and **implicit grant** flows; clients using `response_type=token` with a challenging client id (e.g. `openshift-challenging-client`) get `WWW-Authenticate` challenge/redirect semantics per RFC 6749 §4.2.2/§4.1.2.1.

## Token types and duration
- **Access tokens** — longer-lived; default **24-hour** lifetime (`accessTokenMaxAgeSeconds`), configurable per-cluster via the `OAuth` CR (`spec.tokenConfig`) or overridden per `OAuthClient`.
- **Authorize codes** — short-lived, single-purpose: only exchanged for an access token.
- **Grant options** — `auto` (silently approve) vs `prompt` (ask the user) when a client hasn't previously been granted access.

## Relationship to RBAC and ServiceAccounts
OAuth answers *who is this* (authentication); [[kubernetes-rbac]] then answers *what can they do* (authorization) — the two are deliberately separate layers. [[service-accounts]] bypass the OAuth server entirely, authenticating with their own JWTs directly to the API server.
