# Route TLS Termination

**An [[openshift-route]]'s `spec.tls.termination` field selects one of three ways HTTPS traffic is handled between the client and the backing pod.**

## The three modes
- **`edge`** — TLS terminates at the Ingress Controller (router); traffic from router to the destination pod runs **unencrypted** inside the cluster network. Configured via `oc create route edge --cert=tls.crt --key=tls.key [--ca-cert=ca.crt]`.
- **`passthrough`** — encrypted bytes pass straight through the router to the pod, which terminates TLS itself. No key/certificate is set on the Route at all — the destination pod owns the whole TLS handshake. `oc create route passthrough --service=frontend --port=8080`.
- **`reencrypt`** — TLS terminates at the router (using the route's own cert/key), then the router opens a **new**, separate TLS connection to the pod. This mode **requires a destination CA certificate** (`--dest-ca-cert`) so the router trusts the pod's certificate — the one prerequisite that doesn't apply to `edge`.

## insecureEdgeTerminationPolicy
- Applies to `edge` and `reencrypt` routes: `None`/empty (HTTP disabled), or `Redirect` (HTTP requests are redirected to HTTPS). `passthrough` routes instead accept only `None` or `Redirect` with no plaintext HTTP path since the router never decrypts.

## HSTS
- Enabling HTTP Strict Transport Security on a route adds a `Strict-Transport-Security` header to HTTP/HTTPS responses, telling browsers to only ever use HTTPS for that host — this removes the need for (and latency of) an HTTP→HTTPS redirect on subsequent visits, working together with `insecureEdgeTerminationPolicy: Redirect`.

## Externally managed certificates
- Both `edge` and `reencrypt` routes support an `externalCertificate` referencing a Secret managed outside the Route object, easing certificate rotation. Caveat: the router does **not** auto-pull a CA bundle from that secret — a `tls.caCertificate` needed for client auth or re-encryption must be supplied separately or bundled into `tls.crt`.

## OpenShift specifics
- This is an **OpenShift-native** feature of the Route API — there is no equivalent field on the upstream Kubernetes [[kubernetes-ingress]] object; Ingress-to-Route translation on OCP maps common TLS configurations onto these three modes under the hood (inferred, from the Route/Ingress coexistence described on [[openshift-route]]).
