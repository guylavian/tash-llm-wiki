# Permission ticket and the UMA flow

**A permission ticket is an opaque UMA token, issued only by resource servers via the [[protection-api|Permission Endpoint]], that names the resources/scopes a client is requesting plus the access context. The client exchanges it at the token endpoint for an [[requesting-party-token|RPT]].**

## The UMA authorization process
1. Client calls a UMA-protected resource server **without** an RPT.
2. Resource server replies `401` with `WWW-Authenticate: UMA realm="...", as_uri="https://.../realms/{realm}", ticket="..."`.
3. Client uses `as_uri` (and UMA2 discovery) to find the token endpoint and POSTs `grant_type=urn:ietf:params:oauth:grant-type:uma-ticket` with `ticket=${permission_ticket}`.
4. RHBK evaluates the policies referenced by the ticket and returns an RPT (`200`) or `403 request_denied`.

## Person-to-person sharing
UMA enables a resource **owner** (e.g. Alice) to share their resource (her bank account) with a **requesting party** (Bob) for a specific scope (view), asynchronously and revocably. Enable **User-Managed Access** in Realm Settings; owners then manage sharing under Account Console → **My Resources** (share, view people with access, approve/deny pending requests, revoke).

## Asynchronous request access
Adding `submit_request=true` to the ticket exchange makes RHBK persist a permission request per denied resource, surfacing it to the owner for approval — the "Request Access" button pattern.

## Contradictions / caveats
- Stable across RHBK **26.0–26.6**.
- Permission tickets are issued **only** by resource servers (holding a [[protection-api|PAT]]); clients cannot mint them.
- UMA sharing requires the realm-level User-Managed Access toggle ON; without it the Account Console "My Resources" flow is unavailable.
