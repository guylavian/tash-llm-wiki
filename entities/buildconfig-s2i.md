# BuildConfig and Source-to-Image (S2I)

**A `BuildConfig` is OpenShift's REST object for a build definition: a build strategy (how) plus one or more sources (what), with triggers for when a new build should run.**

## BuildConfig anatomy
- **`source`** — `Git` (a repo URI), `Dockerfile` (inline), or `Binary` (accept a payload); multiple sources are possible in one build.
- **`strategy`** — `sourceStrategy` (S2I), `dockerStrategy`, or `customStrategy`; the strategy section names the builder image to use (e.g. an `ImageStreamTag`).
- **`output`** — where the resulting image is pushed, typically `to: {kind: ImageStreamTag, name: ...}` — see [[image-streams]] for what happens next.
- **`triggers`** — a list of events (`GitHub`/webhook, `Generic` webhook, `ImageChange`) that create a new build automatically; a config-change to the `BuildConfig` itself is otherwise the only way to trigger one.
- **`runPolicy`** (default `Serial`) — whether builds from this config run sequentially or in parallel.
- **`postCommit`** — an optional hook script run against the built image (e.g. running the test suite) before the build is considered complete.

## The three build strategies
- **Source (S2I)** — the default and OpenShift's signature strategy: injects application source into a builder image and assembles a new image via the builder's `assemble`/`run` scripts, without requiring a Dockerfile from the developer. Advantages over a raw Dockerfile build: supports incremental builds (reuses previously downloaded dependencies/artifacts), avoids exposing the host to arbitrary root-privileged Dockerfile operations, and lets an org patch/rebuild consistently from a shared builder-image ecosystem.
- **Docker** — builds a container image directly from a Dockerfile (via Buildah under OpenShift 4).
- **Custom** — the builder image itself owns the entire build process; runs with high privilege and is not available to regular users by default — restrict to trusted cluster admins.

## Customizing an S2I builder image
An S2I builder image exposes its `assemble`/`run` scripts at a location given by the `io.openshift.s2i.scripts-url` image label (inspectable with `podman inspect`). To customize behavior without losing upgrade compatibility, wrap the default script from a `.s2i/bin/assemble` (or `.s2i/bin/run`) override rather than replacing it outright — a `run` wrapper must `exec` the default script so signals propagate correctly.
