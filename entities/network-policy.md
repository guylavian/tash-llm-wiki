# NetworkPolicy

**A NetworkPolicy selects pods by label and declares which other pods, namespaces, or IP blocks (CIDRs) they may exchange traffic with, for ingress and/or egress independently.** It requires a network plugin that implements it — creating the object against a plugin without support is a no-op.

## Default posture
- **By default, all pods in a project/namespace are reachable from any other pod or network endpoint** — a pod is "non-isolated" until a NetworkPolicy selects it.
- Once **any** NetworkPolicy selects a pod for a given direction (ingress/egress), that pod only accepts the connections explicitly allowed by the union of all policies selecting it for that direction; a pod matched by zero policies stays fully open.
- **NetworkPolicies are additive** — combining an `allow-same-namespace` policy and an `allow-http-and-https` policy on the same pods grants the union of both, not the intersection.
- Traffic to/from the node a pod runs on is always allowed regardless of IP-block rules; a pod also can never fully block access to itself.

## OpenShift specifics
- As of OCP 4.22, OpenShift **ships its own default NetworkPolicy objects in some control-plane namespaces** to protect control-plane components — do not modify these; check with `oc get networkpolicies --all-namespaces`. Earlier/later releases may cover more namespaces (inferred: coverage is expected to grow release over release, so an upgrade can introduce new implicit deny-by-default behavior in a namespace that previously had none).
- [[ovn-kubernetes]] is the default OCP network plugin and implements NetworkPolicy enforcement (plus NetworkPolicy audit logs) via OVN/OVS flows.

## Contradictions / caveats
- A NetworkPolicy silently doing nothing is almost always either (a) no supporting network plugin, or (b) a selector typo — both fail open/closed without an error on the policy object itself; confirm actual enforcement by testing connectivity, not just `oc get networkpolicy`.
