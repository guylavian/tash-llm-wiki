# Global Catalog

**A global catalog (GC) server is a domain controller that stores a full, writable replica of its own domain directory partition plus a partial, read-only replica of every other domain in the forest — exposing a single queryable port (3268/TCP) for forest-wide attribute lookups and UPN logon.**

## Body

### What the GC holds

Every GC stores:
- Full, writable replicas of the **schema** and **configuration** partitions (same as all DCs).
- Full, writable replica of **its host domain** directory partition.
- Partial, read-only replicas of **every other domain** in the forest — containing all objects but only the subset of attributes marked for GC replication in the schema (the **Partial Attribute Set**).

### Why the GC is needed

In multi-domain forests, two operations cannot complete without reaching a GC:

1. **Forest-wide search** — LDAP queries on port 3268 fan out across all domains implicitly; without a GC the client would need to know which DC in which domain holds each object.
2. **UPN logon** — when a user logs on with a UPN (`user@contoso.com`) and the authenticating DC cannot resolve the UPN suffix to a domain, it must query a GC to identify the correct domain.

Universal group membership is also stored in and distributed by the GC (see [[universal-group-membership-caching]] for the alternative when GC placement is not feasible).

### Placement guidance

**Single-domain forest:** designate all DCs as GC servers — no additional replication traffic is incurred because there is no second domain partition to replicate. Only GC-designated DCs respond to queries on port 3268.

**Multi-domain forest:** place a GC at every site that contains more than 100 users or that runs GC-dependent applications (Exchange, MSMQ, DCOM-heavy workloads). Exceptions:

- **Limited WAN bandwidth:** skip the GC and enable [[universal-group-membership-caching]] instead.
- **Infrastructure Master conflict:** do not co-locate a GC with the Infrastructure Operations Master FSMO unless every DC in the domain is a GC, or the forest has a single domain. See [[fsmo-roles]].

RODCs can be promoted to GC status, but major applications such as Microsoft Exchange Server do not support an RODC as a GC server (inferred — from placement note citing Exchange 2003/2007 behavior).

### Replication implications

GC replication adds inter-domain partial-attribute-set traffic. In large forests, adding GC servers at every site trades WAN replication bandwidth for lower logon and search latency. The KCC builds separate replication connections for the GC partial replicas (inferred — combining replication-concepts and placement notes).

## Contradictions / caveats

- In a single-domain forest, even non-GC DCs behave as "virtual GC servers" for authentication (they hold the only domain partition), but only GC-designated DCs answer port 3268 queries for tools like Find People or Expand Universal Groups.
- Roaming users always contact a GC on first logon at a new location; if GC access requires a slow WAN hop, logon latency may be unacceptable.
