# Cross-Site Synchronization & Split-Brain Recovery

**The manual procedure to re-synchronize two Data Grid sites after their caches
diverge — e.g. after a split-brain or a maintenance outage. The offline site's
caches are cleared and replaced from the active site.**

## When it is needed
The Active/Passive multi-cluster model is consistency-first but not self-healing:
after a failure, **manual operations** are usually required to restore redundancy.
Sites become out-of-sync when a synchronous Data Grid request fails; this is hard
to monitor and needs a **full manual re-sync**. Until completed, the "no data
loss" guarantee does not hold for a subsequent failure.

## Procedure (offline site = `site-b`, active = `site-a`)
1. **Stop RHBK on the offline site** — set the `Keycloak` CR `instances: 0`. This
   clears RHBK's own caches so its state cannot drift from Data Grid.
2. **Connect to the offline Data Grid** via the CLI:
   `oc -n keycloak exec -it pods/infinispan-0 -- ./bin/cli.sh --trustall --connect https://127.0.0.1:11222`
   (credentials are the `developer`/admin ones set in
   [[external-data-grid-operator]]).
3. **Take cross-site replication offline** toward the active site so the upcoming
   clear does not propagate and wipe good data:
   `site take-offline --all-caches --site=site-a`
   then confirm `site status --all-caches --site=site-a` returns `offline`
   (**critical** — if not offline, clearing wipes both sites).
4. **Clear the stale caches** on the offline site:
   `clearcache actionTokens`, `clearcache authenticationSessions`,
   `clearcache loginFailures`, `clearcache work`.
5. **Bring replication back online**:
   `site bring-online --all-caches --site=site-a`, confirm status `online`.
6. Restart RHBK on the offline site (restore `instances`), then re-add the site to
   the load balancer EndpointGroup ([[ha-load-balancer-failover]]).

## Caveats / gotchas
- A re-sync issues a **full state transfer**, stressing the system (higher
  response times / resource usage) — schedule accordingly.
- The clear list (`actionTokens`, `authenticationSessions`, `loginFailures`,
  `work`) is the set of synchronously replicated caches in this blueprint; verify
  the cache set for your version before clearing.
- Taking a site offline / online in the LB is a related but separate operation
  (the AWS Lambda automates the fencing decision; manual `operate-site-offline` /
  `operate-site-online` chapters cover doing it by hand) (inferred — drawn from the
  load-balancer-failover material, not this chapter's cited sources).
- Wording shifted "multi-site" (26.0/26.2) → "multi-cluster" (26.4/26.6); the CLI
  steps are stable.
