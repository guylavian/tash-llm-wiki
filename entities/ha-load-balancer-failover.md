# HA Load Balancer & Site Failover (AWS Global Accelerator)

**The multi-cluster load-balancer building block: an AWS Global Accelerator with
a static anycast IP routes client traffic to both sites, health-checks the
`/lb-check` endpoint, and fails over to the healthy site on outage.**

## Why a static-IP accelerator
Client-side DNS caching makes DNS-based failover unreliable, so the blueprint
uses an **AWS Global Accelerator** that exposes a **static IP** that does not
change when traffic is re-routed between sites.

- One **Network Load Balancer (NLB)** per ROSA cluster exposes the Keycloak pods
  as Accelerator endpoints.
- Each cluster endpoint gets **weight 128** (half of max 255) so traffic splits
  evenly while both sites are healthy.
- The accelerator listens on TCP **443** and forwards to the NLBs.
- **Fail-open:** if *both* sites are marked unhealthy, the Accelerator forwards to
  a randomly chosen site rather than dropping all traffic.

## Health checking
The NLB service is annotated to probe the RHBK **`/lb-check`** path over HTTPS:
```
service.beta.kubernetes.io/aws-load-balancer-healthcheck-path: "/lb-check"
service.beta.kubernetes.io/aws-load-balancer-healthcheck-protocol: "https"
service.beta.kubernetes.io/aws-load-balancer-healthcheck-interval: "10"
service.beta.kubernetes.io/aws-load-balancer-healthcheck-healthy-threshold: "3"
service.beta.kubernetes.io/aws-load-balancer-healthcheck-unhealthy-threshold: "3"
```
`/lb-check` is exposed only when the **`multi-site` feature** is enabled
([[multi-site-feature-flag]]) (inferred — not verified verbatim in this page's
three cited chapters). Operational verification:
- `curl -s https://<lb-url>/lb-check` (and per-site URLs) for app health.
- `curl -s https://keycloak:<managementport>/health` for DB readiness (management
  port only).
- Data Grid cache-manager health via
  `/rest/v2/cache-managers/default/health/status`.

## Automated fencing (split-brain)
A separate **AWS Lambda** — triggered by ROSA's Prometheus/Alert Manager — detects
Data Grid cross-site connectivity loss and **disables a non-responding site** in
the Accelerator EndpointGroup. This prevents requests reaching a degraded/isolated
site. Manual site offline/online procedures are also documented (e.g.
`site take-offline`/`site bring-online` on the Data Grid CLI) and feed into
[[site-synchronization]] (inferred — these commands are grounded in the
corpus's Infinispan CLI Batch / Synchronizing sites chapters, not one of this
page's three cited chapters).

## Sticky sessions
On OpenShift the default passthrough Ingress (HAProxy) uses **source-IP sticky
sessions**. For load tests or when a reverse proxy sits in front, disable them on
the CR (grounded in the corpus's "Deploying RHBK for HA with the Operator"
chapter — not one of this page's three cited chapters):
```yaml
spec:
  ingress:
    enabled: true
    annotations:
      haproxy.router.openshift.io/balance: roundrobin
      haproxy.router.openshift.io/disable_cookies: 'true'
```

## Contradictions / caveats
- The blueprint is **AWS-specific** (Global Accelerator + NLB + Lambda). On other
  platforms you must provide an equivalent static-IP failover LB that probes
  `/lb-check` and can fence a degraded site.
- **Fail-open** means that with both sites unhealthy the LB still forwards
  traffic — it does not guarantee a working backend.
- Failover is not instantaneous: requests may error until the LB detects the
  failure; some scenarios incur up to 5 min downtime (inferred — the "up to 5
  minutes" figure is grounded in the corpus's multi-site Introduction chapter,
  not one of this page's three cited chapters).
