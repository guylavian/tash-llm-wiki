# Operator rolling updates (`spec.update`)

**How the RHBK Operator decides between a zero-downtime rolling update and a
downtime-incurring recreate when the [[keycloak-cr]] changes.**

## Default behavior

By default the Operator does **rolling updates** on configuration changes (no
downtime when ≥2 replicas run) and **recreate** updates when the image name/tag
changes. Tune via `spec.update`:

```yaml
spec:
  update:
    strategy: RecreateOnImageChange | Auto | Explicit
    revision: "abc"   # only meaningful for Explicit
```

## Strategies

- **`RecreateOnImageChange`** — recreate (scale down first) whenever the image
  field changes. Mimics RHBK 26.1-or-older behavior.
- **`Auto`** — the Operator detects whether a rolling vs recreate update is
  possible. Currently it does a rolling update if the **RHBK version is the same**
  for old and new image; it starts a short **Job** to assess feasibility (consumes
  cluster resources, adds a slight delay). Future versions will use more signals
  (config/image/version).
- **`Explicit`** — the user decides. The `revision` field is a manual trigger:
  the Operator does not interpret its value, but any CR change while `revision` is
  **unchanged** triggers a rolling update.

## Statuses (`RecreateUpdateUsed` condition)

`Unknown` (no update yet), `False` (last update was rolling), `True` (last update
was recreate); `lastTransitionTime` marks when.

## Rolling updates for patch releases (`rolling-updates:v2`, experimental)

Enable automatic rolling updates across patch versions in the same `major.minor`
stream:

```yaml
spec:
  features:
    enabled:
      - rolling-updates:v2
  update:
    strategy: Auto
```

This is **experimental and not recommended for production**.

## Contradictions / caveats

- The `update` strategy and `rolling-updates:v2` are documented from **26.4/26.6**;
  pre-26.2 streams predate this configurability (the `RecreateOnImageChange` value
  exists precisely to reproduce 26.1-and-older behavior).
- **`Auto` + unsupported `podTemplate`**: the feasibility Job may miss
  podTemplate-derived settings (or Secrets/ConfigMaps/Volumes referenced there) and
  draw the wrong conclusion — prefer another strategy if you use podTemplate
  ([[operator-pod-template]]).
- **`Explicit` + automatic OLM upgrades** can cause failures, since the Operator may
  attempt an unsupported rolling update after being upgraded — use Manual OLM
  approval ([[operator-olm-install]]) and test in non-prod first.
