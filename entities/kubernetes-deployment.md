# Kubernetes Deployment

**A Deployment is the controller for stateless workloads: it manages one or more ReplicaSets to reach and hold a declared desired state, replacing Pods at a controlled rate.**

## What it manages
- `.spec.replicas` — desired Pod count.
- `.spec.selector` — how the owned ReplicaSet finds its Pods (must match the Pod template's labels).
- Updating `.spec.template` (the Pod template) creates a **new ReplicaSet**; the Deployment scales it up while scaling the old one down. Each new ReplicaSet bumps the Deployment's revision.
- `kubectl rollout status deployment/<name>` tracks an in-progress rollout; `kubectl rollout undo deployment/<name>` (optionally `--to-revision=N`) rolls back to a prior, stable revision — the standard remedy when a rollout leaves the app crash-looping.

## Rollout strategy
`.spec.strategy.type` is one of:
- **RollingUpdate** (default) — gradually scales the new ReplicaSet up and the old one down. `maxUnavailable` (default 25%) bounds how far below `replicas` the Deployment may drop; `maxSurge` (default 25%) bounds how far above `replicas` it may temporarily go. Actual Pod count during a rollout sits between `replicas - maxUnavailable` and `replicas + maxSurge`.
- **Recreate** — kills all existing Pods before creating new ones. Simpler, but causes a availability gap; use only when the app can't run two versions concurrently (e.g. a schema migration that isn't backward compatible).

## OpenShift: Deployment vs DeploymentConfig
OpenShift ships **two** similar objects: the Kubernetes-native `Deployment` (built on `ReplicaSet`) and OpenShift's own, older `DeploymentConfig` (built on `ReplicationController`, the predecessor of ReplicaSet). **Use `Deployment` unless a specific `DeploymentConfig`-only feature is required** — `DeploymentConfig` is the legacy path. See [[openshift-workloads]] for the OpenShift-specific strategy set (Rolling/Recreate/Custom) that applies only to `DeploymentConfig`.

## Contradictions / caveats
- The Kubernetes upstream Deployment strategy set is only `Recreate`/`RollingUpdate`. OpenShift's `DeploymentConfig` additionally supports `Custom` strategies and image/config-change triggers — these are **not** available on a plain Kubernetes `Deployment` (inferred: OpenShift layers strategy/trigger richness onto the older object, not the newer one).
