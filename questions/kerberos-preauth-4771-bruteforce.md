# Repeated Event 4771 Kerberos pre-auth failures — brute force? What to check in AD

**Repeated 4771 events with failure code 0x18 (bad password) from one source against one account are the domain-controller signature of a Kerberos password-guessing / brute-force attempt; confirm by correlating with Event 4740 (account lockout) and your lockout policy.**

> This question spans two skills (windows-eventlog for the Event-ID semantics, the AD
> wiki for the directory context). Answer follows the wiki-query protocol; the
> event-code detail below is sourced to the windows-eventlog skill and tagged
> accordingly.

## Question

> We're seeing repeated Event 4771 Kerberos pre-authentication failures from one
> workstation against a service account — is this a brute-force attempt, and what
> should we check in AD?

## Answer

**Lead with the observed signal.** 4771 is logged **on the KDC (domain controller)**,
one per failed Kerberos AS-REQ pre-authentication —
"4771 … Kerberos pre-authentication failed"
(`reference/active-directory/ad-ds-appendix-l-events-to-monitor.md:223`, legacy ID 675).
The **failure code** field discriminates the cause (windows-eventlog skill): `0x18` =
bad password (the brute-force signature), `0x12` = account disabled/locked/expired,
`0x17` = password expired — a burst of `0x18` from one source against one principal is
password guessing; a mix of codes is more likely a stale credential (inferred, from the
failure-code semantics).

**What to check in AD, in order:**

1. **Correlate with lockout — Event 4740** "A user account was locked out"
   (`reference/active-directory/ad-ds-appendix-l-events-to-monitor.md:198`;
   also `reference/active-directory/ad-ds-advanced-audit-policy-configuration.md:309`).
   If 4771×N is followed by 4740, the guessing crossed the lockout threshold — that
   confirms both the attempt and that your policy caught it (inferred).
2. **The source**: 4771 identifies the client address; a *service account* being
   targeted from a *workstation* is abnormal (service accounts authenticate from
   servers) — treat the source workstation as suspect (inferred).
3. **NTLM path too**: if the same campaign tries NTLM, it surfaces as 4776 on the DC,
   not 4771 — check both if the attacker is protocol-hopping (inferred; 4776 is the
   NTLM validation event per the windows-eventlog skill).
4. **Lockout policy**: verify Account Lockout Threshold/Duration/Observation-window are
   set so guessing is bounded (the policy that produces 4740).

## Contradictions / caveats

- 4771 alone is not proof of compromise — a user with a stale cached credential or a
  mis-scheduled task with an old password produces the same event. The discriminator is
  the **failure code** (0x18 repeated) plus the **source/target mismatch**, not the
  event ID alone (inferred). Read the actual 4771 code before declaring an incident.
- Event-code meanings (0x18/0x12/0x17) and the 4776 NTLM correlation are from the
  windows-eventlog skill, not the AD reference corpus — grounded there, tagged here.
