# How OpenShift handles persistent storage, PVCs, and dynamic provisioning

OpenShift uses the standard upstream Kubernetes storage model with no new storage API objects — all OpenShift-specific behavior is operational (shipped CSI drivers, documented admin procedures).

## The PV/PVC/StorageClass model

- A **PersistentVolume (PV)** is a cluster resource describing an actual piece of storage — backend type, capacity, access modes, reclaim policy, volume mode. An admin pre-provisions it, or a provisioner creates it on demand.
- A **PersistentVolumeClaim (PVC)** is a namespaced request for storage: size, access mode(s), and volume mode. Pods reference the PVC by name in their `volumes` block. ([persistent-volume-claim])
- If no matching pre-created PV exists, and the PVC names a **StorageClass** (or a default class exists), that class's `provisioner` triggers **dynamic provisioning** — the cluster calls the driver to create a new volume and its PV object. ([storage-class])
- A PVC with **no matching PV and no viable StorageClass** (neither specified nor a cluster default) stays `Pending` forever — the most common storage failure mode. ([openshift-storage]:40)

## Dynamic provisioning via CSI

Dynamic provisioning is driven by a **StorageClass** whose `provisioner` field names a **CSI driver** (the modern plugin model). When a PVC references that class and no PV matches, the CSI driver creates the backing volume, publishes a PV object, and the control plane binds it to the PVC. ([csi-driver]:28-29)

Key StorageClass knobs that affect provisioning behavior:
- **`volumeBindingMode: WaitForFirstConsumer`** — delays provisioning until a pod consumes the PVC, so the volume lands in the correct topology for the pod's scheduling constraints. `Immediate` (the default) can provision a volume the scheduler can't reach. ([storage-class]:31)
- **`allowVolumeExpansion: true`** — must be set on the class before a bound PVC can resize. ([storage-class]:29)
- **`reclaimPolicy`** — `Delete` (dynamic-provisioning default) removes the PV and backing storage when the PVC is deleted; `Retain` preserves them. ([openshift-storage]:42-45)

## Access modes & volume modes

A PVC requests one of: `ReadWriteOnce` (RWO, single node), `ReadOnlyMany` (ROX), `ReadWriteMany` (RWX), or `ReadWriteOncePod` (RWOP, single pod cluster-wide). Using RWO for a multi-replica workload that needs concurrent writers is the textbook **Multi-Attach error**. Volume mode is `Filesystem` (default, mounted as a directory) or `Block` (raw block device). ([persistent-volume-claim]:26-27)

## OpenShift vs Kubernetes upstream

The PV/PVC/StorageClass/CSI model is pure upstream Kubernetes — OpenShift adds no new API surface. What differs is operational: OCP ships CSI drivers for its supported cloud/on-prem platforms (AWS EBS, GCE PD, Azure Disk, vSphere, etc.) out of the box, and documents day-2 admin tasks like changing the cluster default StorageClass and expanding persistent volumes as first-class procedures. ([openshift-storage]:51-52)
