# Capping concurrent authentication sessions per browser/root session (authSessionsLimit)

**Yes — cap it with the `authenticationSessions` SPI's `authSessionsLimit`; default 300 per root session; oldest sub-session is evicted at the limit.**

## Answer

Each unfinished browser login flow is an `AuthenticationSessionEntity` held under one
`RootAuthenticationSessionEntity` (one per browser). The maximum number of
`AuthenticationSessionEntity` per `RootAuthenticationSessionEntity` is configured in the
`authenticationSessions` SPI via the `authSessionsLimit` property
(rhbk-26-4-mitigating-security-threats.md:450-453).

- **Default:** 300 authentication sessions per root authentication session
  (rhbk-26-4-mitigating-security-threats.md:455-456).
- **Behavior at the limit:** the oldest authentication sub-session is removed when a new
  authentication session request arrives — growth is bounded, not rejected
  (rhbk-26-4-mitigating-security-threats.md:457-458).
- **How to change — RHBK 26.4+ (double-dash SPI syntax):**
  `bin/kc.sh start --spi-authentication-sessions--infinispan--auth-sessions-limit=100`
  (rhbk-26-4-mitigating-security-threats.md:460); env form
  `KC_SPI_AUTHENTICATION_SESSIONS__INFINISPAN__AUTH_SESSIONS_LIMIT`
  (rhbk-26-4-all-provider-config.md:13).
- **How to change — RHBK 26.0 / 26.2 (single-dash syntax):**
  `--spi-authentication-sessions-infinispan-auth-sessions-limit`; env
  `KC_SPI_AUTHENTICATION_SESSIONS_INFINISPAN_AUTH_SESSIONS_LIMIT`
  (rhbk-26-2-all-provider-config.md:12, rhbk-26-2-mitigating-security-threats.md:407).

## Contradictions / caveats

- **Version-attributed syntax:** the SPI option spelling changed between 26.2 (single-dash)
  and 26.4 (double-dash separators between SPI/provider/option). Use the form matching your
  RHBK version; both are quoted verbatim above from their respective versions' docs.
- **Scope of the cap (the hardening caveat):** `authSessionsLimit` bounds sub-sessions
  *within one* root session. A flood that opens many *distinct* browser/root sessions
  creates many `RootAuthenticationSessionEntity` objects, which this setting does not cap —
  so this knob alone does not stop a distributed half-open-login flood (inferred). The same
  chapter's own guidance: to keep the number of `RootAuthenticationSessionEntity` under
  control, "using an advanced firewall control to limit ingress network traffic is
  recommended" (rhbk-26-4-mitigating-security-threats.md:445-446); it also warns that many
  root sessions with many sub-sessions raise memory usage, and that without load-balancer
  session stickiness the cluster pays extra network round-trips per non-owner-node request
  (rhbk-26-4-mitigating-security-threats.md:447-449).
