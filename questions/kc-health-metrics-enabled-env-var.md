# What does `KC_HEALTH_METRICS_ENABLED` turn on?

**`KC_HEALTH_METRICS_ENABLED` does not exist** in the Keycloak / Red Hat build of Keycloak corpus. There is no combined health-and-metrics build-time option — that name is a fabrication (extracted: `_meta/eval/cases300.jsonl` case `fab-004`).

## The real separate options

What the user likely wants is one or both of these separate **build-time** environment variables:

| Variable | Effect | Source |
|---|---|---|
| `KC_HEALTH_ENABLED=true` | Enables the `/health/*` endpoints (started/live/ready) on the management port | `rhbk-26-6-containers.md:31` (extracted) |
| `KC_METRICS_ENABLED=true` | Enables the `/metrics` Prometheus/OpenMetrics endpoint on the management port | `rhbk-26-6-containers.md:32` (extracted) |

- **`KC_HEALTH_ENABLED`** — turns on the four health REST endpoints (`/health/started`, `/health/live`, `/health/ready`, `/health`) that return HTTP `200 OK`/`503` + JSON `status`. Documented in the Observability Guide, chapter 2 (`rhbk-26-6-health.md:28-40`). Also maps to `bin/kc.sh build --health-enabled=true`.
- **`KC_METRICS_ENABLED`** — turns on the `/metrics` scrape endpoint serving system/JVM/DB/HTTP/cache metric families in OpenMetrics text format. Documented in the Observability Guide, chapter 3 (`rhbk-26-6-configuration-metrics.md:22-24`). Also maps to `bin/kc.sh start --metrics-enabled=true`.

Both are typically enabled together in Containerfile examples (`rhbk-26-6-containers.md:31-32`, `rhbk-26-4-containers.md:32-33`, `rhbk-26-0-containers.md:30-31`), which may explain why a combined name seems plausible — but the product never shipped a single combined variable.
