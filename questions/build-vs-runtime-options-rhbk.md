# What is the difference between build options and runtime options in RHBK?

**Build options are persisted into an optimized RHBK image by `kc.sh build`; runtime (configuration) options are applied at `kc.sh start`.** The two classes exist because `build` performs a Quarkus re-augmentation that bakes certain decisions into the server image — provider scanning, config pre-parsing, DB vendor resources — so the server skips that work at every startup.

## Build options

- Applied with `kc.sh build <build-options>` — marked with a 🛠 (tool icon) in *All configuration* (`rhbk-26-4-configuration.md:243`).
- Persisted into the server image in **plain text** — never store sensitive data (passwords, secrets) as build options (`rhbk-26-4-configuration.md:242`).
- The build command performs a closed-world provider scan, pre-parses config files, and prepares DB-specific resources — an optimization that matters most in container/Operator environments where startup time is critical (`rhbk-26-4-configuration.md:286-291`).
- **Examples:** `db`, `features`/`features-disabled`, `health-enabled`, `metrics-enabled`, `vault` (extracted — `entities/build-vs-runtime-options.md:5-6`).
- List them with `kc.sh build --help`.

## Runtime (configuration) options

- Applied at `kc.sh start` — everything *not* marked with the tool icon.
- **Examples:** `db-url-host`, `db-username`, `db-password`, `hostname`, `https-certificate-file`, `proxy-headers` (extracted — `entities/build-vs-runtime-options.md:7-8`).
- Use the KeyStore Config Source for sensitive runtime options (passwords, secrets) — it is designed for that purpose (`rhbk-26-4-configuration.md:242`).

## Optimized startup flow

The recommended pattern for containers/Operator deployments (`rhbk-26-4-configuration.md:248-252`):
```
kc.sh build --db=postgres          # persist build options into the image
kc.sh start --optimized            # skip implicit build; faster start
```

Without `--optimized`, `kc.sh start` detects the need for build and runs it implicitly — slower, but no separate step.

## What happens when a build option appears at `start`

- Value matches what was built → **silently ignored** (`rhbk-26-4-configuration.md:255-258`).
- Value differs from what was built → **warning logged, previously built value used**; must re-run `build` for the new value to take effect (`rhbk-26-4-configuration.md:259-261`).

## Stricter behavior in RHBK 26.6+

In RHBK 26.6+, mismatched build-time options at startup cause the server to **fail to start** instead of just logging a warning — previously a warning (`rhbk-26-0-migration-changes.md:290-291`).

## Contradictions / caveats

- The 🛠 annotation split is stable across 26.0–26.6, but the exact *set* of build options can grow between releases (inferred).
- Do not put build options in a Java KeyStore — they are persisted in plain text regardless of config source (`rhbk-26-4-configuration.md:242`).
- For Operator-managed deployments, custom images **must** be optimized (all build-time options set + `kc.sh build`).
