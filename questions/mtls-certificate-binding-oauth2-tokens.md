# What is mTLS certificate binding for OAuth2 tokens?

**mTLS certificate binding** (RFC 8705) is a mechanism that sender-constrains OAuth2 access tokens by embedding the SHA-256 thumbprint of the client's TLS certificate into the token's `cnf.x5t#S256` confirmation claim. The resource server extracts the client certificate from the mutually-authenticated TLS layer and compares thumbprints — if they match, the request is the legitimate holder of that token. A stolen token is useless without the matching private key.

## Key points

- **Two independent features in RFC 8705:** (1) mTLS as a client authentication method at the token endpoint (`tls_client_auth` or `self_signed_tls_client_auth`), and (2) certificate-bound token issuance. These are orthogonal — a public client that does not use mTLS client-auth can still receive a cert-bound token.
- **Binding claim:** `cnf.x5t#S256` = base64url(SHA-256(DER-encoded certificate)), with trailing `=` padding omitted.
- **Resource server validation:** extract the client cert from the mTLS layer, compute SHA-256 of the DER encoding, require exact match against `cnf.x5t#S256`. The RS MUST NOT validate the cert's trust chain — this is a proof-of-possession check, not PKI.
- **FAPI 2.0 mandate:** all access tokens must be sender-constrained using either mTLS (RFC 8705) or DPoP (RFC 9449).
- **Two client auth modes:** PKI mode (AS validates the cert chain to a trusted CA, matches subject DN/SAN) and self-signed mode (AS matches the presented cert against the client's registered JWK `x5c`).
- **Cert rotation invalidates bound tokens** — treat it like expiry and obtain fresh tokens via refresh.
- **Not practical in browsers** — use DPoP for SPA/native clients.
