# How does RHBK function as an identity broker?

**RHBK acts as an identity broker — an intermediary that delegates authentication to external identity providers (social, OIDC, SAML v2.0) and then issues its *own* token to the client. Applications only ever integrate with RHBK; they never see the external protocol.**

## The broker flow

1. **User requests a protected resource** in a client app.
2. **Client redirects to RHBK** for authentication.
3. **RHBK displays the login page** with configured IdP options (or auto-redirects to a [[identity-brokering|default IdP]] via the Identity Provider Redirector authenticator).
4. **User selects an IdP** — social (Google, Facebook, GitHub, etc.), OIDC/OAuth v2.0, or SAML v2.0.
5. **RHBK issues an auth request** to the external IdP; the user's browser is redirected there.
6. **User authenticates** at the external IdP.
7. **External IdP redirects back** to RHBK with a security token (auth code + tokens for OIDC; SAML assertion for SAML).
8. **RHBK validates the response** — checks signature, issuer, audience, expiry. For OIDC, the realm can authenticate using a client secret, the realm private key, or a Signed JWT. For SAML, it validates the assertion against the IdP's Entity ID, SSO/SLO URLs, and signing certificates.
9. **RHBK imports/links the user** — if new, it creates a user via identity federation (governed by the First Login Flow); if existing, it prompts account linking. Sync modes (legacy/import/force) control how attributes are merged.
10. **RHBK issues its own token** to the client. The client uses only this RHBK token; it never holds the external IdP's token (unless retrieved via the Identity Brokering API).

## Key capabilities

- **Provider types:** social (Google, Facebook, GitHub, GitLab, Bitbucket, LinkedIn, Microsoft, PayPal, OpenShift, Stack Overflow, Twitter), OIDC/OAuth v2.0, SAML v2.0.
- **Client-suggested IdP:** pass `kc_idp_hint=<alias>` to skip the IdP selection page and go directly to a specific provider.
- **Store external tokens:** V1 (enabled by default) stores the external IdP's token in the DB; V2 (preview, `--features=identity-brokering-api:v2`) stores it in the session and requires confidential client auth via POST.
- **Client-initiated account linking:** authenticate an existing user, then use `kc_action=idp_link:<alias>` to link their account to an external IdP without logging out.
- **First Login Flow / Post Login Flow:** custom authentication flows that run after the external IdP returns, enabling additional steps (attribute mapping, email verification, TOTP, etc.).

## Contradictions / caveats

- Instagram broker is deprecated for removal (prefer Facebook). Enable with `--features=instagram-broker` (inferred — specific to 26.4+ reference).
- Identity Brokering API V2 is Technology Preview and disabled by default — not fully supported.
