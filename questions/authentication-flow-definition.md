# What is an authentication flow in Keycloak and what does it contain?

An **authentication flow** is an ordered container of executions (authenticators, screens, and actions) and sub-flows that runs during login, registration, reset-credentials, first-broker-login, and other RHBK workflows ([ref:rhbk-26-0-configuring-authentication-server-administration-guide.md:155]).

## What it contains

1. **Executions** — individual authenticators or actions, either automatic (e.g. Cookie check) or interactive (e.g. Username Password Form). Each execution can carry an optional authenticator reference value for the `amr` OIDC claim.

2. **Sub-flows** — nested flow containers (type `basic` or `form`) inside a top-level flow.

3. **Requirement types** on each element:
   - **Required** — must succeed sequentially; flow terminates on failure.
   - **Alternative** — only one Alternative must succeed; ignored if a sibling Required exists.
   - **Disabled** — skipped, does not count.
   - **Conditional** (sub-flows only) — acts as Required if all condition executions evaluate true, else Disabled.

4. **Bindings** — top-level flows are bound to a context: Browser, Direct Grant, Reset Credentials, Registration, First Broker Login, or Client Authentication.

5. **Built-in flows** — Browser, Registration, Reset Credentials, First Broker Login, etc. These are immutable but duplicable; you modify their requirement types or duplicate and edit.

6. **The default Browser flow**: `Cookie` (Alternative) → `Kerberos` (disabled) → `Identity Provider Redirector` (Alternative) → `Forms` sub-flow (Username Password Form Required → Conditional OTP sub-flow gated by `Condition - User Configured`).
