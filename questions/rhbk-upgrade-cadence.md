# RHBK — באיזו תדירות לשדרג?

**ל-RHBK אין מדיניות "שדרג כל X חודשים" רשמית, אבל מחזור השחרורים וההמלצות בשטח ברורים.**

## מחזור שחרורים

- **גרסאות מינור** (major.minor — 26.0 → 26.2 → 26.4 → 26.6): יוצאות בערך **כל רבעון** (3–4 חודשים). הגרסה הנוכחית (נכון ליולי 2026) היא 26.6. קודמתה: 22.x, 24.x — קפיצת major כל ~שנה עד שנתיים (inferred — ניתוח תבנית הגרסאות בארכיון).
- **גרסאות פטש'** (z-stream — 26.6.0 → 26.6.1): יוצאות בתדירות משתנה לפי צורך — CVEs, באגים קריטיים, עדכוני תלויות (Quarkus, Infinispan). למשל, 26.4 הגיעה ל-26.4.12, 26.2 ל-26.2.15 (extracted: rhbk-26-4-updates-for-26-4-12, rhbk-26-2-updates-for-26-2-15-sp1).

## ההמלצה בשטח

1. **גרסת פטש' — להחיל מייד.** רוב הפטש'ים הם תיקוני CVEs. מגרסה 26.6, פטש'ים תומכים ב-rolling update (אפס השבתה) — אין סיבה לדחות (extracted: rhbk-26-6-newfeatures `§2.3.7`; rhbk-26-6-rolling-updates).
2. **גרסה מינור — לשדרג תוך 1–2 רבעונים מ-GA.** דחייה מעבר לכך פירושה לפספס תיקונים שמגיעים רק במינור (למשל: Infinispan 16, zero-downtime rolling, fine-grained admin permissions). גרסאות מינור דורשות recreate downtime (או בחלון תחזוקה) (extracted: rhbk-26-6-upgrading `§3.1`; rhbk-26-6-multi-cluster-introduction `§3.22.1`).
3. **גרסה major — אל תידרדר הרחק.** אם אתה עדיין על 22.x או 24.x, קפיצה ל-26.6 כרוכה ברצף של המרות — תכנן מסלול הדרגתי (inferred: משתמע מ-rhsso-to-rhbk-migration ומאזכורי upgrade paths בהנחיות השדרוג).
4. **Multi-site HA:** שדרוגי מינור/major של RHBK, Data Grid ו-DB דורשים downtime; מומלץ לבצע את כולם באותו חלון תחזוקה (extracted: rhbk-26-6-multi-cluster-introduction `§3.22.3`).

## קווים מנחים לפעולה

| מה | מתי | איך |
|---|---|---|
| patch (26.6.0 → 26.6.1) | עם פרסום | rolling update (zero-downtime) |
| minor (26.4 → 26.6) | תוך 1–2 רבעונים | recreate → downtime |
| major (24.x → 26.x) | תוך שנה מ-GA | recreate, תכנון מסלול |
| multi-site upgrade | בחלון תחזוקה אחד | site offline → upgrade → synchronize |
