# LDAPS Truststore and AD-Side Settings for Keycloak Federation

**Where to configure the truststore when federating Active Directory users into Keycloak over LDAPS, and what AD-side settings affect the connection.**

## Truststore configuration

### Bare-metal / `kc.sh`

Two equivalent methods described in the Server Configuration Guide (`rhbk-26-0-keycloak-truststore.md:21-33`):

1. **`conf/truststores/` directory** — drop PEM or unencrypted PKCS12 (`.p12`/`.pfx`) files into `conf/truststores/` or any subdirectory. Scanned recursively on startup and merged into the JVM default truststore.
2. **`--truststore-paths` option** — specify files or directories:
   ```
   bin/kc.sh start --truststore-paths=/opt/truststore/domain-ca.pem
   ```
   Accepts comma-separated file or directory paths. Absolute paths recommended.

The "Use Truststore SPI" setting on the LDAP provider page (which historically toggled truststore usage per provider) is **deprecated** in RHBK 26.x and should be left as `Always`.

### Operator / OpenShift

Use `spec.truststores` on the `Keycloak` CR (`rhbk-26-6-advanced-configuration.md`):

```yaml
spec:
  truststores:
    ad-truststore:
      secret:
        name: ad-ca-secret
```

The Secret must contain PEM or PKCS12 files and be in the same namespace as the CR. Cluster CAs (`service-ca.crt`, `ca.crt`) are added automatically. The Operator polls for changes and performs a rolling restart.

## AD-side settings that matter

### 1. DC certificate for LDAPS

The domain controller serving LDAPS (port 636 or 3269 for GC) needs a certificate that:
- Has the **Server Authentication** EKU (`1.3.6.1.5.5.7.3.1`)
- Carries the DC's **FQDN** in the Subject CN or SAN DNS entry
- Is issued by a CA whose root certificate you add to the RHBK truststore (above)
- Has its private key in the Local Computer or NTDS store with the Schannel CSP

If the DC cert is self-signed or issued by an internal AD CS CA, add the CA root (not the DC cert itself) to the RHBK truststore.

### 2. LDAP signing and channel binding

Windows Server defaults have hardened over time (`ldap-signing-and-channel-binding.md:42-47`):

| Version | LDAP signing default | Channel binding default |
|---|---|---|
| WS 2019 and earlier | Optional (unsigned accepted) | Never |
| WS 2025 (new install) | Required | When supported |

Keycloak's JNDI LDAP stack supports both SASL signing and channel binding tokens (CBTs), but if AD enforces these and the Java LDAP client doesn't negotiate them correctly, connections may fail. Symptoms appear as **Event ID 3039** (client lacks CBT support) or **3040** (CBT mismatch) on the DC.

**Recommended approach** (`ldap-signing-and-channel-binding.md:77-82`):
1. Set signing to "Negotiate signing" and channel binding to "When supported" (audit mode)
2. Monitor Events 2887 (unsigned bind) and 3039 (no CBT) to confirm Keycloak is compliant
3. Then enforce: signing → "Require signing", channel binding → "Always"

### 3. Use immutable `objectGUID` as the stable identifier

If using identity brokering (AD as an external OIDC/SAML IdP), the Username Template Importer mapper defaults to mutable attributes like `sAMAccountName`, `userPrincipalName`, or `cn`. When AD renames an account, the federated link breaks and users see a "merge accounts" prompt (`doc-7128299.md:22-26`).

**Fix:** Change the IdP mapper template to `${ATTRIBUTE.objectGUID}` (binary, must be base64-encoded; the mapper handles this).

For User Federation (the built-in LDAP provider under User Federation → Add LDAP providers), the user link is DN-based, which is also mutable. Use an `objectGUID`-based custom attribute mapper to stabilize the link across renames (see [[ad-idp-link-loss-objectguid]]).
