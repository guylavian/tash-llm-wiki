# Which built-in policy types can you use in Keycloak fine-grained authorization?

Keycloak (RHBK) provides **9 built-in policy types** in Authorization Services, each implementing a different access control model. Every policy also has a **Logic** field (Positive/Negative) that applies after the conditions are evaluated.

## Built-in types

1. **User** — grant to a named set of users (`rhbk-26-6-policy-overview.md:27-28`, extracted).
2. **Role** — grant if the requester has any of the listed realm/client roles; roles can be marked **Required** (all required roles must be held) (`rhbk-26-6-policy-overview.md:39-65`, extracted).
3. **Group** — grant to members of selected groups; **Extend to Children** includes subgroups (`rhbk-26-6-policy-overview.md:216-235`, extracted).
4. **Client** — grant to a set of clients (`rhbk-26-6-policy-overview.md:203-215`, extracted).
5. **Client scope** — grant if the requesting client holds any (or all, when marked **Required**) of the listed client scopes (`rhbk-26-6-policy-overview.md:236-256`, extracted).
6. **Regex** — match a value from the current identity against a regex pattern (`rhbk-26-6-policy-overview.md:257-273`, extracted).
7. **Time** — grant only within a Start/Expire window, optionally repeating by day/month/year/hour/minute (all conditions AND-ed) (`rhbk-26-6-policy-overview.md:151-176`, extracted).
8. **JavaScript** — rule-based policy using the Evaluation API (`$evaluation`), supporting ABAC, RBAC, and mixed modes; deployed as JAR files via JavaScript Providers (`rhbk-26-6-policy-overview.md:66-150`, extracted).
9. **Aggregated** — combine existing policies with a decision strategy (Unanimous/Affirmative/Consensus); circular references are rejected (`rhbk-26-6-policy-overview.md:177-202`, extracted).

## Key distinctions

- **Per-policy Logic** (Positive → apply result as-is; Negative → negate it) is separate from a permission's [[decision-strategies|Decision Strategy]] — do not conflate them (`rhbk-26-6-policy-overview.md:274-276`, extracted).
- **Fetch Roles** on Role policies ignores the token and reads roles server-side — relevant when tokens carry minimized claims (`rhbk-26-6-policy-overview.md:56`, extracted).
- **Groups Claim** on Group policies lets you specify the token claim holding group names, falling back to realm group membership (`rhbk-26-6-policy-overview.md:225-226`, extracted).
- JavaScript policies **cannot be uploaded** via Admin Console by default — they must be deployed as JAR files (`rhbk-26-6-policy-overview.md:70-73`, extracted).
