# What is the HA cross-site deployment model for Red Hat Build of Keycloak?

**RHBK's documented cross-site HA model is a two-site Active/Passive topology — not Active/Active.** It is designed to tolerate a full OpenShift cluster failure and bridge non-transparent networks.

## Architecture overview

Two **independent** RHBK deployments run in two separate OpenShift clusters/sites, connected by a low-latency network (`< 10 ms` RTT required, `< 5 ms` suggested). The model uses:

- **Synchronously replicated database** across both sites — both sites connect to the same DB writer instance (e.g. Aurora PostgreSQL multi-AZ) (`references/high-availability.md:125-128`).
- **External Red Hat Data Grid (RHDG) per site** — each site has its own Data Grid cluster; the two clusters form a Cross-DC connection using JGroups over TLS via Data Grid's Gossip Router (`references/high-availability.md:128-129`, `references/high-availability.md:189`). RHBK connects to its local Data Grid as a remote store via `cache-remote-host`/`cache-remote-port`/`cache-remote-username`/`cache-remote-password` (`ha-cross-site:53-57` *extracted*). On change, the DB is updated and an invalidation message is sent to the other site through the **`work`** cache (`references/high-availability.md:127-129` *extracted*).
- **External load balancer** — the tested blueprint uses AWS Global Accelerator with a static anycast IP, routing to an NLB per site that health-checks the `multi-site`-feature-exposed `/lb-check` endpoint. An automated fencing Lambda disables a non-responding site on Data Grid cross-site connectivity loss (`ha-load-balancer-failover:10-13` *extracted*).
- **`multi-site` feature flag** must be enabled on the `Keycloak` CR (`ha-cross-site:57` *extracted*, `rhbk-ha-architectures:76-77` *extracted*).

## Consistency model

The architecture **prioritizes consistency over availability**: synchronous DB + synchronous Data Grid replication means the next request never returns stale data regardless of which site serves it. An asynchronous design would survive network failures more gracefully but risks stale data (e.g. old passwords accepted after a password change) (`references/high-availability.md:178-183` *extracted*).

## Failover characteristics

- **RPO:** no data loss (when not already degraded from a prior failure) (`references/high-availability.md:165-168` *extracted*).
- **RTO:** site failover `< 2 min`; some failure/switchover scenarios incur **up to 5 min** downtime (`rhbk-ha-architectures:45-46` *extracted*).
- After certain failures, **manual intervention** is required to restore redundancy — including a full Data Grid re-sync via `clearcache` commands on the offline site (`site-synchronization:19-32` *extracted*).

## Limitations

- **Two sites only** — tested and supported only with exactly two sites (3+ is unsupported) (`references/high-availability.md:148-149` *extracted*).
- **Active/Passive only** — Active/Active is not the documented supported model (`rhbk-ha-architectures:74-75` *extracted*).
- Out-of-sync sites are hard to monitor and need a manual full state transfer that stresses the system (*inferred* from `site-synchronization`).
- Requires **Data Grid 8.5.3+** for external deployments (`references/high-availability.md:144` *extracted*; some earlier chapters state 8.5.2 — verify per version).
- Naming changed by version: 26.0/26.2 call this "**multi-site**"; 26.4/26.6 rename to "**multi-cluster**" — the topology is unchanged (`rhbk-ha-architectures:61-64` *extracted*).
