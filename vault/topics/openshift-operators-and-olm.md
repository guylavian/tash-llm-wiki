# OpenShift Operators, OLM & Machine Config — Overview

**"Operator" in an OpenShift cluster can mean three different things, each with its own controller and its own CRDs — knowing which one a symptom belongs to is most of the triage.**

## 1. The Operator pattern itself
An Operator packages operational knowledge (install, upgrade, failure handling, backup) as software that watches the cluster and reconciles toward a desired state, using CRDs to extend the Kubernetes API so a custom resource (e.g. a `MongoDB`) behaves like a native object. This is upstream Kubernetes' extension mechanism, not OpenShift-specific — OpenShift adds the two management layers below on top.

## 2. Platform components — ClusterOperators + the CVO
Every built-in OpenShift platform component (kube-apiserver, network, ingress, authentication, …) reports itself as a [[cluster-operators|ClusterOperator]] with `Available`/`Progressing`/`Degraded` conditions. The **Cluster Version Operator (CVO)** applies release manifests in ordered runlevels and won't advance a runlevel until every ClusterOperator in it is `Available=True`, `Degraded=False`, and at the target version. Platform ClusterOperators have **no Subscription object** — that's the OLM side.

## 3. Application Operators — [[operator-lifecycle-manager|OLM]]
User-installed Operators (from OperatorHub or a custom catalog) are managed by OLM through `CatalogSource` → `Subscription` → `InstallPlan` → `ClusterServiceVersion` (CSV), with `OperatorGroup` controlling namespace multitenancy via install modes (`OwnNamespace`/`SingleNamespace`/`MultiNamespace`/`AllNamespaces`). Subscription status conditions (`CatalogSourcesUnhealthy`, `InstallPlanFailed`, `ResolutionFailed`, …) are the first diagnostic stop for "an Operator won't install/upgrade" — distinct from ClusterOperator Degraded, which is the CVO/platform side.

## 4. Node-level day-2 — [[machine-config|MachineConfig / MCO]]
The Machine Config Operator applies `MachineConfig` objects (rendered per `MachineConfigPool`) to RHCOS nodes via the on-node Machine Config Daemon, and detects **configuration drift** (on-disk state diverging from the rendered config) — marking the node and pool `Degraded` if drift is found. MCO manifests apply near the *end* of a CVO runlevel sequence, so "control plane updated" and "all nodes updated" are genuinely different milestones in time, not the same event (inferred: direct consequence of runlevel ordering described in `kb:updating-4-22-how-updates-work`).

## How the three interact during an upgrade
1. CVO applies platform-component manifests in runlevel order, gating on each ClusterOperator's conditions.
2. OLM-managed application Operators upgrade independently on their own Subscription/channel cadence — not gated by CVO runlevels.
3. MCO manifests land near the end of the CVO's runlevel sequence, then nodes drain/update/reboot one at a time — the *last* phase to finish, often well after the cluster "reports as updated."

## Triage checklist
| Symptom | Look at | Page |
|---|---|---|
| `oc get co` shows Degraded | CVO/ClusterOperator conditions, not app-level logs | [[cluster-operators]] |
| Operator install/upgrade stuck | `oc get subs`, InstallPlan/CatalogSource conditions | [[operator-lifecycle-manager]] |
| Node shows Degraded/NodeDegraded | MachineConfig drift, `oc describe node` annotations | [[machine-config]] |
| "Upgrade is stuck" broadly | Check CVO runlevel first (ClusterOperators), then MCO node rollout — they finish at different times | [[cluster-operators]], [[machine-config]] |
