# User sessions remain in PostgreSQL database after logout or expiration in RHBK

User sessions remain in PostgreSQL database after logout or expiration in RHBK
Environment
- Red Hat Build of Keycloak (RHBK)
- 26.x
Issue
- Delay in database cleanup for expired sessions in Red Hat Build of Keycloak 26.x
- Expired user sessions are not immediately deleted from the database in RHBK 26.x
- Resolving stale session record accumulation in PostgreSQL with RHBK 26.x
Resolution
Option 1: Tune the Cleanup Frequency
If the default 15-minute lag is causing database saturation, make the cleanup task run more frequently and in smaller batches. Add these settings to your conf/keycloak.conf:
Properties
# Reduce cleanup interval from 15 mins to 2 or 5 mins (value in seconds)
spi-user-sessions-jpa-expiration-cleanup-interval=300
# Adjust the number of records deleted in a single transaction
# For 1,500 sessions/min, a batch size of 3000-5000 is recommended
spi-user-sessions-jpa-expiration-batch-size=5000
Option 2: Disable Persistent User Sessions
If you do not require user sessions to survive a Keycloak cluster restart, you can move session management entirely to RAM (Infinispan). This completely eliminates the database load for session management:
Start Keycloak with the following flag:
--features-disabled=persistent-user-sessions
If all Keycloak nodes restart simultaneously, all users will be logged out.
Option 3: Realm Configuration Optimization
Ensure that your session timeouts are not excessively long. Shorter timeouts reduce the volume of data the background task must process:
Navigate to Realm Settings > Sessions
Align SSO Session Idle and SSO Session Max to business requirements.
Note: Using uniform values across different session settings (Idle vs. Max) helps the cleanup task query the database more efficiently.
Option 4: PostgreSQL Maintenance
For high-volume environments (1,500+ sessions/min), the database must be tuned to handle the high row-deletion rate:
Increase the frequency of Autovacuum on the user_session and client_session tables.
Ensure indexes exist on the max_expiration and timestamp columns of the user_session table to accelerate the background cleanup queries.
Root Cause
The behavior is caused by the asynchronous cleanup architecture of Red Hat Build of Keycloak (RHBK). Starting with version 25/26, Persistent User Sessions are enabled by default, meaning the database (PostgreSQL) is the primary store for session state.
Decoupling of Cache and Database: When a session expires (based on Realm "SSO Session Idle" or "Max" settings), it is immediately evicted from the Infinispan in-memory cache. This results in the session instantly disappearing from the Admin UI.
Lazy Deletion Logic: To maintain high performance—especially in environments with high session churn (e.g., 1,500 sessions/minute)—Keycloak does not execute a synchronous DELETE query the exact millisecond a session expires. Doing so would cause excessive database lock contention and connection pool exhaustion.
Scheduled Cleanup Task: Instead, a background task called the UserSessionPersister runs periodically (defaulting to every 900 seconds / 15 minutes). This task performs a batch deletion of all expired or explicitly terminated sessions. This creates a predictable "lag" where sessions may remain in the database for 10–15 minutes after they have vanished from the UI.
Diagnostic Steps
To confirm if your environment is experiencing expected asynchronous cleanup or a performance bottleneck, perform the following:
Compare UI vs. Database Counts:
Check the "Sessions" tab in the Admin Console. Then, run the following SQL query in PostgreSQL:
SELECT count(*) FROM user_session;
If the database count is significantly higher than the UI count, sessions are awaiting the next cleanup cycle.
Identify Expired Records:
Run this query to find rows that have exceeded their lifespan but have not yet been deleted by the background task:
SQL
-- Check for sessions past their absolute Max Lifespan
SELECT count(*) FROM user_session
WHERE max_expiration < (EXTRACT(EPOCH FROM NOW()));
Monitor Database Connection Pool:
Check Keycloak logs for Active count exceeds max-size or Timeout waiting for idle connection. High-traffic environments (1,000+ sessions/min) may see pool saturation if the cleanup task tries to delete too many rows at once in a single large transaction.
Check Table Bloat:
In PostgreSQL, check for "dead tuples" in the user_session and client_session tables. High churn without aggressive auto-vacuuming can lead to table bloat, slowing down the cleanup task.
