## native-app-oauth

- **RULE (§8.12):** Native apps MUST NOT use embedded user-agents (webviews); use an external user-agent — system browser or in-app browser tab (§4, §6). **ANTI-PATTERN:** opening the login page in a `WebView` / `UIWebView` / `WKWebView` / Android `WebView` inside the app. **SYMPTOM:** federated IdPs refuse the embedded agent ("disallowed_useragent", "403 disallowed_useragent: This user-agent is not permitted"); no SSO/cookie reuse with system browser; host app can scrape keystrokes/cookies (credential phishing risk flagged in security review).

- **RULE (§6, §6.1):** Use the authorization code grant; the response is captured by the external agent and handed back to the app via the registered redirect. **ANTI-PATTERN:** scripting/auto-submitting the login form, or screen-scraping the auth page. **SYMPTOM:** breaks on UI/flow changes; MFA/IdP redirects fail; brittle login.

- **RULE (§6, §8.1):** Public native clients MUST use PKCE and servers MUST support it; servers SHOULD reject native-app auth requests without PKCE (§8.1). **ANTI-PATTERN:** plain code flow with no `code_challenge`/`code_verifier`, relying on a shared secret instead. **SYMPTOM:** "PKCE code verifier not specified" / "Missing parameter: code_challenge"; code-interception attack possible when a malicious co-installed app claims the same scheme.

- **RULE (§8.2):** Implicit flow is NOT RECOMMENDED for native apps. **ANTI-PATTERN:** `response_type=token` to get an access token straight in the redirect fragment. **SYMPTOM:** no refresh token; token exposed in redirect; cannot be PKCE-protected — security review rejection.

- **RULE (§7, §8.4):** Servers MUST offer at least three redirect-URI types — private-use scheme, loopback IP, claimed `https` — and MUST require registration of the complete redirect URI (incl. path) with exact match; only the port may vary for loopback. **ANTI-PATTERN:** prefix/wildcard matching of redirect URIs, or unregistered redirects. **SYMPTOM:** "Invalid redirect_uri" / "invalid_request: Invalid parameter: redirect_uri"; open-redirect finding.

- **RULE (§7.1, §8.4):** Private-use URI scheme MUST be a reverse-DNS name under the app's control (e.g. `com.example.app:/oauth2redirect/...`, per RFC 7595 §3.8); servers SHOULD reject any scheme without a "." (§8.4). **ANTI-PATTERN:** generic schemes like `myapp://` or `oauth://` that any app can also register. **SYMPTOM:** scheme collision — wrong app receives the code; store-level squatting; server rejects the no-dot scheme.

- **RULE (§7.2):** Claimed `https` redirect (verified app-link / universal link) SHOULD be preferred where available because the OS guarantees the destination app's identity. **ANTI-PATTERN:** defaulting to a custom scheme on platforms that support verified https claims. **SYMPTOM:** another app can hijack the custom-scheme redirect; weaker than verified https.

- **RULE (§7.3, §8.3):** Loopback redirect uses `http://127.0.0.1:{port}` or `http://[::1]:{port}`; server MUST allow any port at request time; `http` is acceptable (never leaves device); listen on loopback interface only, open the port only for the request; `localhost` is NOT RECOMMENDED (use the literal IP). **ANTI-PATTERN:** registering a fixed port and rejecting others; binding to `0.0.0.0`/all interfaces; using `localhost`; assuming only IPv4. **SYMPTOM:** "redirect_uri port mismatch"; port-already-in-use; other local processes/devices reach the listener; IPv6-only host fails to bind.

- **RULE (§8.4, §8.5):** Native apps MUST be registered/classified as public clients and the client type recorded; requiring a static shared secret is NOT RECOMMENDED, and if present the server MUST NOT treat it as proof of identity (secret shipped in the app binary is not confidential). **ANTI-PATTERN:** embedding a `client_secret` in the app and treating it as confidential auth. **SYMPTOM:** secret extracted from APK/IPA by any user; "invalid_client" once the leaked secret is rotated; false sense of client authentication.

- **RULE (§8.9):** Include a high-entropy random `state` and reject auth responses whose state does not match a pending request (CSRF / cross-app request forgery). **ANTI-PATTERN:** omitting `state` or not validating it. **SYMPTOM:** session/code injection; "state mismatch" only when correctly implemented — silent acceptance of forged responses when not.

- **RULE (§8.10):** Use a distinct redirect URI per authorization server (e.g. vary the path); the app MUST store the request's redirect URI with the session/state and MUST verify the response arrived on an exactly matching URI (mix-up defense). **ANTI-PATTERN:** one shared redirect path for multiple IdPs; not pinning the redirect to the session. **SYMPTOM:** IdP mix-up attack — code/token sent to the wrong AS; response accepted on the wrong endpoint.
