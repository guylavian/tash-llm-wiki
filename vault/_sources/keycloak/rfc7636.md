# RFC 7636 — Proof Key for Code Exchange (PKCE)

Threat mitigated (§1): the **authorization code interception attack** — a malicious app on the same device (custom-scheme / loopback redirect) grabs the auth code, then redeems it. PKCE binds the code to a per-request secret only the legit client knows.

## pkce

### code_verifier generation (§4.1, §7.1)
- **RULE**: `code_verifier` is a high-entropy random string, 43–128 chars from the unreserved set `[A-Z][a-z][0-9]-._~` (§4.1). RECOMMENDED: 32 random octets → base64url → 43 chars; min 256 bits entropy from a CSPRNG (§4.1, §7.1).
  - **ANTI-PATTERN**: deriving the verifier from a timestamp, counter, `Math.random()`, GUID, or a static/per-install constant; or a short verifier under 43 chars.
  - **SYMPTOM**: works in tests but codes get hijacked in the wild; verifier guessed/brute-forced; server rejects with `invalid_request` for a verifier outside 43–128 / bad charset.

### code_challenge methods: plain vs S256 (§4.2, §4.3)
- **RULE**: `code_challenge_method` is `plain` or `S256`. **If the client can do S256 it MUST use S256** (S256 is mandatory-to-implement on servers) (§4.2). `plain` only when S256 is impossible AND the server is known to support plain via out-of-band config.
  - **ANTI-PATTERN**: defaulting to `plain` for convenience; or sending the raw verifier as the challenge while still capable of SHA-256.
  - **SYMPTOM**: with `plain` the challenge equals the verifier and travels in the auth request — interception of the request leaks the secret, defeating PKCE; security review / scanner flags "plain PKCE in use."
- **RULE**: `code_challenge_method` is OPTIONAL and **defaults to `plain` if absent** (§4.3).
  - **ANTI-PATTERN**: omitting the method while sending an S256 hash as the challenge.
  - **SYMPTOM**: server treats challenge as `plain`, compares the S256 hash literally against the verifier → `invalid_grant` at token exchange.

### S256 transform (§4.2, §3)
- **RULE**: `code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))`; base64url is URL-safe with **all trailing `=` padding stripped** (§4.2, §3).
  - **ANTI-PATTERN**: standard base64 (`+`/`/`) instead of base64url (`-`/`_`); leaving `=` padding; hashing UTF-8/bytes other than the ASCII verifier; double-encoding.
  - **SYMPTOM**: challenge/verifier never match → `invalid_grant` ("PKCE verification failed") at the token endpoint on every login.

### authorization endpoint binding (§4.3, §4.4, §4.4.1)
- **RULE**: server MUST associate `code_challenge` + `code_challenge_method` with the issued authorization code (§4.4), and MUST NOT expose `code_challenge` so other entities can extract it (§4.4).
  - **ANTI-PATTERN**: not persisting the challenge with the code; reflecting it back to the client/UA where an attacker can read it.
  - **SYMPTOM**: no binding to verify against → PKCE silently ineffective; codes still interceptable.
- **RULE**: if PKCE is required and `code_challenge` is missing, or the transform method is unsupported, the authorization endpoint MUST respond `invalid_request` (§4.4.1).
  - **ANTI-PATTERN**: accepting an auth request with no challenge when PKCE is enforced.
  - **SYMPTOM**: `error=invalid_request` ("code_challenge required" / "transform algorithm not supported").

### token endpoint verification (§4.5, §4.6)
- **RULE**: client sends `code_verifier` (REQUIRED when a challenge was used) on the token request (§4.5). Server recomputes: S256 → `BASE64URL(SHA256(ASCII(code_verifier))) == stored code_challenge`; plain → `code_verifier == stored code_challenge`. Equal → proceed; **not equal (or missing verifier) → MUST return `invalid_grant`** (§4.6).
  - **ANTI-PATTERN**: skipping verification; comparing the verifier against the wrong stored value; accepting a token request with no `code_verifier` when a challenge was stored.
  - **SYMPTOM**: legit clients see `invalid_grant` ("PKCE verification failed" / "code_verifier mismatch"); or — worse, silently — attack succeeds because the check was skipped.

### downgrade-attack defense (§7.2)
- **RULE**: clients MUST NOT downgrade to `plain` after attempting S256 (§7.2). An S256 error can only mean a faulty server or a MITM attempting downgrade; `plain` SHOULD NOT be used (compat only), `S256` SHOULD be used (§7.2).
  - **ANTI-PATTERN**: "retry with plain on failure" fallback logic; offering plain as a configurable default.
  - **SYMPTOM**: MITM forces plain, harvests the verifier from the request, and replays the intercepted code — interception protection defeated.

### no salt, no runtime negotiation (§7.3, §6.2, §4.2)
- **RULE**: do not salt the verifier — its entropy alone resists brute force (§7.3). No dynamic discovery of methods; the IANA registry seeds only `plain` + `S256` (§6.2); clients learn server support out-of-band (§4.2).
  - **ANTI-PATTERN**: adding a salt/pepper scheme; probing the server at runtime to "detect" S256 support.
  - **SYMPTOM**: over-engineered, non-interoperable flow; verifier/challenge mismatches; wasted round-trips.
