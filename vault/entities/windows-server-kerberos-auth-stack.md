# Windows Server Kerberos / authentication stack

**Windows Server implements the Kerberos version 5 protocol as its default
domain authentication mechanism, integrated with Winlogon single sign-on and
backed by the domain controller's Key Distribution Center (KDC).**

## Body

The Kerberos client is a **Security Support Provider (SSP)**, reachable through
the **Security Support Provider Interface (SSPI)**; initial sign-on is integrated
with **Winlogon**. The **KDC** runs on every domain controller and uses the
domain's **Active Directory Domain Services database** as its account store — AD
DS is required for a default Kerberos implementation within a domain or forest.

**Why Kerberos over NTLM:**
- **Delegated authentication** — a front-end service can act on behalf of the
  client's identity when calling back-end services (constrained/unconstrained
  delegation), which NTLM/Kerberos-local impersonation alone doesn't cover for
  multi-hop distributed apps.
- **Single sign-on** — once authenticated via Winlogon, Kerberos manages
  credentials transparently across the whole forest.
- **More efficient server authentication** — servers validate renewable session
  tickets locally instead of round-tripping to a domain controller for every
  client (a DC round-trip is needed only to validate a Privilege Attribute
  Certificate, PAC).
- **Mutual authentication** — either end of a connection can verify the other's
  identity; NTLM assumed servers were genuine and couldn't do this.
- **Interoperability** — Microsoft's Kerberos v5 implementation follows
  IETF standards-track specifications, so it interoperates with non-Windows
  Kerberos realms.

**Encryption types:** starting with **Windows Server 2025**, Kerberos **no longer
honors** the legacy `SupportedEncryptionTypes` `REG_DWORD` at
`HKEY_LOCAL_MACHINE\CurrentControlSet\Control\Lsa\Kerberos\Parameters` — Microsoft
now requires Group Policy for configuring allowed encryption types.

## Contradictions / caveats

This entity covers Windows Server's Kerberos **implementation and protocol
behavior** in general; forest/domain-specific mechanics (SPN/UPN uniqueness
enforcement, `krbtgt` rotation, time-skew troubleshooting against the PDC
Emulator) live in the `active-directory` domain's dedicated pages — treat this
page as the protocol layer those AD-specific pages sit on top of.
