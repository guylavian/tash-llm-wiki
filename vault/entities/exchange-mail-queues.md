# Exchange Mail Queues

**A queue is a temporary holding location for a message waiting on the next
processing/delivery stage; Exchange 2016/2019/SE persists all queue types in a
single Extensible Storage Engine (ESE) database per transport server.**

## Body

Queues exist on both Mailbox servers and Edge Transport servers ("transport
servers"), and are managed via the Exchange Management Shell or **Queue Viewer**
in the Exchange Toolbox (`exchange-exchange-servertoc-p1721-1760.md:1339-1348`).
Five types
(`exchange-exchange-servertoc-p1721-1760.md:1350-1400`):

- **Submission queue** — messages accepted by the Transport service but not yet
  categorized. Exactly one per server; the categorizer pulls from it, determines
  the recipient's route, then moves the message to a delivery queue or the
  Unreachable queue.
- **Delivery queues** — hold messages en route to a destination; created
  dynamically per unique destination (`NextHopSolutionKey` on Mailbox servers, or
  per destination SMTP domain/smart host on Edge Transport servers) and deleted
  once empty past `QueueMaxIdleTime` (default 3 minutes, on `Set-TransportService`).
- **Poison message queue** — isolates messages judged harmful after a server/service
  crash. Typically empty (doesn't even show in queue tools when empty); messages
  here are **never** auto-resumed or expired — an admin must act. Exactly one per
  server.
- **Shadow queues** — hold redundant in-transit copies for shadow redundancy.
- **Unreachable queue** — messages that can't be routed, usually from a
  configuration change that broke the routing path. Exactly one per server.

The queue database defaults to
`%ExchangeInstallPath%TransportRoles\data\Queue`
(`exchange-exchange-servertoc-p1721-1760.md:1401-1406`).

**Diagnosing stuck mail flow starts here.** A permanent NDR from a delivery queue
carries an enhanced status code: `4.4.7` ("Message delayed"/"Queue expired") points
at Send-connector routing misconfiguration (wrong DNS-vs-smart-host routing, HELO
FQDN mismatch, SPF issues) or a stopped Mailbox Transport Delivery service on the
destination; `5.1.1` ("User unknown" / `RESOLVER.ADR.ExRecipNotFound`) means the
recipient address is wrong or stale (often a recreated mailbox plus an Outlook
autocomplete cache holding an old X.500/LegacyExchangeDN entry)
(`exchange-exchange-servertoc-p1841-1880.md:485-547`). A Receive connector rejecting
a relay attempt returns `550 5.7.1 Unable to relay`
(`exchange-exchange-servertoc-p1561-1600.md:1879-1893`) — check you're hitting the
right connector, the source host is permitted, and the connector's permission
groups.

## Contradictions / caveats

None — the three notes describe the same queue model consistently across Exchange
2016/2019/SE.
