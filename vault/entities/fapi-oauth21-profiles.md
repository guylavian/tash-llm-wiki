# FAPI & OAuth 2.1 Client Profiles

**Built-in RHBK Client Policy profiles that make the authorization server enforce
FAPI 1/2 and OAuth 2.1 conformance on clients.**

RHBK verifies the authorization-server-side requirements of these specs; the
**adapters do not** validate FAPI/OAuth-2.1/DPoP on the client side, so app-side
checks may still be needed.

## FAPI profiles
Link Client Policies to global profiles available in every realm:
- `fapi-1-baseline` — includes the `pkce-enforcer` executor (requires PKCE with
  `S256`).
- `fapi-1-advanced`.
- `fapi-2-security-profile`, `fapi-2-message-signing` — FAPI 2 Draft compliance.
- `fapi-ciba` — CIBA-specific executors; combine with `fapi-1-advanced`.
- For **PAR (Pushed Authorization Request)** it's recommended to use
  `fapi-1-baseline` together with `fapi-1-advanced`.

Regional profiles built on FAPI 1 Advanced are also supported: **Open Finance
Brasil** (stricter — may need the `secure-request-object` executor with
Encryption Required, `PS256` for JWS, `RSA-OAEP` + `A256GCM` for JWE) and
**Australia CDR** (requires PKCE when also using PAR).

## OAuth 2.1 profiles
- `oauth-2-1-for-confidential-client`
- `oauth-2-1-for-public-client`

For OAuth 2.1 public clients, pairing with [[dpop]] is recommended to
sender-constrain tokens.

## TLS
FAPI requires TLS for all interactions, with cipher/protocol constraints.
Configure via `https-protocols` and `https-cipher-suites`; RHBK defaults to
`TLSv1.3`.

## Contradictions / caveats
- The **OAuth 2.1 spec is still a draft**, so the built-in OAuth 2.1 profiles can
  change between RHBK versions.
- FAPI 2 profiles track **Draft** specifications (inferred — the cited chapter states this explicitly only for OAuth 2.1 and Open Finance Brasil; FAPI 2's own draft status is a reasonable but unverified-in-this-chapter extrapolation).
- Detailed Client Policy configuration lives in the Server Administration Guide,
  not this guide.
