# KeycloakSession & retrieving providers

**`KeycloakSession` is the per-request handle passed into every provider; it is how an extension looks up other providers, the current realm/context, and runtime services.**

## Retrieving other providers

Within your provider you obtain collaborators through the session (or the factory's `KeycloakSessionFactory`):

- **Single-implementation type** — one active impl per server:
  `keycloakSession.getProvider(HostnameProvider.class)`.
- **Multiple-implementation type** — pick one by provider id:
  `session.getProvider(EventListener.class, "jboss-logging")`. The second argument is the id returned by that factory's `getId()`.

Some provider types are retrieved with a `ComponentModel` argument, and a few (e.g. `Authenticator`) historically required the `KeycloakSessionFactory`; the docs note implementing your own providers that way may be deprecated in future, so prefer the session-based lookup.

## Context & lifecycle

- The session exposes context such as the current realm: `session.getContext().getRealm()` (e.g. a Theme Selector reading `getLoginTheme()`), and the HTTP request: `session.getContext().getHttpRequest()`.
- Factories receive a session in `create(KeycloakSession ...)`; for User Storage providers the signature is `create(KeycloakSession, ComponentModel)`. See [[user-storage-spi]].
- A single factory instance is shared server-wide and may hold state; provider instances are short-lived (per request/transaction) (inferred — general SPI lifecycle pattern, not spelled out verbatim in the cited chapter).

## Contradictions / caveats

- Stable across RHBK 26.0–26.6. The note that `KeycloakSessionFactory`/`ComponentModel`-based lookups "may be deprecated in the future" is in the 26.6 dev guide — prefer `session.getProvider(...)`.
