# Token Exchange

**Using one token (or credentials) to obtain a different token, via the
`urn:ietf:params:oauth:grant-type:token-exchange` grant on the realm token
endpoint.**

Invoked as a grant on `/realms/{realm}/protocol/openid-connect/token` with
`application/x-www-form-urlencoded` parameters. It's a client endpoint, so the
request must carry client authentication (public: `client_id` form param;
confidential: form `client_id`+`client_secret`, Basic Auth, client JWT, or client
cert).

## Two implementations (RHBK 26.6)
- **Standard token exchange — V2**: fully supported, **enabled by default**.
  Implements the IETF spec for use-case (1) only: exchange an existing RHBK token
  minted for one client for a new token issued to the requesting client. **Both
  clients must be in the same realm.** Recommended going forward.
- **Legacy token exchange — V1**: a **preview, deprecated** feature, off by
  default. Supports all four use-cases (internal→internal, internal→external,
  external→internal, user impersonation) but may not be forward-compatible and
  will eventually be removed. Requires **FGAP v1** (Fine-grained admin
  permissions version 1) because FGAP v2 deliberately has no token-exchange
  permissions. Both V1 and V2 can be enabled together.

## Key form parameters
`grant_type` (required, the token-exchange URN), `subject_token` /
`subject_token_type`, `subject_issuer`, `requested_token_type` (defaults relate
to refresh vs access token), `audience` (target client), `requested_issuer`
(external provider alias), `requested_subject` (impersonation), `scope`.

## Limits
Only **OpenID Connect / OAuth** exchanges are supported — **no SAML** clients or
identity providers. A successful exchange returns HTTP 200 with `access_token`
(and `refresh_token` if a refresh token was requested).

## Contradictions / caveats
- **26.0**: token exchange is a single **Preview** feature, enabled with
  `--features=preview` or `--features=token-exchange`; non-internal flows also
  need `admin-fine-grained-authz`. **26.6**: split into supported V2 + deprecated
  preview V1 as above. State the version when relying on it.
- Legacy V1 setup needs fine-grained admin permissions (a `token-exchange`
  permission on the *target* client) — see Server Administration Guide.
