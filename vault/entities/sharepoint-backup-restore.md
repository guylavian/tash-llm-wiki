# SharePoint Farm Backup & Restore

**`Backup-SPFarm` and `Restore-SPFarm` back up and restore any addressable farm
component — a content database, a service application, or the whole farm — via
PowerShell or the Central Administration UI.**

## Body

### Backing up

```
Backup-SPFarm -Directory <BackupFolder> -BackupMethod <Full | Differential> -Item <FullPathToComponent>
```

Example (backing up a Search service application):

```
Backup-SPFarm -Directory \\server\searchbackup -BackupMethod Full -Item "Farm\Shared Services\Shared Services Applications\Contoso Search Service Application"
```

`-BackupMethod` only governs the **databases**; search indexes are always fully
backed up regardless of the method chosen. Progress is visible on Central
Administration's **Backup and Restore Job Status** page (readiness + current-job
sections, auto-refreshing every 30 seconds); errors land in the **Failure Message**
column there and in `Spbackup.log` at the backup UNC path. Backup/restore run as
SharePoint Timer Service jobs, so a start can lag by several seconds
(`administration-back-up-a-service-application.md:125-127`).

### Finding a backup to restore

Every backup/restore is recorded in `spbrtoc.xml` in the backup directory, one
`<SPHistoryObject>` entry per run carrying an `<SPId>` (the backup ID GUID),
`<SPBackupMethod>`, start/finish times, and the component path. Central
Administration's **Backup and Restore History** page reads and displays this file; it can
also be read directly, or queried with `Get-SPBackupHistory`
(`search-best-practices-of-disaster-recovery-for-search.md:241-266`).

### Restoring

```
Restore-SPFarm -Directory <BackupFolder> -Item "<ServiceApplicationName>" -RestoreMethod Overwrite [-BackupId <GUID>]
```

If `-BackupId` is omitted, the most recent backup in the directory is used.
`-RestoreMethod New` prompts for a target location for every component/database in
the backup — useful when the DR farm's topology/naming doesn't match production.
`-RestoreMethod Overwrite` restores into the existing, matching component and is
typically used only when restoring to the same farm the backup came from
(`search-best-practices-of-disaster-recovery-for-search.md:268-278`).

### Search service application: RPO/RTO and outage tradeoffs

SharePoint supports an **RPO and RTO of one week** for the Search service application
— configuration, analytics, and index freshness can lag by up to a week after a
restore. Because only one backup runs at a time, backup duration sets the practical
RPO floor, and restore duration sets the RTO floor; both grow as the index grows.
During an `Overwrite`-mode restore the service application is **offline** (no queries or
updates); an alternative that avoids the outage is standing up a **new** Search service
application, crawling it fresh, then cutting the association over — at the cost of
roughly double the index/database capacity while both exist
(`search-best-practices-of-disaster-recovery-for-search.md:199,298`). See [[sharepoint-search-service]].

## Contradictions / caveats

The one-week RPO/RTO figure is stated specifically for the **Search** service
application, not content databases generally — do not generalize it to farm-wide
backup SLAs without checking the relevant component's own guidance.
