# SCCM Collections

**A collection groups devices or users into a manageable unit; most Configuration Manager
operations — deployments, client settings, role-based administration scoping, maintenance
windows — target a collection rather than individual resources.**

## Body

Collections appear as **User Collections** and **Device Collections** under **Assets and
Compliance**. Configuration Manager ships built-in collections (e.g. All Systems), but using the
built-ins directly for management tasks is not a best practice — create custom collections that
specifically identify the devices/users a task needs (e.g. an AD OU-based grouping, or a query
for computers missing a specific app).

### Evaluation

**Collection evaluation** updates membership based on the rules you define; the evaluator's
activity is recorded in `colleval.log`. A collection with no schedule of its own is still
re-evaluated whenever the collection that **limits** it updates — a full evaluation cascades to
every collection a changed collection limits, so a deep collection tree can see far more
evaluation activity than a flat one implies.

### Best practices

- Limit how many collections update on a **frequent** schedule — full evaluation is not cheap,
  and it cascades through the limiting-collection graph.
- In a deep collection tree, decrease evaluation frequency the deeper a collection sits, since
  higher-level evaluations already trigger the collections below them.
- The default software update maximum run time is 60 minutes. When Configuration Manager
  calculates whether an update can install, it separately adds a five-minute buffer to that run
  time to account for a restart. So size **maintenance windows** so their remaining duration is
  longer than the update's maximum run time plus that buffer — a window that's too small leaves
  the client unable to install (and thus vulnerable to) the update it was targeted with.

## Contradictions / caveats

The source explicitly calls out that collection guidance can be contradictory: frequent
evaluation is convenient (most functionality depends on current collection membership) but costly
at scale — there's no single "right" schedule, only a performance/business-requirement tradeoff
to make deliberately per collection.
