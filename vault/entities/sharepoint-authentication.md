# SharePoint Server Authentication (Claims, Classic, SAML)

**SharePoint Server authenticates users, apps, and servers; user authentication is
claims-based by default and supports Windows, forms-based, SAML, and (Subscription
Edition) OIDC providers, with the older Windows Classic mode deprecated.**

## Body

### Three authentication surfaces

`security-for-sharepoint-server-authentication-overview.md:23-27` distinguishes three
required-authentication interactions: **users** who access on-premises SharePoint
resources, **apps** that access on-premises SharePoint resources (app authentication —
OAuth 2.0-based, e.g. an external app calling a secured SharePoint resource
(inferred example — the mechanism is `security-for-sharepoint-server-authentication-overview.md`;
the specific IFRAME framing is not itself spelled out there)), and **on-premises servers**
that access on-premises SharePoint resources or vice versa (server-to-server
authentication).

### Claims-based authentication

The result of claims-based authentication is a claims-based security token generated
by the SharePoint Security Token Service (STS). SharePoint Server supports **Windows**,
**forms-based**, **SAML**, and — as of Subscription Edition — **OpenID Connect (OIDC)
1.0** claims providers. Claims-based auth is built on Windows Identity Foundation (WIF)
and standards WS-Federation/WS-Trust/SAML; it converts Windows accounts and
forms-based membership users into claims tokens automatically, and augments them
with extra claims as needed. Multiple authentication providers can be layered on one
zone (see [[sharepoint-web-applications]])
(`security-for-sharepoint-server-plan-user-authentication.md:63-77`).

### SAML token-based authentication

Uses the SAML 1.1 protocol; an environment with ADFS 2.0 (or equivalent) is a SAML
token-based authentication environment. A farm can configure multiple SAML providers,
but a token-signing certificate can only be used once per farm. **Caveat**: when a web
application uses SAML token-based authentication, the SPTrustedClaimProvider class
does not power People Picker search — any text typed resolves as if valid regardless of
whether the account/group/claim actually exists, unless a custom claims provider with
real search/resolution is built
(`security-for-sharepoint-server-plan-user-authentication.md:327`).

### Windows Classic mode (deprecated)

Classic mode uses plain Windows authentication and treats accounts as AD DS
accounts rather than claims. It can **only** be created via the `New-SPWebApplication`
PowerShell cmdlet — Central Administration only offers claims-based web-application
creation. A classic-mode web app cannot be migrated to claims-based mode without
a dedicated migration procedure, and migration back from claims to classic is not
supported at all
(`security-for-sharepoint-server-plan-user-authentication.md:85`).

The Health Analyzer rule **"One or more web applications are configured to use
Windows Classic authentication"** fires whenever any web app is still in Classic mode,
because many SharePoint Server features require claims-based auth; the documented
resolution is migrating the web application to claims-based authentication
(`technical-reference-one-or-more-web-applications-are-configured-to-use-windows-classic-authenticatio.md:21-27`).

## Contradictions / caveats

The corpus does not give an explicit end-of-support date for Windows Classic mode —
only that it is deprecated and flagged by a standing Health Analyzer rule. Treat "still
supported but actively discouraged" as the accurate characterization rather than
"removed."
