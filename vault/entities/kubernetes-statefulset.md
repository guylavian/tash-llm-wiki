# Kubernetes StatefulSet

**A StatefulSet is the workload controller for applications that need stable identity across rescheduling: a persistent ordinal, network name, and volume — where a [[kubernetes-deployment]]'s stateless, interchangeable Pods are the wrong fit.**

## When to use it
Use a StatefulSet when the app needs one or more of:
- Stable, unique network identifiers (each Pod gets a predictable DNS name).
- Stable, persistent storage per Pod, provisioned via `.spec.volumeClaimTemplates`.
- Ordered, graceful deployment and scaling.
- Ordered, automated rolling updates.

If none of that is required, use a Deployment or ReplicaSet instead — they're simpler to operate.

## Pod identity
Each Pod in a StatefulSet gets a unique identity made of an **ordinal** (an integer, 0 through N-1 by default), a **stable network identity**, and **stable storage** — the identity sticks to the Pod across rescheduling.

## Storage and networking requirements
- Storage must come from a `PersistentVolume` provisioner (dynamic, via a StorageClass) or be pre-provisioned by an admin.
- **Deleting or scaling down a StatefulSet does NOT delete its PersistentVolumeClaims** — a deliberate data-safety default; volumes must be cleaned up separately.
- A StatefulSet requires a **Headless Service** (`clusterIP: None`) to provide the network identity of its Pods — you create this Service yourself, it is not automatic.

## Rolling updates and forced rollback
With the default `OrderedReady` pod management policy, a rolling update can get stuck in a broken state that needs **manual intervention to repair** (a forced rollback) — this is a known limitation, not a bug.
