# Protection API and PAT

**The Protection API is a UMA-compliant set of endpoints that lets a resource server remotely manage its own resources, permission tickets, and (per-user) policies. Access requires a special access token — the PAT — carrying the `uma_protection` scope.**

## Capabilities
- **Resource Management** — create/read/update/delete and query resources (and scopes) via the **Resource Registration Endpoint** (`/realms/{realm}/authz/protection/resource_set`). Lets [[policy-enforcer|policy enforcers]] query which resources need protection.
- **Permission Management** — issue and manage [[permission-ticket|permission tickets]] via the **Permission Endpoint** (`/realms/{realm}/authz/protection/permission`). In UMA only resource servers may create tickets.
- **Policy API** — set permissions on resources on behalf of users via `/realms/{realm}/authz/protection/uma-policy`.

Only resource servers may call these endpoints (enforced by the `uma_protection` scope). Remote management is gated by the resource server's **Remote Resource Management** toggle.

## PAT — Protection API Token
A PAT is an ordinary OAuth2 access token whose scope is `uma_protection`. When you create a resource server, RHBK auto-creates a `uma_protection` role and assigns it to the client's **service account**. Obtain a PAT like any token, e.g. via `client_credentials`:

```
curl -X POST -H "Content-Type: application/x-www-form-urlencoded" \
  -d 'grant_type=client_credentials&client_id=${client_id}&client_secret=${client_secret}' \
  http://${host}:${port}/realms/${realm}/protocol/openid-connect/token
```

Any supported client authentication method works (secret, JWT, etc.). The returned token's `expires_in` in the example is 300s.

## Discovery
Endpoint locations come from the UMA2 discovery document:
`GET /realms/{realm}/.well-known/uma2-configuration` — exposes `token_endpoint`, `token_introspection_endpoint`, `resource_registration_endpoint`, `permission_endpoint`, and `policy_endpoint`.

## Contradictions / caveats
- Stable across RHBK **26.0–26.6**.
- The PAT is *not* the [[requesting-party-token|RPT]]: a PAT authorizes *managing* protected resources; an RPT *carries granted permissions* for accessing them (inferred — a distinction synthesized across the two guide chapters, not stated as a single side-by-side comparison in either).
- Token validation of PATs/RPTs follows normal rules — see [[oidc-token-validation]] and [[tokens-and-sessions]].
