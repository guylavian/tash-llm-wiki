# Expired sessions linger in PostgreSQL

**Symptom → cause → fix for `user_session` rows surviving logout/expiry under RHBK 26 persistent sessions.**

## Body
**Symptom.** Sessions disappear from the Admin UI but rows remain in PostgreSQL
(`user_session` count >> UI count) for ~10–15 minutes. Under high login churn
this can saturate the DB or exhaust the JDBC connection pool.

**Cause.** Lazy/asynchronous cleanup. With `persistent-user-sessions` (default
in RHBK 25/26) the `UserSessionPersister` background task batch-deletes expired
rows on a schedule (default 900 s), so DB deletion lags eviction from the
Infinispan cache.

**Fix.** Three options (from the public KB body):

1. Tune cleanup cadence in `conf/keycloak.conf`:
   ```properties
   spi-user-sessions-jpa-expiration-cleanup-interval=300
   spi-user-sessions-jpa-expiration-batch-size=5000
   ```
2. Move sessions to RAM (eliminates the DB session load):
   ```
   --features-disabled=persistent-user-sessions
   ```
   Caveat: if **all** nodes restart together, all users are logged out.
3. Shorten timeouts: align *SSO Session Idle* / *SSO Session Max*
   (Realm Settings > Sessions) to business needs so the task processes less data.

Also: raise PostgreSQL autovacuum aggressiveness and ensure indexes on the
session expiration/timestamp columns.

Applies to RHBK 26.x (25/26 with `persistent-user-sessions` on) on PostgreSQL.

## Contradictions / caveats
Disabling persistent sessions trades durability for DB load — see
[[session-persistence-volatile]] for the volatile (cache-as-source-of-truth)
model and its restart semantics.
