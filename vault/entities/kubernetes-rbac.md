# Kubernetes RBAC (Roles, Bindings, ClusterRoles)

**RBAC authorizes an already-authenticated identity by checking its bound Roles' rules (verb + resource) against the requested action; no matching rule ⇒ deny by default.**

## Core objects
- **Rule** — a set of permitted verbs (`get`, `list`, `create`, `update`, `delete`, `deletecollection`, `watch`) on a set of resources.
- **Role / ClusterRole** — a collection of rules. A `Role` is namespaced; a `ClusterRole` is cluster-wide.
- **RoleBinding / ClusterRoleBinding** — associates a user, group, or [[service-accounts|ServiceAccount]] with a Role. A `ClusterRoleBinding` grants cluster-wide; a `RoleBinding` can reference **either** a `Role` or a `ClusterRole`, but only grants within its own namespace — the standard way to reuse a cluster-wide permission set (e.g. `view`) scoped to one project.

## OpenShift's two-level hierarchy (OpenShift-specific)
OpenShift layers cluster RBAC (applies everywhere) and local/project RBAC (scoped to one project) on top of upstream Kubernetes RBAC, and evaluates both together: cluster-wide allow rules, then locally-bound allow rules, then deny by default. A `ClusterRoleBinding` at the cluster level differs sharply from binding `cluster-admin` via a **local** `RoleBinding` — the latter only grants `admin`-plus-a-few privileges *inside that one project*, not real cluster-admin. This is a common misconfiguration trap the OpenShift docs call out explicitly (inferred: framed as the "confusing in the web console" pitfall from `kb:authentication-4-22-using-rbac`).

## Default cluster roles (OpenShift-specific)
| Role | Grants |
|---|---|
| `cluster-admin` | Full control over every action/resource in every project |
| `admin` | View/modify anything in a project except quota |
| `edit` | Modify most objects, but not roles/bindings |
| `view` | Read-only, cannot see roles/bindings |
| `basic-user` | Basic project/user info |
| `self-provisioner` | Can create their own projects |
| `cluster-status` / `cluster-reader` | Cluster status / read-most-objects |

Default roles are reconciled automatically on upgrade (missing permissions re-added); manual edits survive but disable reconciliation, so a customized default role needs manual policy updates on every upgrade thereafter.

## Evaluation order
1. Identity (user + groups) + the requested project-scoped action are matched against all applicable bindings.
2. Bindings resolve to Roles, Roles resolve to Rules.
3. First matching rule wins (allow); no match ⇒ deny.

## Good practice (upstream, inferred)
Grant the minimum verbs needed; avoid `get pods/exec` / wildcard verbs except where execution access is truly required — OpenShift's docs flag these as effectively execution privileges and call for least-privilege review (upstream Kubernetes RBAC good-practice guidance applies directly since OpenShift RBAC is a superset, not a fork).
