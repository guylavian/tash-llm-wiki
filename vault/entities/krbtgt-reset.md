# krbtgt Password Reset

**The `krbtgt` account holds the key that signs and encrypts every Kerberos TGT in a domain; resetting its password rolls that key, so all tickets minted under the old key stop being valid.**

## Body

The `krbtgt` user account is the domain's Key Distribution Center (KDC) service
account. Its password-derived key signs/encrypts Ticket-Granting Tickets, so changing
the password invalidates tickets issued before the change. This is why the
[[ad-forest-recovery]] procedure resets it as part of cleaning up after a forest-wide
compromise.

**Reset it twice, waiting between resets.** The krbtgt account keeps a password
**history of 2** (the two most recent passwords). Resetting once leaves the prior key
still usable for replication/validation; resetting **twice** flushes the old key out
of the history so no DC can still authenticate with it. You must wait **10 hours**
between the two resets — that's the default *Maximum lifetime for user ticket* and
*Maximum lifetime for service ticket*; if those policy values were changed, wait
longer than the configured maximum so in-flight tickets expire before the second
reset.

The password value you type is irrelevant — the system generates a strong password
automatically regardless of what you enter.

**Golden Ticket relevance** (inferred): a Golden Ticket is a forged TGT an attacker
mints offline using a stolen krbtgt key, granting arbitrary, long-lived domain access.
Because the forgery depends on the krbtgt key, the double krbtgt reset is the
authoritative remediation — once both old keys are out of history, every forged ticket
becomes unusable (inferred from how the krbtgt key signs TGTs and the two-reset
history-flush mechanic).

## Contradictions / caveats

- **RODCs are different.** This procedure applies to **writable** DCs only. Each
  read-only DC has its own krbtgt account named `krbtgt_<number>`; if you plan to
  recover an RODC during the forest recovery, **do not delete** its krbtgt account.
- **Custom password filters.** A customized password filter (e.g. `passfilt.dll`) on a
  DC can cause the krbtgt reset to error; Microsoft KB 2549833 documents a workaround.
- **Don't skip the wait.** Resetting both passwords back-to-back without the lifetime
  wait can break replication or service tickets still in flight (inferred from the
  source's emphasis on the 10-hour interval).
