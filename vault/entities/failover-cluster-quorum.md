# Failover Clustering & Quorum

**Failover Clustering groups independent servers (nodes) so that clustered roles
automatically fail over between them; quorum is the voting mechanism that decides
whether the cluster is allowed to keep running.**

## Body

Nodes are interconnected over both physical cabling and a private heartbeat
network; clustered roles are health-monitored and restarted/migrated on failure.
Clusters can run **active-active** (all nodes share load) or **active-passive**
(standby nodes take over only on failure).

**Quorum** exists to prevent split-brain: each node gets a vote, and a **quorum
witness** (an extra tie-breaking vote) can be added. The cluster needs a strict
majority of active votes to keep running; if votes drop below that, the cluster
service stops rather than risk two halves of the cluster acting independently.
Three witness types:

- **Cloud witness** — an Azure Blob Storage container (`msft-cloud-witness`), one
  blob per cluster, shareable across many clusters from one storage account.
- **Disk witness** — a small shared disk holding the cluster configuration
  database; needs shared storage all nodes can reach.
- **File share witness** — an SMB share (works without shared disks — the required
  choice for Storage Spaces Direct, SQL Always On AG, or Exchange DAG clusters,
  none of which use shared disks).

Best practice: keep an **odd number** of total voting elements; add a witness when
the node count is even. **Dynamic quorum management** lets the cluster
automatically adjust which nodes hold votes as nodes shut down in sequence, so it
can keep running down to the last surviving node — but it still can't survive the
simultaneous loss of a voting majority, and **a Storage Spaces Direct cluster can
tolerate only up to two node failures regardless of dynamic quorum**.

**Recovery when quorum is lost:** `Start-ClusterNode -ForceQuorum` force-starts a
node in **ForceQuorum** mode, overriding the normal quorum requirement (Event ID
1177 is logged when the cluster service stops for lost quorum). Remaining nodes
should then be started with `-PreventQuorum` so they rejoin the forced cluster
instead of forming a second, competing instance. Once the cluster regains enough
votes it automatically leaves ForceQuorum mode.

## Contradictions / caveats

"No majority (disk witness only)" quorum mode is documented but explicitly
**not recommended** — it makes the disk witness a single point of failure for the
whole cluster.
