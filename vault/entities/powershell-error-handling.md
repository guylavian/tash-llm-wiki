# PowerShell Error Handling (try/catch/finally)

**`try`/`catch` is the modern way to handle errors in PowerShell, but it only catches
**terminating** errors — a non-terminating error (the default for most cmdlets) must be
converted to terminating with `-ErrorAction Stop` before `catch` will ever run.**

## Body

### Terminating vs. non-terminating

```powershell
function Test-MrErrorHandling {
    [CmdletBinding()]
    param (
        [Parameter(Mandatory, ValueFromPipeline, ValueFromPipelineByPropertyName)]
        [string[]]$ComputerName
    )
    process {
        foreach ($Computer in $ComputerName) {
            try {
                Test-WSMan -ComputerName $Computer
            }
            catch {
                Write-Warning -Message "Unable to connect to Computer: $Computer"
            }
        }
    }
}
```

Even though this function *has* error handling, it still produces an **unhandled exception**
when `Test-WSMan` fails, because that failure is a non-terminating error and "only terminating
errors are caught." Adding `-ErrorAction Stop` to the `Test-WSMan` call turns the non-terminating
error into a terminating one that the surrounding `catch` block actually intercepts
(`reference/powershell/powershell-powershell-scripting-powershell-7-6-p0201-0240.md:569-614`).

### `$ErrorActionPreference`

Don't modify the *global* `$ErrorActionPreference` variable unless it's truly necessary — if you
change it inside a local scope, it reverts to its previous value on exiting that scope. If a
function calls straight into a .NET method (where there's no `-ErrorAction` parameter to set),
change `$ErrorActionPreference` immediately before that call instead
(`reference/powershell/powershell-powershell-scripting-powershell-7-6-p0201-0240.md:631-637`).

## Contradictions / caveats
None noted — this is uncontested, version-stable PowerShell language behavior.
