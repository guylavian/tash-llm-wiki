# PowerShell Functions and Advanced Functions

**Adding `[CmdletBinding()]` to a function's `param()` block turns it into an "advanced function"
that behaves like a compiled cmdlet — it automatically gains the common parameters, and
`[CmdletBinding(SupportsShouldProcess)]` adds the `-WhatIf`/`-Confirm` risk-mitigation
parameters.**

## Body

### Naming and lifecycle

Functions load into the `Function:` PSDrive once defined; `Get-ChildItem -Path Function:\Get-*`
lists them, and `Get-ChildItem -Path Function:\Get-*Version | Remove-Item` (or closing the
session, or `Remove-Module` for a function that shipped in a module) unloads them
(`reference/powershell/powershell-powershell-scripting-powershell-7-6-p0201-0240.md:1-53`).
Because a function can silently shadow a built-in cmdlet with the same name, a documented
practice is prefixing the noun with your own initials to keep the name unique (e.g.
`Get-MrPSVersion` instead of `Get-Version`)
(`reference/powershell/powershell-powershell-scripting-powershell-7-6-p0201-0240.md:14-25`).

### CmdletBinding and common parameters

A plain function like:

```powershell
function Test-MrParameter {
    param ($ComputerName)
    Write-Output $ComputerName
}
```

exposes only its declared parameters. Adding `[CmdletBinding()]` — which requires a `param()`
block, even an empty one — automatically adds the **common parameters**: `Verbose`, `Debug`,
`ErrorAction`, `WarningAction`, `InformationAction`, `ErrorVariable`, `WarningVariable`,
`InformationVariable`, `OutVariable`, `OutBuffer`, `PipelineVariable`
(`reference/powershell/powershell-powershell-scripting-powershell-7-6-p0201-0240.md:150-230`).
`[CmdletBinding(SupportsShouldProcess)]` additionally adds `-WhatIf` and `-Confirm`, meant for
functions that make changes
(`reference/powershell/powershell-powershell-scripting-powershell-7-6-p0201-0240.md:228-260`).

## Contradictions / caveats
None noted — this is uncontested, version-stable PowerShell language behavior.
